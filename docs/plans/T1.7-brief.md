# T1.7 Brief: Scheduler + silent ticks, Expo push client, receipts

## Task

**ID:** T1.7
**Title:** Scheduler + silent ticks: APScheduler in lifespan, `tick` job per device in `monitoring`, Expo push client (silent), `push_notifications` table (migration 0002), receipts job, window start/end transitions, `fallback` state
**Size:** M (≈ 1 day)
**Depends:** T1.6 (telemetry endpoint, day state machine, get_or_create_day, on_confirmed hook)
**Acceptance criteria** (from the plan):
1. With a fake Expo client, a simulated day sends ticks every 5 min inside the window only.
2. Ticks stop on confirm (day.state → confirmed).
3. Day transitions to `fallback` at window end (state idle/monitoring → fallback).
4. Receipts recorded (push_notifications table rows with receipt_status).
5. `MessageRateExceeded` error backs off (next tick delayed by one interval).

---

## Why it matters

T1.7 connects the confirmed day to delivery and drives the core morning routine:

- **Without ticks**, the phone never wakes to sample signals (D04). No telemetry → no scoring → no morning.
- **Without window-start / window-end transitions**, the day state machine stalls at `monitoring`. No fallback → no push if the owner never reaches the confirm threshold (D07).
- **Without Expo push**, silent notifications don't reach the phone (D15). The app cannot run in background.
- **Without receipt tracking**, the system has no feedback on whether pushes arrived (D28 observability). Cannot detect throttling or device registration issues.
- **Without error handling** (MessageRateExceeded backs off, DeviceNotRegistered clears token), the morning sequence breaks on iOS throttling or app reinstallation.
- **`next_tick_in_sec` in telemetry response** tells the app when to expect the next tick; the debug panel shows it; replay tools use it.

T1.7 is the plumbing that transforms "a day with rules" (M1) into "a ringing alarm on your iPhone" (a usable morning).

## Governing decisions

| ID | Binding constraint |
|---|---|
| D04 | **Background wake mechanism**: silent pushes every `tick_interval_min` (5 min default) wake the app; the server drives the ticks. |
| D07 | **Window**: weekdays 06:00–11:00, weekends 08:00–14:00, phone's IANA tz. **Fallback delivery at window end** (11:00 weekday, 14:00 weekend) if not confirmed. |

| D28 | **Observability**: structlog JSON events + counters; `/metrics` (Prometheus text format); nightly report. Secret fields never logged. |

## Inputs and outputs

### Input: Silent tick payload (to Expo)

**What T1.7 sends to `exp.host` on each tick (docs/05 §6)**:

```json
{
  "to": "ExponentPushToken[xxxxxx]",
  "_contentAvailable": true,
  "priority": "high",
  "data": {
    "type": "tick",
    "local_date": "2026-10-06",
    "tick_seq": 15,
    "window_start": "2026-10-06T06:00:00+05:30"
  }
}
```

- `_contentAvailable`: signals silent push (no alert shown); ios app woken in background.
- `priority: "high"`: Expo passes to APNs with high priority (delivery within seconds).
- `data`: payload delivered to app; no `title` or `body` (silent, no banner).
- `window_start`: the window's start time in the device's local timezone (included so app can validate it locally).

### Output: Expo `send()` response → `push_notifications` table

**Expo POST /--/api/v2/push/send returns**:

```json
{
  "data": [
    {
      "id": "95a635f5-30a2-4d81-97ca-e0f1e82b6e78",
      "status": "ok"
    }
  ]
}
```

Or on error:

```json
{
  "data": [
    {
      "status": "error",
      "message": "MessageRateExceeded"
    }
  ]
}
```

**Errors (docs/05 §6 push payloads; Expo SDK reference)**:
- `ok`: ticket_status=ok.
- `DeviceNotRegistered`: token is invalid; device.expo_push_token should be cleared; stop ticks for this device.
- `MessageRateExceeded`: iOS throttled this device; back off: delay next tick by `tick_interval_min`.
- `MessageTooBig`: payload > Expo size limit (not expected for tick payloads).
- `InvalidCredentials`: CHRONOS_EXPO_ACCESS_TOKEN is wrong (caught in startup check).

**Receipts**: fetched 15+ min later via GET /--/api/v2/push/getReceipts**:

```json
{
  "data": {
    "95a635f5-30a2-4d81-97ca-e0f1e82b6e78": {
      "status": "ok"
    }
  }
}
```

Or receipt_status = `DeviceNotRegistered`, `MessageTooBig`, etc. Receipts available for ~24 h.

## Constraints

### Timing and scheduling

- **Tick interval**: 5 min (configurable via `config.wake_rules.yaml` `tick_interval_min`, 2–30 min range, validated).
- **Ticks sent during [window_start_utc, window_end_utc)**: half-open window. A tick at 10:59:50 UTC (in-window) sends; a tick at 11:00:00 UTC (at end_utc) does not.
- **Tick cadence**: `tick_instants(window, tick_interval_min)` returns the exact UTC seconds at which ticks are generated.
- **Transition timing**:
  - **window start** (window_start_utc reached): scheduler wakes idle → monitoring (logs cause=scheduler_window_start).
  - **window end** (window_end_utc reached): scheduler wakes monitoring → fallback (logs cause=scheduler_window_end). No-op if already confirmed/delivered.
- **Scheduler loop**: runs every 1 second (or every minute for a cheaper loop); each invocation checks "what's due now?" and executes.
- **Process restart resilience**: day state and last tick seq are in the DB. On restart, scheduler re-derives what ticks have been sent (from push_notifications max(tick_seq)) and resumes.
- **Confirm stops ticks**: once day.state = confirmed, T1.7 stops enqueuing ticks for that day (no further ticks sent after confirm).

### Push API and rate limiting

- **Expo endpoint**: https://exp.host/--/api/v2/push/send (fixed, D15).
- **Authentication**: `Authorization: Bearer <CHRONOS_EXPO_ACCESS_TOKEN>` (from Settings).
- **MessageRateExceeded handling**: when received, delay the *next tick by one interval* (e.g., from 5 min to 10 min for this device) and continue. After 3 consecutive throttles (configurable), give up until the next day.
- **Chunking**: send up to 100 messages per request (Expo limit).
- **Timeout**: 10 s per request (T1.7 uses httpx, D09 says no cloud APIs by default — this is Expo which is the default push provider per D15).
- **Retries**: on 5xx / 429, back off (exponential or fixed) up to 3 attempts, then fail the tick and log.

### Security

- **SSRF guard**: push requests to Expo use the SSRF-guarded HTTP client (T3.2) with pinned host https://exp.host only.
- **No secrets in logs**: `ticket_id`, `error`, `receipt_status` can be logged; never log the token. T1.7 should verify structlog redaction of `authorization` header.
- **Device bearer token**: required for all telemetry to fetch device.expo_push_token; ticks are server-initiated so they don't need bearer auth on this endpoint, but the scheduler checks that device.status = active.
- **Device token cleared on error**: if Expo returns `DeviceNotRegistered`, clear device.expo_push_token and log (once per day, not per tick).

### Concurrency and state

- **Single scheduler instance per process**: APScheduler (D10) or a hand-rolled asyncio loop. One loop, one thread (or async task) that drives ticks for all devices.
- **Multiple devices (future)**: each active device with a push token gets its own tick stream for its window. Today (v1) there is exactly one active device.
- **Day state transitions atomic**: the scheduler checks day.state and compares UTC now against window bounds; if a transition is due, it calls a pure state-change function and commits. No race condition with telemetry endpoint (both use SQLite locking).

### Observability and metrics

- **Logging** (structlog): log every tick send (device_id, local_date, tick_seq, ticket_id, error if any), every state transition (from_state, to_state, cause), every receipt check result.
- **Counters** (D28): `chronos_ticks_sent_total{device}`, `chronos_push_errors_total{kind, error_code}`, `chronos_day_state{state}` (last observed).
- **Nightly report** includes: ticks sent vs received, confirm time, fallback reason if used, push errors.

## Edge cases

### 1. Process restart mid-window

**Scenario:**
- Day: state=monitoring, ticks_sent=6 (ticks at 06:00, 06:05, 06:10, 06:15, 06:20, 06:25 sent).
- Process restarts at 06:27.
- Scheduler resumes; now=06:27 UTC.

**Expected outcome:**
- Fetch day; state=monitoring; next tick is due at 06:30.
- Query `MAX(tick_seq) FROM push_notifications WHERE device_id=? AND local_date=?` → tick_seq=5 (0-indexed, so 6 ticks sent, last one is seq 5).
- Next tick_seq = 6.
- At 06:30, send tick with tick_seq=6.
- Continue normally.

### 2. MessageRateExceeded backoff

**Scenario:**
- Tick at 06:20: success (ticket_status=ok).
- Tick at 06:25: Expo returns error ticket_status=error, error=MessageRateExceeded.
- Next scheduled tick would be 06:30.

**Expected outcome:**
- Log warning: "MessageRateExceeded for device 5; backing off".
- Push record with ticket_status=error, error=MessageRateExceeded.
- Delay next tick by one interval: instead of 06:30, next tick is 06:35.
- At 06:35: send tick; if success, resume 5-min interval (next at 06:40).

### 3. DeviceNotRegistered → clear token

**Scenario:**
- Tick sent at 06:15 to device with expo_push_token=ExponentPushToken[xxxxx].
- Expo returns error=DeviceNotRegistered (app reinstalled, token expired, etc.).

**Expected outcome:**
- Push record: ticket_status=error, error=DeviceNotRegistered.
- Query device; update device.expo_push_token = NULL.
- Log once per day (not per tick): "DeviceNotRegistered; token cleared for device 5".
- On next tick: device.expo_push_token = NULL → skip sending this device (log "device has no push token", continue).
- On next pairing or app re-register: app sends new token via PATCH /v1/device/me; device.expo_push_token updated.

### 4. Confirm arrives during window

**Scenario:**
- Ticks scheduled: 06:00, 06:05, 06:10, 06:15, 06:20, 06:25, 06:30, ...
- Tick 06:15: score=72, decision=high.
- Tick 06:20: score=88, decision=confirm → day.state = confirmed.
- Scheduled tick 06:25 is queued.

**Expected outcome:**
- At 06:25, scheduler wakes to check what's due.
- Fetch day; state=confirmed.
- Skip sending ticks (check: if day.state != monitoring, skip tick enqueue for this device).
- No tick sent.

### 5. Window end while in monitoring state

**Scenario:**
- Window: 06:00–11:00.
- At 10:55, day.state=monitoring (never confirmed).
- At 11:00 UTC, scheduler checks window_end.

**Expected outcome:**
- Fetch day; window_end_utc <= now; state=monitoring.
- Transition: monitoring → fallback (insert DayTransition with cause=scheduler_window_end).
- Update day.state=fallback, day.updated_at.
- On_fallback hook called (no-op in T1.7; T5.2 wires delivery).

### 6. Window end with already-confirmed day

**Scenario:**
- At 07:30: confirmed (tick with high score).
- At 11:00: window end.

**Expected outcome:**
- Fetch day; state=confirmed (not monitoring).
- No transition (already confirmed).
- Scheduler detects no action needed; logs "day already confirmed, skipping window_end transition".

### 7. Multiple devices with different timezones

**Scenario:**
- Device 1: tz=Asia/Kolkata (+05:30), window 06:00–11:00 local = 00:30–05:30 UTC.
- Device 2: tz=America/New_York (−05:00), window 06:00–11:00 local = 11:00–16:00 UTC.
- Scheduler running in UTC.

**Expected outcome:**
- Each device has its own days row per local_date, with its own window_start_utc / window_end_utc (computed in create_or_create_day).
- Scheduler iterates all active devices with push tokens; for each, checks its windows[local_date].
- At UTC 00:30, device 1's window opens → state=monitoring.
- At UTC 11:00, device 2's window opens → state=monitoring (different day row, different local_date).
- Each device's ticks sent at its own UTC schedule.

### 8. Day boundary (03:00 local)

**Scenario:**
- Device: tz=Asia/Kolkata (+05:30).
- Event at 02:59 local = "2026-10-05T21:29:00Z" (previous calendar date UTC).
- Next event at 03:00 local = "2026-10-05T21:30:00Z" (boundary).
- Local date derived: "2026-10-05" → "2026-10-06".

**Expected outcome:**
- First event: local_date="2026-10-05"; day row created for Oct 5.
- Second event at boundary: local_date_for(..., tz) → "2026-10-06" (boundary crossed).
- New day row created for Oct 6 if it doesn't exist.
- Each day has its own idle/monitoring/confirmed lifecycle.

### 9. Clock jump (device clock corrected or manual set)

**Scenario:**
- Tick sent at 06:20 UTC (expected).
- System clock jumps back 5 min (e.g., NTP sync, manual set).
- Next scheduled tick would have been 06:25 UTC, but now is 06:20 UTC again.

**Expected outcome:**
- Scheduler's "now" function uses system time. After jump, now < expected_next_tick.
- Tick not sent (next_tick > now).
- No duplicate tick; the scheduler waits until actual 06:25.
- Telemetry from phone with skewed device_ts may be rejected by the endpoint (T1.6 clock_skew check).

### 10. No window for a date (holiday special case)

**Scenario:**
- Config has `holidays_as_weekend: ["2026-10-14"]` (Dussehra, treated as weekend).
- Oct 14 is a weekday (Tuesday), but rules say treat it as weekend → window 08:00–14:00.

**Expected outcome:**
- window_for(2026-10-14, tz, config) → kind=weekend, window 08:00–14:00 (local).
- Ticks sent at 08:00, 08:05, ..., 13:55 (stopping before 14:00).
- Fallback at 14:00 if not confirmed.

### 11. `next_tick_in_sec` in telemetry response

**Scenario:**
- Tick sent at 06:15; device samples and POSTs telemetry at 06:15:30.
- Endpoint processes telemetry at server time 06:15:35 UTC.
- Next tick scheduled for 06:20 UTC.

**Expected outcome:**
- Scheduler's internal state has `next_tick_utc[device_id] = 06:20`.
- Telemetry endpoint queries this state; computes `next_tick_in_sec = (06:20:00 − 06:15:35) = 265 s` (or similar).
- Response includes `"next_tick_in_sec": 265`.
- App shows this in debug panel (useful for manual testing).

### 12. Receipts job checks after 15 min

**Scenario:**
- Tick 1 sent at 06:15, ticket_id=id1, ticket_status=ok, receipt_status=NULL.
- 15 min later (06:30), receipts job runs.
- Query push_notifications: WHERE receipt_status IS NULL AND sent_at < (now − 15 min) AND kind='tick'.
- Fetch receipts for ticket_id=id1 from Expo.

**Expected outcome:**
- If receipt found: receipt_status=ok (or error code), receipt_checked_at updated.
- If receipt not found: leave receipt_status=NULL, retry next check.
- After 24 h, Expo drops the receipt; retention job (T5.1) deletes the row from push_notifications.

## Proposed approach

**Five modules:**

### 1. **`chronos/scheduler.py`** — Main scheduler loop

- Class `Scheduler`:
  - `__init__(session_factory, settings, logger)`: store dependencies.
  - `async start()`: spawns background task (asyncio.Task) that runs the main loop.
  - `async stop()`: cancels background task; waits for cleanup.
  - `async _run_loop()`: infinite loop that runs every 1 second (or every minute for efficiency):
    - Check what's due: `run_due(now: datetime)`.
    - For each due action, execute (fetch day, check state, transition if needed, send tick if monitoring).
  - `async run_due(now: datetime) -> None`: stateless; queries DB to find:
    - All devices with status=active and expo_push_token IS NOT NULL.
    - For each device, check its current local_date in its tz.
    - Fetch (or create) days row for (device, local_date).
    - Check against window: is now in [start_utc, end_utc)?
      - Before start: skip.
      - In window: if day.state=idle, transition to monitoring (cause=scheduler_window_start). If day.state=monitoring, send tick if due (next_tick_utc <= now).
      - At/after end: if day.state=monitoring, transition to fallback (cause=scheduler_window_end).
    - Track state: `last_tick_utc[device_id]` so we know when the next one is due.

- **Deterministic for testing**: accept `now: datetime` parameter (dependency inject, frozen in tests).

### 2. **`chronos/delivery/push.py`** — Expo push client

- Abstract base class `PushClient`:
  - `async send(messages: list[PushMessage]) -> list[Ticket]`: send up to 100 messages; return tickets with status and ticket_id.
  - `async get_receipts(ticket_ids: list[str]) -> dict[str, Receipt]`: fetch receipt statuses for ticket IDs.

- Class `ExpoPushClient(PushClient)`:
  - `__init__(access_token: SecretStr | None, http_client: httpx.AsyncClient)`: store token and HTTP client.
  - `async send(messages) -> list[Ticket]`: POST to https://exp.host/--/api/v2/push/send with Authorization header. Parse response; chunk > 100 messages.
  - `async get_receipts(ticket_ids) -> dict[str, Receipt]`: GET with ticket IDs as query param. Handle up to 1000 tickets per request (Expo limit).
  - Handle errors: DeviceNotRegistered → clear token; MessageRateExceeded → log backoff; retry on 5xx / 429.

- Class `FakePushClient(PushClient)` (for testing):
  - `async send(messages) -> list[Ticket]`: return ok tickets with mock ticket_ids (or configurable errors).
  - `async get_receipts(ticket_ids) -> dict[str, Receipt]`: return mock receipts (configurable per test).

- Pydantic models:
  - `PushMessage`: `to` (token), `_contentAvailable`, `priority`, `data` (dict).
  - `Ticket`: `status` (ok / error), `id` (ticket_id), `message` (error text).
  - `Receipt`: `status` (ok / error code).

### 3. **`chronos/scheduler.py` — Push hook**

- Add to `Scheduler._run_loop()` after transitions:
  - If state changed to fallback or confirmed (T5.2 wires delivery): call `on_confirmed(session, day)` / `on_fallback(session, day)` hooks (no-op in T1.7).
  - For window_start transition (idle → monitoring): log, but no push (no visible notification yet; only silent ticks).
  - For window_end transition (monitoring → fallback): log (delivery is T5.2's job).

### 4. **`chronos/jobs/receipts.py`** — Receipts checker job

- Function `check_receipts(session, push_client, now)`:
  - Query: `SELECT * FROM push_notifications WHERE receipt_status IS NULL AND sent_at < (now − 15 min) AND kind IN ('tick', 'reel_ready', 'text_fallback')`.
  - Collect ticket_ids; chunk into groups ≤ 1000.
  - For each chunk, call `push_client.get_receipts(ticket_ids)`.
  - Update rows: `UPDATE push_notifications SET receipt_status=..., receipt_checked_at=now WHERE ticket_id=...`.
  - Log: "checked X receipts, found Y ok, Z errors".

- Called from scheduler every 15 min (or as a jobs table entry if T3.1 is available; for M1, inline in scheduler).

### 5. **Migration 0002** (`alembic/versions/0002_push_notifications.py`):
- Create `push_notifications` table with columns from data model §2.5.
- Add indexes: `(device_id, local_date)`, `(kind)`, unique `(ticket_id)`.
- Down: drop table.

## Risks

### Most likely to go wrong

1. **Tick sent after confirm, polluting telemetry**:
   - Risk: scheduler sends tick at 06:25 before seeing day.state=confirmed (set at 06:20 by telemetry endpoint).
   - Test: mock scheduler loop with frozen time; telemetry endpoint sets state=confirmed; next tick iteration skips.

2. **MessageRateExceeded not backed off, flood Expo**:
   - Risk: every 5 min, retry the same device, hit 429 again.
   - Test: FakePushClient returns MessageRateExceeded; verify next tick delayed; counter incremented.

3. **DeviceNotRegistered token not cleared, infinite retry**:
   - Risk: device.expo_push_token still set; ticks keep failing.
   - Test: FakePushClient returns DeviceNotRegistered; verify device.expo_push_token set to NULL; next tick skips (no token).

4. **Receipt checker crashes on malformed response**:
   - Risk: Expo returns unexpected JSON; code assumes known shape.
   - Test: FakePushClient returns malformed receipt; assert error logged (not crash).

5. **Process restart loses tick state, resends old ticks**:
   - Risk: last_tick_seq not recovered from DB; next tick is 0 (duplicate).
   - Test: query MAX(tick_seq) from push_notifications; verify next tick_seq is max+1.

6. **Window boundary race (11:00:00.000000Z)**:
   - Risk: tick sent at 10:59:59, then window_end transition fires at 11:00:00, causing inconsistent state.
   - Test: frozen time at window boundary; verify half-open interval [start, end).

7. **Multiple devices, same window time, race condition**:
   - Risk: two devices on same Wi-Fi, window starts at 06:00 UTC for both; both transition to monitoring; one blocks the other.
   - Test: mock scenario with two devices; verify both transition and receive first tick.

8. **Telemetry endpoint receives old tick in outbox after window end**:
   - Risk: device offline, re-enters outbox at 11:05 UTC for a tick sent at 06:15. Day is already fallback. Evaluation should still be stored and counted.
   - Test: window end transition sets state=fallback; old telemetry arrives; verify evaluation stored with decision=already_confirmed, no state change.

- **Mock Expo responses**: FakePushClient returns ok, error, MessageRateExceeded, DeviceNotRegistered scenarios; verify behavior.
- **DB recovery test**: insert ticks into push_notifications; restart scheduler; verify tick_seq continues from max+1.
