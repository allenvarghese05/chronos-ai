## 2. Why it matters

The next tasks need durable stage identity, bounded execution and restart recovery rather than an in-memory background callback. A duplicate claim can repeat side effects; an expired lease can be more dangerous if the original process is still running. Different jobs running simultaneously can also exceed the laptop's 16-GB budget even if each row is claimed only once.

Queue ownership, actual execution exclusivity and process cleanup are separate obligations. Successful database fencing alone cannot stop an already running renderer. A timeout on an awaitable or thread likewise does not kill its Python work or descendants. The implementation must prove real termination before retry/reclaim and describe at-least-once recovery honestly: arbitrary future external effects cannot be guaranteed exactly once by this queue.

## 4. Current state

### Database, migrations and model conventions

Connections set WAL, `foreign_keys=ON`, `busy_timeout=5000`, `check_same_thread=False`. Migration engine uses `NullPool`; application engine uses SQLAlchemy's normal pool. A Session is not safe to share among concurrent worker operations.
- Actual Alembic chain is revision **`0001` → `08a434829bca`**, the latter stored in `alembic/versions/0002_push_notifications.py`. A file named `0003_...` must reference **`down_revision='08a434829bca'`**, not an invented revision `0002`. Do not rename applied revisions. `alembic/env.py` imports `chronos.models`, uses the shared metadata/PRAGMAs and `render_as_batch=True`.
- Current nine tables: `devices`, `pairing_codes`, `rule_versions`, `telemetry_events`, `wake_evaluations`, `days`, `day_transitions`, `settings`, `push_notifications`. No content, jobs or media tables/classes currently exist. `chronos.models.__init__` explicitly imports every table to register metadata; new models must be added there.
- T1.1 Owner answers require SQLModel table classes, plain FK columns/explicit joins (no `Relationship()`), shared enums with named TEXT CHECK constraints, application-side ULIDs where exposed identifiers require them, and autogenerated then hand-reviewed migrations with schema parity tests. Time helpers are `utc_now_iso() -> str`, `format_utc_iso(dt: datetime) -> str`, `parse_utc_iso(s: str) -> datetime`; queue entry points should require aware instants rather than silently accepting naive values because one formatting helper tolerates them.

New `Brief` must reference the composite day key. Do not prematurely create reels, add unrelated cyclic day/reel links, or renumber old revisions just to fix prose.
- `tests/test_migrations.py:TestMigration0001.EXPECTED_TABLES` currently expects all **nine** head tables despite its old name; it runs `upgrade head`. Extend expected head coverage, preserve assertions and add explicit prior-head upgrade/downgrade tests. `tests/test_migration_0002.py` uses head for table/parity/drift probes; new models must preserve that drift check. `test_schema_constraints.py`, `tests/factories.py` and T1.1 parity assertions provide FK/unique/CHECK conventions.

### Execution, scheduling and process gaps

- There is no `chronos/jobs/`, `chronos/content/`, `chronos/media/`, `pipeline.py`, subprocess wrapper or source configuration file. `services/api/config/` currently contains only `wake_rules.yaml`. T3.2 adds the source loader/fetchers; T3.4 adds script handlers; T3.5 adds enqueue chaining/admin-run/CLI and prewarm. Avoid fake production stage handlers or automatic enqueueing now.
- Existing scheduler is **custom asyncio**, not the old APScheduler sketch: `Scheduler(*, session_factory: Callable[[], Session], push_client: PushClient, settings: Settings, clock: Callable[[], datetime] | None = None)`, with `run_forever(stop_event)`, `run_due(now)` and `run_receipts(now)`. APScheduler is not an installed dependency. Do not rewrite it or introduce that dependency for this queue.
- `main.py:create_app(settings: Settings | None = None) -> FastAPI` creates one engine, initializes rules in lifespan, owns an Expo client, conditionally starts an asyncio scheduler task, then shuts it down before disposing the engine. No worker is started. New worker ownership must survive startup failures/shutdown cancellation and stop before engine disposal; blocking database/process waits must not block the API event loop.
- `Settings.scheduler_enabled` defaults true. CLI `serve(reload=False, host=None, port=None, no_scheduler=False)` sets `CHRONOS_SCHEDULER_ENABLED=false` for `--no-scheduler`, then launches one Uvicorn factory process (no worker-count option). Worker enablement/data-root/stop-budget controls do not exist. An explicit worker setting/disable switch and injectable lifecycle seam should preserve independent scheduler behavior and make tests/isolated API opt out safely.
- Existing production launchd command is `uv run --locked chronos serve` in `services/api`, KeepAlive with normal-user permissions; no separate worker process/service should be added. Caffeinate design variants are `caffeinate -i` around stages and `caffeinate -i -w <pid>` in ops; use the system tool only on macOS with an injectable/platform-safe test seam and guaranteed cleanup.
- Existing `cli.py` uses `subprocess.run(argv, check=False)` to supervise Uvicorn/Alembic, and `ops/doctor.py` has an injectable probe with timeout. These are bootstrap/probe commands, not a media/job wrapper. New pipeline child processes must go through the single new wrapper; converting the long-running CLI server into a finite media job is not this task.
- A thread can orchestrate a job but cannot forcibly stop arbitrary Python code. The task's sleeping-job acceptance requires killable supervised execution, not only `asyncio.wait_for`, `Future.cancel()` or a daemon thread left running. Allowed kind→handler registration must be internal; there must be no network endpoint accepting an argv, module name, arbitrary Python code or environment.
- Documented `locked_at` timeout reclaim is insufficient when the old process still runs. `locked_by` is described as worker ID; using a fresh owner token per claim (with worker identity if needed) can fence every completion/retry/release. A separate OS-held host execution lock can provide actual seriality across competing API/worker instances without another DB table or a dependency, subject to question1.
- Recovered jobs remain at-least-once attempts. Future handlers must make artifact writes/side effects idempotent and only publish while they still own their attempt. A stale owner must not finish/fail/requeue a newer attempt. Reclaim must not accept a reused PID as ownership proof or kill an arbitrary PID read from the DB.

## 6. Constraints

- Do not run heavy handlers inside a database write transaction or keep a SQLite writer lock for an entire stage; that would block telemetry/settings. Claims and fenced state updates are short transactions; OS execution ownership is separate.
- Enforce both same-row exclusivity and different-row global seriality. Future completion, failure, retry and reclaim updates must compare status and per-attempt ownership. The OS lock path must be stable for the canonical DB/data root across processes, not a different random temp file per worker; prevent accidental duplicate lock identities through relative paths/symlinks.
- Canonical aware UTC wall time controls persistence/run_after; monotonic elapsed time controls actual execution deadlines. Clock jumps, sleep and expired locks must not justify overlapping still-active jobs. Small injectable clocks/backoff sequences make tests deterministic without minutes of sleeping.
- Bounded payload/object validation and finite attempts/timeouts/priorities; no permissive arbitrary module/command serialization. Handler registration is trusted program code, not content data. Unknown/unregistered kinds need an explicit safe policy that does not silently execute fake stages or consume genuine queued work during mixed-version deployment.
- The single wrapper must validate `cwd.resolve()` remains under the configured data root (including symlink escape), take argv lists, allowlist environment, drain output with bounded retained bytes, and terminate/reap the whole tracked process group on timeout/stop. A malicious or faulty child filling stdout must not deadlock or allocate unlimited memory. Error logging must not dump captured secrets simply because output is bounded.
- Caffeinate and the serial lock must cover the real execution lifetime, including a parent crash/orphaned child, and be released after cleanup. Fail closed if cleanup/ownership cannot be established; never start another heavy job merely because a database timestamp expired. No distributed/multi-machine guarantees or arbitrary-external-effect exactly-once promise.
- Keep JSON storage distinct from semantic generated-script validity. Tables are groundwork; no source/network fetch, model invocation, artifact hash-skip implementation, retention deletion or visible delivery is claimed by this task.
- Test fresh migration, upgrade from populated prior head, downgrade only0003 with earlier data intact, base round trip, named constraints/index/FK/metadata drift. Do not remove a failing migration assertion or alter golden score expectations to accommodate the new tables.

## 7. Edge cases

| Concrete case | Expected result |
|---|---|
| Two distinct DB connections claim the same due row | One claim/attempt only; the loser gets no work, without duplicate handler execution. |
| Two workers have two different due heavy jobs | Actual execution remains globally serial, not merely different-row-safe. Readers/telemetry still proceed. |
| Same(kind,key) enqueued concurrently with different payloads | One durable original row; no silent payload replacement/restart. Return existing identity or explicit conflict according to a documented internal API. |
| Priority0 deliver versus priority10 ingest, same run_after | Stable lower priority then ID wins. Future/not-due rows do not block due rows. |
| Running job exceeds timeout; child ignores TERM and spawned a sleeper | Deadline triggers escalation, group reaped, caffeinate cleaned, then retry/failed transition; no residual sleeper or stage overlap. |
| Python handler sleeps/loops instead of spawning a tool | Killable job boundary still enforces deadline; no background thread continues writing after retry. |
| API/worker crashes while handler/descendant remains alive | Next worker cannot overlap it; recovery waits for/terminates the supervised execution safely, then reclaims according to attempt limit. |
| Attempt A expired, attempt B owns row, A returns late | A's success/failure/requeue/lock-release is rejected by ownership check; B remains intact. |
| locked_by resembles a PID now reused by unrelated process | Do not signal it; DB strings are not authority to kill a process. |
| Laptop sleeps or UTC clock jumps forward/backward | No overlap based solely on lease expiry; monotonic execution bounds and real lock ownership remain authoritative. |
| Attempt1 fails, then2, then3 at max_attempts3 | Persist attempts/run_after and deterministic bounded backoff; final failure has finished time/safe reason and is not claimed again. |
| Shutdown arrives during output drain/database busy/child startup | Stop claiming, cancel current work within a documented grace, reap descendants and preserve recoverable fenced state before engine disposal. |
| Two sessions share one Session object | Prohibited; each claim/update/run has its own scoped Session. Tests use actual independent connections. |
| Huge output or invalid UTF8/nonzero exit with secret-looking text | Drain without blocking, retain only bounded bytes, safe summary/error code, no raw payload/secret in API or ordinary logs. |
| `cwd=data/jobs/link` resolves outside data | Reject before spawn. Output paths and key-derived directories cannot escape through traversal or symlink. |
| No caffeinate on Linux CI / macOS adapter failure | Platform-safe injected/no-op Linux behavior; explicit safe macOS failure policy, no orphan assertion/child or fabricated test success. |
| Future kind has no registered handler in this version | No arbitrary code execution and no fake success; explicit unsupported-kind policy, covered by tests. |
| Item high-bit64 simhash / duplicate source external ID | Reversible signed storage convention and named uniqueness; no overflow or data truncation. |
| Brief references nonexistent composite day / brief-item nonexistent item | FK rejects it; brief retention prevents deleting referenced items. |
| Populated0002 DB upgrades then downgrades0003 | Existing pairing/rules/telemetry/push data remain unchanged; only the five new tables are removed in safe order. |
| GET jobs without/revoked token, bad status/limit/cursor | Existing401/403/422/429 behavior; no queue mutation or unbounded response. |
| Job payload/error contains bearer/path/feed text | Safe projection omits it; test response/log scan proves absence. |

## 8. Proposed approach

1. Add content/job SQLModel tables, shared enums and named constraints/indexes; migration0003 chains from actual revision08a434829bca, with fresh/populated up/down/drift tests.
2. Implement internal validated enqueue/atomic claim/fenced completion/retry/reclaim APIs using independent short-lived Sessions, aware fixed clocks and bounded backoff; keep stage keys/payload immutable.
3. Subject to question1, combine a canonical data-root OS execution lock with fresh per-attempt ownership fencing and a killable supervised handler boundary; retain exclusivity until descendants stop, including parent-crash recovery.
4. Introduce the single `media/subprocess.run` execution wrapper with argv/data-cwd/environment validation, bounded drains, process-group timeout/cancellation/reaping and a managed macOS caffeinate adapter; no new dependency.
5. Keep an internal trusted kind→handler registry and an idle worker lifecycle seam. Future tasks register actual pipeline stages; no live content/script/render work is enqueued or faked now.
6. Wire opt-out/test-injectable worker ownership into existing API lifespan without replacing scheduler or blocking requests; stop/reap before engine disposal and document independent worker controls.
7. Add authenticated bounded metadata-only GET/v1/jobs with filters/stable paging, then regenerate OpenAPI/TS; no mobile UI, HTTP enqueue or arbitrary command endpoint.
8. Test independent-thread/process races, global seriality, stale owner rejection, parent crash, retry exhaustion, real sleeping-child/descendant termination, output overflow, shutdown and migration preservation.
9. Run full checks/security in implementation/review, update exact contracts/recovery limitations and provide isolated backend evidence; do not touch owner data or claim downstream M3/M4 work complete.

## 10. Open questions

1. **Safe serial execution and stale recovery:** May T3.1 strengthen the documented per-row claim/timeout sketch with a host-wide OS execution lock under `data/`, fresh per-attempt ownership tokens in the existing lock fields, and killable supervised handler execution? **Recommendation:** yes. Require the lock to cover the true child/process-group lifetime, and reclaim/retry only after the old execution cannot overlap; if cleanup/ownership is uncertain, fail closed. The API and orchestrator remain one service, with no new dependency or additional database table beyond the five planned tables. This prevents two different heavy jobs from running together and prevents a timed-out but still-live job from overlapping its retry. It does **not** promise exactly-once external side effects; future stage handlers must remain idempotent. Tests must prove cross-worker different-job seriality, stale completion rejection, worker-crash recovery and actual sleeper/descendant termination rather than treating a cancelled thread/future as killed.
