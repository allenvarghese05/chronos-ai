# T1.2 Brief: Pairing and device auth

## Task

**ID:** T1.2
**Title:** Pairing and device auth: `chronos pair-code` (prints code + QR), `POST /v1/pair`, bearer dependency, `GET/PATCH/DELETE /v1/device/me`, `chronos device revoke`, rate limiting, problem+json error model
**Size:** M (≈ 1 day)
**Depends:** T1.1 (devices + pairing_codes tables migrated; enums defined)

**Acceptance criteria** (from the plan):
1. Wrong code ×5 burns it (test).
2. Token works, revoked token → 403.
3. Tokens stored hashed.
4. 60 req/min limit test.

---

## Why it matters

T1.2 is the gateway to all authenticated endpoints (T1.6 telemetry, T2.2 mobile, T5.1+ reels). Without pairing, the phone cannot send signals. Without rate limiting and token hashing, the system is vulnerable to brute-force attacks and token theft. The acceptance criteria are security and functional requirements: five wrong attempts burn a pairing code (denies attackers 2⁴⁰ ≈ 1 trillion codes but caps damage per code), revoked tokens must 403 *immediately* (a revoked device must not access anything), and tokens must be hashed at rest (so a stolen DB does not leak login credentials). The 60 req/min rate limit (docs/05-api-contracts.md §0) prevents automated attacks on the pairing endpoint (5/min per IP) and other endpoints (120/min). Every piece is testable: wrong-code exhaustion, immediate revocation, rate-limit headers and backoff, hashed token verification.

| ID | Binding constraint |
|---|---|
| D16 | **Network**: phone ↔ laptop over home LAN. API binds to LAN interface (never `0.0.0.0`), HTTPS with mkcert CA; device bearer token on every call. ## Constraints

### Security constraints (docs/09-security.md §2)

**Transport and auth:**
- API binds to the LAN interface only (not `0.0.0.0`); hostname is `chronos.local` or the LAN IP; TLS with mkcert root CA installed on phone.
- Bearer tokens: 32 random bytes, base64url-encoded (43 chars); stored as SHA-256; no plaintext in DB.
- Constant-time token compare: `hmac.compare_digest()` for every bearer check.
- Pairing code: 8 characters (40 bits), one-time, 10-min expiry, 5 attempts before burn, 5/min per IP rate limit.

**Input validation:**
- `Pydantic extra="forbid"` on all request models.
- Timezone must be in `zoneinfo.available_timezones()`.
- Code format: 8 alphanumeric (no 0/O/1/I to avoid ambiguity) with optional single dash (e.g., `7K2M-9QXD`).
- Device name, model, versions: length-limited, no special chars (or sanitised).

**Rate limiting:**
- Keyed by client IP only (no `X-Forwarded-For` trust; LAN direct).
- Per-IP, in-process memory (fine per D10).
- Pairing: 5/min.
- Telemetry: 30/min.
- Other: 120/min.
- Response includes `Retry-After: <seconds>` on 429.

**Secret handling:**
- Token hashing happens at generation (T1.2) and comparison (every request).
- SHA-256 digest stored, never plaintext.
- Pairing code hash from normalised form (uppercase, dash removed).

### Functional constraints

**Pairing:**
- One active device at a time (D16). Pairing while an active device exists → 409 `conflict`.
- Re-pairing revokes the old device automatically (or require explicit `chronos device revoke` first; likely the latter per the task description).
- Tokens valid indefinitely until revoked or re-pairing burns them.
- Every endpoint except `POST /v1/pair` requires a valid, active (non-revoked) bearer token.

**Device state:**
- `last_seen_at` updated on every successful authenticated request (not a separate query; happens in the dependency).
- `status` is either `active` or `revoked`; once revoked, no requests are accepted.
- `revoked_at` is set when the token is revoked (via DELETE or re-pairing).

**Code lifecycle:**
- Generated with `expires_at = now + 10 min`.
- Shown **once** to the user (terminal and/or QR).
- On first POST `/v1/pair` with the code: increment `attempts`, check expiry, check code hash.
- If wrong code: increment `attempts`; if ≥ 5, set `consumed_at` to mark it burned.
- If correct code: consume it (`consumed_at = now`), return a new token and device row.
- Expired code (past `expires_at`) → 410.
- Consumed code (not `null`) → 400 `pairing_invalid`.
- Burned code (attempts ≥ 5) → 400 even with the right code.

**Token format:**
- `secrets.token_urlsafe(32)` → 43 characters (base64url of 32 bytes = 256 bits).
- Stored as SHA-256 hex digest (64 chars) in `devices.token_hash`.
- Returned once in pairing response (only time plaintext is sent).
- Never logged.

### iOS/mobile constraints

- Phone sends `tz` and must accept it from `api_base` response to handle timezone changes.
- Bearer token stored in `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`.
- On 403 revoked: app returns to pairing screen.
- On 401 (invalid token): fall back to re-pairing.

### Timing constraints

- Pairing code valid for 10 minutes (D16).
- Token expiry: indefinite (until revoked).
- Rate limit window: 1 min sliding (5/min = 1 request every 12 sec for pairing).
- `last_seen_at` update should be fast (in-memory increment or one-shot update, not a separate query).

## Edge cases

### 1. Pairing code format and normalisation

**Case:** User enters code with mixed case or dash: `7k2m-9qxd` vs `7K2M9QXD`.

**Expected:** Normalise to uppercase, remove dash, hash. Lookup by hash so entry is case-insensitive and dash-agnostic.

**Test:** Create code, POST with three formats (`7K2M-9QXD`, `7k2m-9qxd`, `7K2M9QXD`) → all succeed.

### 2. Code exhaustion (5 attempts)

**Case:** User mistyped the code 5 times; the 6th attempt with the correct code.

**Expected:** After 5 wrong attempts, the code is marked burned (`attempts = 5` and implicit `consumed_at` is set or a separate flag). The 6th attempt, even with the correct code, fails with 400 `pairing_invalid`.

**Test:**
- Create code.
- POST with wrong code ×4 → each increments `attempts`.
- POST with wrong code ×1 (5th) → still fails; `attempts = 5`.
- POST with correct code → 400 `pairing_invalid` (burned).

### 3. Code expiry (10 minutes)

**Case:** Code generated at 06:00. Now is 06:11.

**Expected:** 410 `pairing_expired`, detail includes server time so user can sync clock.

**Test:** Freeze clock, create code, advance 11 min, POST → 410.

### 4. Code already consumed (one-time)

**Case:** User pairs, gets token. Later, tries to re-use the same code for a second device.

**Expected:** 400 `pairing_invalid` (code already consumed).

**Test:** Create code, POST → success, `consumed_at` set. POST again with same code → 400.

### 5. Active device conflict

**Case:** One device is already active. User tries to pair a new phone.

**Expected:** 409 `conflict`. Detail: "An active device already exists; run `chronos device revoke` first."

**Test:** Pair device A. Pair device B → 409. Device A still active, token still works.

### 6. Re-pairing (revoke old device)

**Case:** User pairs device A, later pairs device B (after revoking A).

**Expected:** Device A's token no longer works (revoked); device B works.

**Test:** Pair A, get token_a. Revoke via CLI or API. Pair B, get token_b. POST with token_a → 403. POST with token_b → 200.

### 7. Token revocation and immediate 403

**Case:** Device A is active. Call `DELETE /v1/device/me` or `chronos device revoke`.

**Expected:** Token is immediately revoked. Any subsequent request with that token → 403 `revoked` (not 401 `unauthorized`).

**Test:**
- Pair device A, get token.
- POST /v1/telemetry with token → 200.
- DELETE /v1/device/me with token → 204.
- POST /v1/telemetry with same token → 403 `revoked`.

### 8. Invalid token format

**Case:** Bearer header has malformed/truncated token.

**Expected:** 401 `unauthorized`. (Not 403; the token is not valid, not revoked.)

**Test:** POST with `Authorization: Bearer invalidtoken123` → 401.

### 9. Missing Bearer header

**Case:** Request to `POST /v1/telemetry` without `Authorization` header.

**Expected:** 401 `unauthorized`.

**Test:** POST without header → 401.

### 10. Rate limiting: pairing (5/min per IP)

**Case:** Send 6 pairing requests from the same IP within 60 seconds.

**Expected:** Requests 1–5 → 429 (or pass, depending on backoff logic); request 6 → 429 with `Retry-After` header.

**Test:** Use a fake IP context manager; make 6 requests; assert 5 pass and 6th is 429 (or all fail after threshold depending on implementation).

### 11. Rate limiting: other endpoints (120/min per IP)

**Case:** Authenticated requests (e.g., GET /v1/device/me) exceed 120/min.

**Expected:** 429 `rate_limited`.

**Test:** Pair, then make 121 requests in sequence with a mocked clock advancing 1 second per request → 121st is 429.

### 12. Unknown token (not in DB)

**Case:** Bearer token is valid base64url and the right length (43 chars) but the SHA-256 hash is not in the DB.

**Expected:** 401 `unauthorized`.

**Test:** Generate a random token, POST /v1/telemetry → 401 (or 403 if the check is always treat-as-revoked; likely 401).

### 13. Device revocation via CLI vs API

**Case:** `chronos device revoke` on the laptop.

**Expected:** The single active device is revoked; `status = revoked`, `revoked_at` set.

**Test:** Pair, run CLI, query DB → device.status = 'revoked'.

### 14. PATCH /v1/device/me with `extra="forbid"`

**Case:** Client sends `{ "expo_push_token": "...", "unknown_field": "value" }`.

**Expected:** 422 `validation`, detail lists unknown field.

**Test:** PATCH with extra field → 422.

### 15. Timezone validation

**Case:** User sends `tz: "Invalid/Zone"` in pairing request.

**Expected:** 422 `validation`.

**Test:** POST /v1/pair with invalid tz → 422.

### 16. `last_seen_at` updates

**Case:** Pair device, GET /v1/device/me twice with a 1-second delay.

**Expected:** `last_seen_at` increases (or at least the timestamp of the second GET is ≥ first).

**Test:** Pair, GET (note `last_seen_at` as `t1`), wait 1 sec, GET again (note `t2`), assert `t2 >= t1`.

## Proposed approach

1. **Auth module** (`chronos/auth.py`):
   - `generate_pairing_code() -> str`: 8-char alphanumeric (no 0/O/1/I); return plaintext.
   - `hash_pairing_code(code: str) -> str`: normalize (uppercase, dash removed), SHA-256 hex.
   - `generate_device_token() -> str`: `secrets.token_urlsafe(32)`.
   - `hash_device_token(token: str) -> str`: SHA-256 hex.
   - `verify_device_token(plaintext: str, stored_hash: str) -> bool`: `hmac.compare_digest`.
   - `get_device_by_token(token: str, session) -> Device | None`: lookup by hash, return if active.
   - `require_device` dependency: extracts Bearer header, looks up token, returns Device or raises 401/403.

2. **Rate limiter module** (`chronos/ratelimit.py` or external `slowapi`):
   - Token-bucket per IP; 5 min for pairing, 30 min for telemetry, 120 min for others.
   - `check_rate_limit(ip: str, kind: str) -> tuple[bool, int | None]`: (allowed, retry_after_sec).
   - Integrate via FastAPI middleware or per-endpoint decorator.

3. **API routers** (`chronos/api/pair.py`, `chronos/api/devices.py`):
   - `POST /v1/pair`: request DTO with code + device info, response DTO with token + api_base.
   - `GET /v1/device/me`: return Device (redacted, no token).
   - `PATCH /v1/device/me`: update expo_push_token, tz, etc.
   - `DELETE /v1/device/me`: revoke, return 204.
   - All except pairing require `require_device` dependency.

4. **CLI commands** (`chronos/cli.py` extension):
   - `pair_code` command: generate code, insert into DB, print plaintext + QR (or ASCII art).
   - `device_revoke` command: revoke the single active device.

5. **Error codes** (`chronos/errors.py`):
   - Add `pairing_invalid`, `pairing_expired`, `conflict` to code map if needed.
   - `conflict` maps to 409; `pairing_invalid` to 400; `pairing_expired` to 410.

6. **Tests** (`tests/test_pairing.py`, `tests/test_devices.py`):
   - Fixture: active device with known token.
   - Fixture: frozen clock for expiry tests.
   - Test code exhaustion, expiry, consumption, token revocation, rate limiting.

7. **Config** (`chronos/config.py`):
   - Optional: `api_base_url` (or compute from `api_bind_host` + port if always local).

## Risks

### 1. Token hashing done at wrong time

**Risk:** Token hashed on retrieval from DB instead of at generation → plaintext token leaks in logs or error messages.

**Mitigation:** Hash in `generate_device_token`, log only hash. Test verifies plaintext never appears in logs (canary token).

### 2. Rate limiter state lost on restart

**Risk:** In-memory rate limiter is cleared when the process restarts → attacker can burst again.

**Mitigation:** Acceptable per D10 (single laptop, low traffic). Accept the trade-off. Document in ADR.

### 3. Bearer token extracted but not hashed before lookup

**Risk:** Token lookup bypasses hashing → timing attack or plaintext leak.

**Mitigation:** Always hash the incoming Bearer token before looking it up. Test: POST with correct token should succeed; one character changed should 401 (not 403).

### 4. `last_seen_at` updated synchronously, causing bottleneck

**Risk:** Every request updates the timestamp; under high load, DB contention.

**Mitigation:** Accept synchronous update for now (single user, ~1 request per 5 min). Async update is T6.1+ tuning.

### 5. Pairing code normalization inconsistency

**Risk:** Code stored with dashes, lookup without dashes (or vice versa) → valid codes rejected.

**Mitigation:** Define a single normalisation function (`hash_pairing_code`); use it for both insert and lookup. Test all three formats.

### 6. QR library adds unexpected dependencies

**Risk:** `qrcode` library pulls in PIL or other bulky deps → build complexity.

**Mitigation:** Use `qrcode` with `print_ascii=True` (built-in); skip PIL. Verify import works. If bloat, defer to T0.6 with the note.

### 7. Rate limiter per-IP relies on honest client IP

**Risk:** Attacker behind proxy sends forged `X-Forwarded-For` → bypass rate limit.

**Mitigation:** Ignore `X-Forwarded-For` (D16 says LAN direct, no proxy). Get IP from `request.client.host` only. Test with a fake request context.

## Summary

T1.2 implements device pairing and bearer-token authentication for the Chronos API. The core is a secure pairing flow (8-char code, 10-min expiry, 5-attempt burn) that issues a 256-bit token hashed with SHA-256. Every authenticated endpoint uses a `require_device` dependency to extract and verify the token. One active device per phone at a time (enforced via 409 conflict). Rate limiting (in-memory token bucket, 5/min for pairing, 120/min for others) protects against brute force. CLI commands print the pairing code (with QR art if a library is available) and allow revocation. All errors are RFC 9457 problem+json. Tests verify code exhaustion, immediate revocation, token hashing, and rate limits. No new migrations needed; T1.1 tables are already in place.

## Owner answers (2026-10-13)

Approved with the orchestrator's recommendations:

1. QR: `segno` (pure Python, terminal output), pinned to the exact latest release.
2. Token: `secrets.token_urlsafe(32)`; stored as SHA-256 hex; `hmac.compare_digest`.
3. Rate limiter: hand-rolled `chronos/ratelimit.py` token bucket, per client IP, injectable clock,
   no dependency. Limits per docs/05 §0: pairing 5/min, telemetry 30/min (wired in T1.6), default
   120/min. The plan row's "60 req/min" wording is stale — the implementer corrects it to the
   documented limits and tests pairing (5/min) and default (120/min).
4. CA fingerprint in the pair response: deferred to T0.6; no field now.
5. `api_base`: `CHRONOS_PUBLIC_BASE_URL` setting (e.g. `https://chronos.local:8443/v1`), default
   derived from bind host/port; never `0.0.0.0`.
6. One active device: `POST /v1/pair` → 409 `conflict` while an active device exists;
   `chronos device revoke` revokes it; no auto-revoke.
7. `require_device` in `chronos/auth.py` returns the `Device` row, 401 `unauthorized` for unknown
   tokens, 403 `revoked`; updates `last_seen_at` synchronously at most once per 60 s per device.
8. Problem+json codes added: `unauthorized`, `revoked`, `pairing_invalid`, `pairing_expired`,
   `rate_limited` (429 with `Retry-After`), `conflict`.
9. Pairing code: 8 chars from an alphabet without 0/O/1/I, displayed as `XXXX-XXXX`; input
   normalised (uppercase, dashes/spaces stripped) before hashing and comparing.
