# T1.6 Plan: Telemetry endpoint + day state machine

## 1. Summary

When done, `POST /v1/telemetry` validates clock skew, stores a `TelemetryEvent` +
`WakeEvaluation`, advances the day's state machine (idle → monitoring → confirmed) and returns
the full scoring breakdown. `GET /v1/day/today` and `GET /v1/day/{local_date}` expose the day
row with score timeline; `PUT /v1/day/{local_date}/actual-wake` annotates ground truth.
All state changes are audited in `day_transitions`. One DB transaction per POST; rollback on
any failure.

## 2. Design

**Three new modules** mirror the brief's proposed approach:

* `wake/state.py` — pure state-machine logic (only DB I/O: SELECT/INSERT/UPDATE on days and
  day_transitions). Keeps scoring logic separate.
* `wake/service.py` — orchestrates the full POST lifecycle: clock skew → idempotency →
  local_date → day get-or-create → previous lookup → evaluate → insert TelemetryEvent +
  WakeEvaluation → increment ticks_received → apply state machine.
* `api/telemetry.py` and `api/day.py` — thin HTTP layers: parse raw body, extract token, rate-limit,
  call service, format response.

**Lazy idle → monitoring transition**: when an in-window event arrives and the day is still
`idle`, `state.py` transitions it to `monitoring` first (cause = `scheduler_window_start`) and
then applies the evaluation. This gives T1.7's scheduler a natural hook without blocking T1.6.

**Alternatives rejected**:
- Combining service + state into one file — too large, harder to test the state machine in isolation.
- Separate transactions for event and evaluation — risks timeline corruption on failure.
- State machine in the HTTP layer — couples routing to domain logic.

### Step 1 — `wake/state.py`: DayStateMachine

**Files touched**: `services/api/src/chronos/wake/state.py`, `services/api/tests/wake/test_state.py`

**Full public interface**:

```python
"""Day state machine for Chronos-AI (T1.6).

Manages Day row lifecycle: creation (get_or_create_day), lazy idle→monitoring
transition when an in-window event arrives, and monitoring→confirmed on a
confirm evaluation decision.  All transitions are audited to day_transitions.

Public API
----------
- :func:`get_or_create_day`  — get or create a Day row for (device, local_date).
- :func:`apply`              — apply an Evaluation to a Day; may transition state.
- :func:`on_confirmed`       — no-op hook called after monitoring→confirmed (T1.7/T5.2).
"""

def get_or_create_day(
    session: Session,
    device: Device,
    local_date: datetime.date,
    tz: str,
    rules: WakeRules,
    now: datetime.datetime,
) -> Day:
    """Get or create the Day row for (device, local_date).

    If no row exists, creates one with:
    - tz: frozen to `tz` argument (the signal's tz, never the device row's tz).
    - kind: derived via day_kind(local_date, window_config).
    - window_start_utc, window_end_utc: computed via window_for().
    - state: idle.
    - ticks_sent/received: 0.
    - created_at, updated_at: now.

    The day's tz and window bounds are frozen at creation; a tz change
    mid-day (owner travels) does not update an existing row.

    Args:
        session:     Open SQLModel Session (caller commits).
        device:      Authenticated device row.
        local_date:  Local calendar date (derived by the caller via local_date_for).
        tz:          IANA timezone string from the Signals payload.
        rules:       Active WakeRules (provides window config and day_kind).
        now:         UTC now (injected by caller; frozen in tests).

    Returns:
        The existing or newly-created Day row (flushed, not committed).
    """

def apply(
    session: Session,
    day: Day,
    evaluation: "Evaluation",
    now: datetime.datetime,
    *,
    evaluation_id: int,
) -> list[DayTransition]:
    """Apply an Evaluation to a Day; insert DayTransition rows as needed.

    Transition rules (in order, short-circuit after first change):
    1. If day.state is idle AND evaluation.gate is open:
       - transition idle → monitoring (cause=scheduler_window_start,
         caused_by_evaluation_id=None); then fall through to rule 2.
    2. If day.state is monitoring AND evaluation.decision is confirm:
       - transition monitoring → confirmed (cause=evaluation,
         caused_by_evaluation_id=evaluation_id).
       - Set day.confirmed_at = now.isoformat() and day.confirm_evaluation_id = evaluation_id.
       - Call on_confirmed(session, day).
    3. If day.state is confirmed, fallback, or delivered: no transition.

    For each transition:
    - INSERT a DayTransition row.
    - UPDATE day.state.
    - UPDATE day.updated_at = now.isoformat().

    Both the Day update and DayTransition insert happen in the same
    session as the caller's TelemetryEvent + WakeEvaluation inserts;
    the caller commits the whole transaction.

    Args:
        session:       Open SQLModel Session.
        day:           The Day row (already in session).
        evaluation:    The scored Evaluation from evaluate().
        now:           UTC now (injected; frozen in tests).
        evaluation_id: PK of the WakeEvaluation row just inserted.

    Returns:
        List of DayTransition rows inserted (0, 1, or 2).
    """

def on_confirmed(session: Session, day: Day) -> None:
    """No-op hook called after a day transitions to confirmed.

    T1.7 replaces this with the delivery trigger; T5.2 wires the render job.
    """
```

**Key invariants to test**:
- idle + closed-gate → no transition, no audit row.
- idle + open-gate → monitoring (1 audit row), even if decision != confirm.
- monitoring + high → no transition (1 audit row from idle→monitoring if applicable).
- monitoring + confirm → confirmed (1 new audit row; day.confirmed_at set; day.confirm_evaluation_id set).
- idle + confirm → 2 audit rows: idle→monitoring then monitoring→confirmed.
- confirmed + confirm → no new transition, no new audit row.
- fallback + confirm → no new transition, no new audit row.
- delivered + confirm → no new transition.
- After apply, day.state and day.updated_at are mutated in the session.
- Multiple apply calls in sequence produce the right cumulative transitions.

### Step 2 — `wake/service.py`: ingest_telemetry

**Files touched**: `services/api/src/chronos/wake/service.py`, `services/api/tests/wake/test_service.py`

**Full public interface**:

```python
"""Telemetry ingestion service for Chronos-AI (T1.6).

Orchestrates the full POST /v1/telemetry lifecycle as a single DB transaction:
clock-skew check → idempotency check → local_date → day get-or-create →
previous tick lookup → evaluate → insert TelemetryEvent + WakeEvaluation →
ticks_received increment → state machine apply.

Public API
----------
- :class:`TelemetryResult`   — typed result returned by ingest_telemetry.
- :func:`ingest_telemetry`   — single entry point; called by the HTTP layer.
"""

from __future__ import annotations

import datetime
import json
from dataclasses import dataclass

import structlog
from sqlmodel import Session, select

from chronos.enums import DayState, EvaluationDecision, EvaluationGate
from chronos.errors import ProblemException
from chronos.models import Day, TelemetryEvent, WakeEvaluation
from chronos.models.devices import Device
from chronos.time import parse_utc_iso, utc_now_iso
from chronos.wake.rules import WakeRules, RuleVersion
from chronos.wake.scoring import EvalContext, Evaluation, PreviousTick, evaluate
from chronos.wake.signals import Signals
from chronos.wake.state import apply, get_or_create_day
from chronos.wake.window import local_date_for, window_for
from zoneinfo import ZoneInfo

log = structlog.get_logger(__name__)

#: Maximum allowed absolute delta between device_ts and server now (seconds).
CLOCK_SKEW_MAX_SEC: int = 300

#: Maximum raw body size stored in raw_json (bytes). Bodies are capped by the HTTP layer.
RAW_BODY_MAX_BYTES: int = 65_536  # 64 KiB


@dataclass
class TelemetryResult:
    """Typed result of :func:`ingest_telemetry`."""

    evaluation_id: int
    """PK of the WakeEvaluation row (new or pre-existing on duplicate)."""

    local_date: datetime.date
    """Local calendar date this evaluation belongs to."""

    evaluation: Evaluation
    """Complete scoring result."""

    day_state: DayState
    """Day state after any transitions."""

    rule_version_id: int
    """PK of the RuleVersion used."""

    rule_version_number: int
    """Human-readable rule version number echoed in the response."""

    is_duplicate: bool = False
    """True when the same (device_id, seq) was already stored."""


def ingest_telemetry(
    session: Session,
    device: Device,
    signals: Signals,
    raw_body: bytes,
    now: datetime.datetime,
    rules: WakeRules,
    rule_version: RuleVersion,
) -> TelemetryResult:
    """Validate, score and persist one telemetry snapshot.

    Steps (all inside one transaction; caller must NOT commit — this function commits):
    1. Clock skew: |device_ts_utc - now| > CLOCK_SKEW_MAX_SEC → ProblemException 422.
    2. Idempotency: SELECT telemetry_events WHERE device_id=? AND seq=?.
       If found → reconstruct Evaluation from stored WakeEvaluation.breakdown_json
       and return early (200, is_duplicate=True).  Log warning if raw_json differs.
    3. local_date_for(device_ts, tz, boundary).
    4. get_or_create_day(session, device, local_date, tz, rules, now).
    5. Previous tick: latest WakeEvaluation WHERE device_id=device.id AND local_date=?
       ORDER BY device_ts DESC LIMIT 1 → build PreviousTick | None.
    6. EvalContext(window, day_state, rule_version, previous, ticks_received_today).
    7. evaluate(signals, rules, now, ctx) → Evaluation.
    8. INSERT TelemetryEvent (raw_json=raw_body[:RAW_BODY_MAX_BYTES], tick_seq=signals.tick_seq).
    9. INSERT WakeEvaluation (breakdown_json=json.dumps(evaluation.model_dump(mode="json"))).
    10. day.ticks_received += 1; day.updated_at = now.
    11. apply(session, day, evaluation, now, evaluation_id=wake_eval.id).
    12. session.commit().
    13. Return TelemetryResult.

    Args:
        session:      Open Session; this function commits it.
        device:       Authenticated Device row.
        signals:      Validated Signals payload.
        raw_body:     Exact request bytes (capped at RAW_BODY_MAX_BYTES).
        now:          UTC now (injected; frozen in tests).
        rules:        Active WakeRules.
        rule_version: Active RuleVersion (for FK and version number).

    Returns:
        :class:`TelemetryResult` with full scoring detail.

    Raises:
        ProblemException 422 clock_skew: if |device_ts - now| > 300 s.
        Exception:       Any unexpected DB error (caller's TestClient or uvicorn catches).
    """
```

**Edge cases to test** (from the brief):
- clock skew exactly 300 s → 200 OK, no exception.
- clock skew 301 s (future) → ProblemException 422, code=clock_skew, detail contains server_time.
- clock skew 301 s (past) → ProblemException 422.
- No rows written on clock_skew rejection (monkeypatch DB flush → assert no events).
- Duplicate seq, identical payload → TelemetryResult returned, is_duplicate=True, no new rows.
- Duplicate seq, different payload → first evaluation returned, is_duplicate=True, warning logged.
- Out-of-window event → day state=idle, decision=outside_window.
- Tz change mid-day → existing day's tz unchanged.
- Late past-date event → stored under past local_date, previous from that date.
- Rollback test: monkeypatch raises after WakeEvaluation INSERT → no TelemetryEvent row either.

```python
"""POST /v1/telemetry — receive, validate, score and store one sensor snapshot.

Endpoint contract (docs/05-api-contracts.md §2):
- Requires device bearer token (require_device).
- Rate limit: 30 req/min per IP (rate_limit("telemetry", 30)).
- Body: application/json, Signals schema (extra=forbid).
- Raw body capped at 64 KiB (reads request.body(), checks len).
- 422 clock_skew if |device_ts - server_now| > 300 s (with server_time in detail).
- Idempotent on (device_id, seq): returns stored evaluation with 200.
- Response: TelemetryResponse (see below).
- next_tick_in_sec: always null (T1.7 scheduler fills this).
"""

router = APIRouter(prefix="/telemetry", tags=["telemetry"])

class TelemetryResponse(BaseModel):
    """Response body for POST /v1/telemetry."""
    model_config = ConfigDict(extra="forbid")

    evaluation_id: int
    local_date: str          # ISO-8601 date "YYYY-MM-DD"
    gate: EvaluationGate
    score: int
    decision: EvaluationDecision
    confirm_reason: str | None   # "strong" | "consecutive" | "both" | null
    threshold: ThresholdsEcho
    consecutive_high: int
    rule_version: int            # WakeRules version number
    breakdown: list[dict[str, Any]]
    penalties: list[dict[str, Any]]
    day_state: DayState
    next_tick_in_sec: int | None  # always null for T1.6

@router.post("", status_code=200)
async def post_telemetry(
    request: Request,
    device: Device = Depends(require_device),
    _rl: None = Depends(rate_limit("telemetry", per_minute=30)),
    session: Session = Depends(get_session_dep),
) -> TelemetryResponse:
    ...
```

**Implementation notes**:
- Read raw body via `await request.body()`, check `len(raw) > 64*1024` → ProblemException 422.
- Parse `Signals.model_validate_json(raw)` (catches extra fields due to `extra="forbid"`).
- Load rules via `get_rules_cache().get_effective(session)`.
- Call `ingest_telemetry(...)`.
- Map TelemetryResult → TelemetryResponse.
- `breakdown` = `evaluation.breakdown` serialised as list[dict]; `penalties` same.
- `threshold` = `evaluation.thresholds`.

## 10. Review-finding fixes (post-review)

**BLOCKING 1** — `clock_skew` 422 carries `server_time` as a structured RFC 9457 extension member
in the problem+json body (not embedded in `detail` text). Extended `ProblemException` and
`make_problem` with optional `extensions: dict[str, object] | None`; `http_exception_handler`
passes extensions through. Tests assert `body["server_time"]` is an ISO string within 2 s of
the frozen clock and `detail` still contains "seconds".

**BLOCKING 2** — Rollback test now injects failure via `patch("chronos.wake.service.apply",
side_effect=...)`, i.e. AFTER both TelemetryEvent and WakeEvaluation are flushed but BEFORE
commit. Assertions: no TE row for that seq, no extra WE rows, no extra DayTransition rows,
day.ticks_received unchanged from first committed tick.

**BLOCKING 3** — Idempotency equality: `test_telemetry.py` asserts `r1.json() == r2.json()`
(same frozen clock); `test_service.py` asserts `r2.evaluation == r1.evaluation` and
`r2.rule_version_number == r1.rule_version_number`.

**MINOR 4** — Duplicate path now fetches the stored `RuleVersion` by `dup_we.rule_version_id`
and returns its `version` number. New test changes active rule between calls; duplicate still
reports the original version.

**MINOR 5** — `telemetry.py` catches `pydantic.ValidationError` (not bare `Exception`) around
`Signals.model_validate_json`; structured `errors` list added as extension member. New test:
unknown field → 422 `validation` (not `clock_skew`).

**MINOR 6** — `_fmt_utc` removed from `service.py` and `state.py`; replaced by `format_utc_iso`
in `chronos/time.py`. Tests for aware, non-UTC, naive, and microsecond inputs added to
`test_time.py`.
