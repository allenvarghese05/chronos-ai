# T2.3 Brief: Telemetry sampler and durable outbox

## 1. Task

**ID:** T2.3

**Title (verbatim):** Telemetry sampler + outbox: `sampleAndSend`, `buildTelemetry`, SQLite outbox, timeouts, seq counter, 401 handling

**Size:** M

**Depends:** T2.1, T2.2

**Acceptance criteria (verbatim):** Jest: payload matches the OpenAPI schema; outbox retries in order and drops > 2 h old; manual: airplane mode → events queued → delivered later with same seqs

**Milestone M2 — Mobile telemetry client, done when (verbatim):** on the owner's iPhone, silent pushes wake the app in the background, real CoreMotion history is posted, and the debug screen shows the server's breakdown.

Branch: `t2-3-telemetry-outbox`, based on `origin/main` `c762861` after PR #35 merged. T2.1 and T2.2 are prerequisites already present on this base. M2's whole-milestone acceptance is not a claim that T2.3 implements T2.4 background handlers or T2.5's debug screen.

## 2. Why it matters

T2.1 can read native signals and T2.2 can securely authenticate, but the app does not yet construct or send telemetry. T2.3 connects those layers and gives later wake handlers one bounded operation. It must preserve an event's sequence and original sampling time across network failure, app restart, and lost responses. A new sequence on retry double-counts one wake; reusing a sequence for a different snapshot silently returns the first evaluation. Queuing under one paired identity and sending under another leaks data and corrupts scoring.

Durability and replay semantics are needed before T2.4 can call the sampler from silent push/BG refresh and before T2.5 can display queue size, last response, or missed ticks. The current phone cannot be connected by cable and is not available for installed-device testing; Simulator testing must be explicit about its limits.

## 4. Current state

### Native sensor surface

`apps/mobile/modules/chronos-sensors/src/index.ts` exports `ChronosSensorsModuleType`:

```ts
pedometerAuthorization(): Promise<'authorized' | 'denied' | 'restricted' | 'not_determined'>;
requestMotionPermission(): Promise<void>;
querySteps(fromMs: number, toMs: number): Promise<{ steps: number; distanceM: number }>;
queryActivity(fromMs: number, toMs: number): Promise<ActivitySummary>;
deviceState(): DeviceState;
```

`ActivitySummary` has `walkingSec`, `runningSec`, `stationarySec`, `automotiveSec`, `cyclingSec`, `unknownSec`, and `walkingConf: 'low' | 'medium' | 'high'`. `DeviceState` has `isUnlocked`, `batteryState`, `batteryLevel: number | null`, `appState`, `lowPowerMode`, and `iosVersion`. It does **not** return timezone; T2.2's `deviceMetadata()` reads `Intl.DateTimeFormat().resolvedOptions().timeZone`.

The Swift wrapper already converts millisecond instants to `Date`, reads UIKit on main, and rejects unavailable step counting with code `pedometer_unavailable`. Simulator cannot supply real steps. The bridge's Jest/Expo-Go fallback returns synthetic zero/default values (`iosVersion: '0.0'`); that must not be mistaken for successful native sampling. Sampling must not request permission implicitly on every wake. The pure Swift core and native wrapper are existing functionality, not a proposed new wake engine.

### Paired session and transport

`apps/mobile/src/pairing/validation.ts` defines:

```ts
export type Session = { version: 1; apiBase: string; deviceId: string; token: string };
```

`createSessionStore(deps: SessionDeps)` in `src/session/store.ts` returns `store`, `hydrate`, `retryHydration`, `pair`, `validate`, `forget`, `revoke`, and `registerPush`. State phases are `hydrating | unpaired | authenticated | storage-error`. Its generation, serialized storage queue, and authenticated-operation helper are currently private. Confirmed 401 **or** 403 invalidates once; transient network/TLS failures preserve pairing. T2.3 needs a deliberate session-bound request/invalidation seam rather than another unrelated token cache or direct Keychain reader.

`createApi(apiBase: string, transport: Transport, token?: string)` in `src/api/client.ts` uses generated `openapi-fetch<paths>`. Its current destination allowlist contains only `/v1/pair` and `/v1/device/me`; only `/v1/device/me` receives a bearer. It has no telemetry/config/day method. `Transport` receives explicit `{ redirect: 'error'; credentials: 'omit'; signal: AbortSignal }`. `src/session/native.ts` passes those options directly to SDK 57 `expo/fetch`.

Requests currently have a 10-second internal timeout; successful responses are streamed under a 32 KiB cap. `ApiError(status, message, retryAfterSec = 0)` exposes status and bounded Retry-After only. Error bodies are not read, so it cannot yet distinguish `422 clock_skew` from `422 validation` or expose validated `server_time`. Queue requests need a shorter externally cancellable remaining deadline while preserving all origin, TLS, redirect, body and sanitization controls.

The current home (`app/index.tsx`) mounts sensor reads only inside `ProtectedScene`, displays device state and a last-10-minute step query, and offers session/push controls. There are no telemetry buttons, outbox, sampler, sequence store, or last evaluation state. `SessionProvider` currently hydrates and validates the session on AppState active; it does not sample or flush telemetry.

### Exact backend contracts and implementation gaps

`services/api/src/chronos/wake/signals.py:Signals` is `ConfigDict(extra='forbid')`. It has 17 properties, of which `battery_level` defaults to null; the other 16 are required:

| Field | Actual model constraint |
|---|---|
| `device_ts` | Pydantic datetime, must be timezone-aware |
| `tz` | string; design requires a real IANA timezone; ingestion constructs `ZoneInfo(signals.tz)` |
| `wake_source` | `silent_push`, `bg_refresh`, `foreground`, `manual` |
| `steps_10m`, `steps_since_window` | integer 0–5000 |
| `walking_sec_10m`, `stationary_sec_10m` | integer 0–600 |
| `walking_conf` | `low`, `medium`, `high` |
| `is_unlocked` | boolean |
| `battery_state` | `unplugged`, `charging`, `full`, `unknown` |
| `battery_level` | number 0–1 or null; optional in actual schema |
| `app_state` | `active`, `background`, `inactive` |
| `low_power_mode` | boolean |
| `pedometer_auth` | `authorized`, `denied`, `restricted`, `not_determined` |
| `seq` | integer >= 0 |
| `app_version`, `ios_version` | strings |

`walking_sec_10m` is described as walking/running duration in docs/03; the native result provides those separately. `distanceM`, cycling/running/automotive/unknown duration keys, charger transitions, and window metadata are not telemetry fields.

**Gap A — missing published request schema:** `api/telemetry.py:post_telemetry(request, device, _rl, session)` reads raw bytes, enforces 65,536 bytes, and manually calls `Signals.model_validate_json(raw)`. Its route does not declare a request body for OpenAPI. Committed `services/api/openapi.json` has no telemetry `requestBody` and no `Signals` component. Generated `src/api/schema.d.ts` therefore has `operations['telemetry_post_telemetry'].requestBody?: never`. The acceptance requirement to validate against OpenAPI and a typed generated POST cannot be met truthfully without repairing schema publication. The raw-body size/validation order must remain enforced.

**Gap B — optional tick sequence missing:** T1.6 owner answer 14 and docs/04 specify optional `tick_seq >= 0 | null`, but `Signals` lacks it and `wake/service.py` sets `TelemetryEvent.tick_seq=None`. Sending the example payload's `tick_seq` currently returns 422 unknown field. The DB column already exists, so restoring that approved contract need not add a migration. Until explicitly authorized in this task's scope, keep it out of the wire body rather than assume it is accepted.

`ingest_telemetry(session, device, signals, raw_body, now, rules, rule_version) -> TelemetryResult` checks absolute clock skew **before** `(device_id, seq)` deduplication. More than 300 seconds old/future returns 422 `clock_skew`, including for a previously accepted retry. Within that limit, duplicate seq returns the original stored evaluation; changed raw bytes only produce a warning. All inserts/scoring/day transitions are one transaction. `ticks_received` counts distinct accepted events. A lower seq is not itself rejected; ordering must be enforced by the phone queue.

`POST /v1/telemetry` returns 200 `TelemetryResponse`: `evaluation_id`, `local_date`, `gate`, `score`, `decision`, nullable `confirm_reason`, `threshold`, `consecutive_high`, `rule_version`, `breakdown`, `penalties`, `day_state`, nullable `next_tick_in_sec`. The generated schema correctly describes that response, although several categorical fields are plain strings. Rate limit is 30/min/IP. Auth is 401 missing/invalid, 403 revoked. Problem responses have structured `type` and `code`; 422 clock skew has a `server_time` extension. 429 has Retry-After.

`GET /v1/config/wake` exposes effective `rules.window` (weekday/weekend times, boundary, holidays); `GET /v1/day/today` exposes `local_date`, frozen `tz`, and local `window.start/end` strings, and returns 404 before the day exists. It does not return an absolute window-start instant. Server pushes already include ISO `window_start`, `local_date`, and `tick_seq`. No client-side window calculator/config cache currently exists.

## 6. Constraints

- `sampleAndSend` must finish in less than 20 seconds per docs/08. Sensor calls are parallel and individually bounded around 5 seconds; queue flush budget is around 8 seconds, with time left for local persistence/metadata. The existing 10-second request timeout cannot simply be reused inside an 8-second flush.
- A timeout must abort fetch/body reads, not merely resolve a competing Promise while a request later mutates the queue. Native sensor APIs do not expose JS cancellation; ignore late resolutions and prevent them from changing an already finalized sample.
- Capture one timestamp and timezone for a snapshot before awaits. `new Date(now).toISOString()` is UTC-with-offset and acceptable; never substitute server receive time for the original sample time.
- Local retention is at most 2 hours; API freshness is separately 300 seconds. Docs/12 already states original timestamps are retained and old events fail skew/drop. Do not relax the server gate or rewrite an old event to make replay acceptable. Even duplicate acknowledgments may be unavailable after 300 seconds because current ingestion checks skew first.
- Queue operations and sequence allocation must be atomic and serialized. A crash after sending but before local acknowledgment must leave the same seq/body for retry; dropped rows must not cause sequence reuse. JS integers must remain safe; never wrap/reset on overflow.
- Bind rows/counters to device identity and approved API origin, never just a globally increasing unaffiliated seq. A stale in-flight request cannot delete or update a new session's rows, last result, or UI. Forget/revoke/re-pair must prevent cross-identity replay; a temporary Keychain outage must not be treated as revocation.
- SQLite operations use parameter binding and short transactions, not interpolated JSON/identity SQL. Persist data before network; never hold a DB transaction open across a fetch. Correct use of exclusive transactions and serialization must be verified against the chosen Expo 57 package.
- Only bounded original telemetry and queue metadata may be stored. No bearer in SQLite, no raw payloads/codes/tokens in logs. Bound queue growth and make expiration/error outcomes observable without retaining permanent dead-letter telemetry indefinitely.
- Retry network/timeout/5xx safely within future budgets; honor Retry-After without sleeping through the wake budget. Stop on auth failure and invoke central session invalidation for both 401 and 403. Terminal invalid schema/old clock-skew items must not block every later valid item forever; show sanitized diagnostics and do not change the OS clock or historical payload.
- No permission prompts from background sampling. No new automatic wake registration or full debug/settings UI in T2.3. A minimal authenticated manual sample/retry/status surface is needed to perform this task's acceptance before T2.5.
- New native SQLite build and normal signing must be verified; fake SQLite Jest tests alone do not establish real persistence across app restart. Use an isolated test API/DB/device, not owner production records.

## 8. Proposed approach (for owner approval)

1. Make only the explicitly approved API/schema contract repair, regenerate OpenAPI/mobile types, and prove raw-body limits and existing ingestion behavior remain unchanged.
2. Add exact Expo 57-compatible SQLite and planned JSON Schema test-validator pins; retain all current SDK/security pins.
3. Implement a pure `buildTelemetry` mapping native results into the authoritative generated request schema, with fixed-clock normalization and no server-derived fields.
4. Wrap native calls in individual deadlines and one total sampling/flush budget, preserving the captured time/tz and actual permission status.
5. Reuse the existing native HTTPS transport through a generated typed telemetry method with a remaining deadline and bounded allowlisted problem metadata; preserve redirect/origin checks.
6. Add a migrated, parameterized SQLite outbox/counter store; atomically allocate seq and enqueue immutable events under origin/device identity, with serialized short transactions and bounded retention.
7. Flush oldest-first under one owner, ACK by exact row/identity, keep transient failures, drop explicit terminal/expired items, and honor server backoff without wake-budget sleeps.
8. Extend the session controller with a narrow generation-bound authenticated operation/lifecycle seam so auth failures and pairing changes cannot leak or revive queued state.
9. Use supplied/cached authoritative window context where available and the owner-approved cold-start fallback; leave actual background wake registration to T2.4.
10. Add only minimal authenticated manual sample/retry/queue-status controls to the current home; preserve sensors and session controls, with broader debug UI still T2.5.
11. Test builder against the actual published schema, queue/counter/races using injected DB/fetch/clock, plus native SQLite restart and isolated HTTPS offline/replay acceptance with original seqs.
12. Run full checks/security/schema-staleness/native build with normal Simulator signing and record exact runtime evidence; do not claim physical airplane-mode, sensors, or push validation.

## 9. Risks and tests that catch them

- **Missing API schema produces a handwritten substitute:** assert `/v1/telemetry` has a real required JSON body schema, generated client accepts it, and builder fixtures validate against that exact component; preserve the route's 64 KiB and extra-field tests.
- **Silent seq reuse or lost durability:** deterministic concurrent/crash-point queue tests plus actual SQLite process restart; inspect server `(device_id,seq)` uniqueness without logging raw snapshots/tokens.
- **Budget only wraps a Promise:** injected hanging body reader/fetch/native promises and clock prove deadlines, aborted transport and no late queue/session mutations.
- **Old rows poison FIFO or fabricate fresh observations:** 301-second/2-hour boundaries, structured clock-skew 422, failed-first-row scenarios, and exact retry body/seq/time assertions.
- **Cached/fallback window disagrees with edited rules or travel:** context/config/timezone/DST/03:00 fixtures and explicit owner choice below; never call a naive Date local to the Mac authoritative.
- **Auth change replays another identity:** interleave deferred sample/flush/401/403 with forget/re-pair, Keychain outage and same-origin/different-device cases.
- **Mocks hide native SQLite/Keychain/TLS failures:** signed native build, isolated real queue persisted through process restart, API outage and recovery, schema/current-source checks; note Simulator limits honestly.

Primary references for implementation-time API verification: [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/) documents parameter binding and exclusive transactions; latest docs may target a newer SDK, so the chosen exact Expo 57 package source remains authoritative. Existing repo contracts and earlier owner answers govern policy.
