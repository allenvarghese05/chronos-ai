## 2. Why it matters

The backend already validates and versions complete wake-rule documents, but editing from the phone is absent. A settings screen must preserve the complete fetched document while editing selected fields, show meaningful validation failures, and distinguish a confirmed save from a timed-out write. Otherwise changing one threshold could silently discard penalty/reweight settings or overwrite a concurrent laptop edit.

General preference and test-push routes in the design are not implemented. T2.6 must provide their narrow backend support and be honest about what is merely stored for the future render pipeline. A test accepted by Expo does not prove that APNs delivered it or that the phone displayed it.

## 4. Current state

### Existing wake configuration API and versioning

- `services/api/src/chronos/api/config_wake.py` exposes authenticated/default-rate-limited `GET /v1/config/wake` and `PUT /v1/config/wake`. `ConfigWakeResponse` has `extra='forbid'` and fields `version`, `source`, `rules: WakeRules`, `sha256`, `yaml_sha256`, `yaml_stale`, `created_at`, `created_by`.
- PUT reads raw bytes with65,536-byte Content-Length/actual-body checks, parses JSON, then `WakeRules.model_validate(data)`. Failure is422 `application/problem+json` with `type='urn:chronos:error:rules_invalid'` and `errors: [{loc, msg, type}]`. These manually built problems need not contain the `code` extension; the client must recognize the exact `type` too. No raw submitted `input` is included in the error list.
- Successful PUT returns201 `{version, created: true}` or200 `{version, created: false}` when the canonical SHA already matches. The success handler returns `JSONResponse` without a concrete response model; generated success types are currently insufficient for a strongly typed settings save. Publishing a narrow DTO is appropriate; preserve pre-parse body validation and both response statuses.
- `wake/rules.py:canonical_json(rules: WakeRules) -> str` uses sorted compact JSON from `model_dump(mode='json')`; `rules_sha256(rules) -> str` hashes it. `activate_new_version(session: Session, rules: WakeRules, source: str, created_by: str) -> tuple[RuleVersion, bool]` uses a savepoint, deactivates current/inserts max-version+1, rolls back failed insertion, and invalidates the singleton `RulesCache`. API commits and records `created_by='api:<device.public_id>'`. `ensure_initial_version` preserves an existing active version across restarts. API writes do not edit YAML; CLI `chronos config apply-yaml` can promote YAML again.
- No conditional `If-Match`, expected-version field or conflict check exists. Two whole-document clients can overwrite each other's edits. The `version` inside `WakeRules` is a document/schema field, distinct from outer `ConfigWakeResponse.version`; editing a confirm threshold must preserve the former and let the server assign the latter.
- GET computes YAML metadata using module `_YAML_PATH`, while startup uses `Settings.wake_rules_path`; if supporting custom rule paths, implementation must avoid inventing provenance and narrowly align the metadata path rather than display a wrong hash.

### Actual WakeRules shape and edit constraints

- `WakeRules = {version: int, window: WakeRulesWindow, thresholds: Thresholds, rules: list[Rule], penalties: list[Penalty]=[], reweight_without_pedometer: dict[str,int]={}}`, `extra='forbid'` throughout the named models.
- `WakeRulesWindow`: `weekday: dict[str,str]`, `weekend: dict[str,str]`, `day_boundary='03:00'`, `holidays_as_weekend: list[str]=[]`, `tick_interval_min: int[2,30]=5`. Validator requires start/end, parseable times, start<end, parseable boundary and ISO holidays. Current time parser uses `datetime.time.fromisoformat`, so it accepts more than exact HH:MM; the form can explicitly use HH:MM without rewriting untouched values silently.
- `Thresholds`: `confirm`/`strong` in[1,100], `dedupe_min` in[1,60], `confirm_max_gap_min` in[2,60] default12; strong must be>=confirm.
- `Rule`: `id`, `signal`, `points: list[list[int|float|bool|str]]`, `cap>=0`, optional `requires: dict[str,list[str]]`, optional `bonus_consecutive: {ticks>=2, points>=0}`. Rows have exactly2 elements; numeric thresholds are strictly descending; boolean thresholds are actual booleans with one row; known enum thresholds must be allowed. `cap>=max(int(row[1]))` currently truncates/coerces award values rather than enforcing nonnegative integer awards.
- `Penalty`: `id`, `when: dict[str,str|list[str]]`, `points<=0`; conditions use the existing tiny parser and signal registry. `WakeRules` requires nonempty/unique rule IDs, reweight keys belonging to rules, total reweight<=100 and bonus reweight>bonus points. Reweight values currently have no nonnegative field bound.
- Thus the security requirement that rule weights are nonnegative is not completely enforced server-side for row awards/reweights. This is an existing validation gap, not evidence that negative values are intended. Narrow correction is an owner question below; do not silently broaden conditions, change scoring math or golden expected results.
- Default YAML has confirm70, strong85, dedupe2, max-gap12; weekday06:00–11:00, weekend08:00–14:00, boundary03:00, tick5. Existing six rules include multi-row numeric awards, bool bonus and enum foreground; penalties and the35/25/40 reweight map must survive a threshold-only save unchanged.
- `wake/service.py` obtains active rules/version per new telemetry evaluation; `wake/context.py:build_eval_context(...)` computes its window from those active rules. `wake/state.py:get_or_create_day(...)` preserves the existing day's stored timezone/window metadata; the scheduler also computes a fresh `Window` from active rules. Therefore a save is active for subsequent processing, but existing day rows/history are not rewritten. Do not promise that every window edit waits until tomorrow or that the stored day's displayed window will be rewritten. Day-boundary/cadence edits are outside the proposed basic form.

### General settings and future consumers

- `models/settings.py:Setting` already exists, with unique `key`, `value: str`, `updated_at`, `updated_by`. Initial migrations already create `settings`; no table/migration is necessary for these preferences.
- There is no `api/config.py` router, `GET/PATCH /v1/config`, general-settings resolver, theme field or runtime read of `Setting`. T1.4 Owner answer7 explicitly deferred generic config to T2.6. Its addition is part of this task, not a previously working endpoint.
- `config.py:Settings` contains environment/security/server/TLS/rules/logging/report fields, `ollama_endpoint`, `llm_provider='ollama'`, scheduler flag and Expo fields. It does not yet have `render_mode`, theme policy, `pexels_enabled` or Pexels `SecretStr` key. `.env.example` likewise lacks them. Safe defaults and exact new optional environment variables must be documented; never serialize `Settings.model_dump()` to produce a phone response.
- Design `GET /v1/config` describes effective values and origins (`env|yaml|db`), and `PATCH /v1/config` stores a subset. Restrict writes to the task's reel theme/render mode/Pexels preference, preserving other `Setting` rows. LLM provider, retention, tick interval and arbitrary environment/key writes are outside this settings form. Tick interval continues to come from WakeRules.
- Proposal for explicit theme preference: `auto|dawn|mono|ink`, defaultauto with the documented weekday/weekend policy; modes `eager|on_trigger`, defaulteager; Pexels requested flag defaultfalse. Report only a key-configured boolean/capability, never the key. An enabled preference with no key must be displayed as unavailable/not effective rather than claiming b-roll is working. Resolve DB over configured safe defaults and label origin honestly; no existing YAML preference file needs inventing.
- Renderer `packages/renderer/src/schema.ts` accepts theme `dawn|mono|ink`; `Root.tsx` currently uses fixture/default dawn. There is no integrated API content/render pipeline reading these settings. Storing/reading the preferences can pass T2.6; actual per-day selection/rendering/Pexels fetching belongs to later tasks and must be labeled accordingly.

### Test push support that must be added

- No admin router or `/v1/admin/push-test` exists. `models/delivery.py:PushNotification` already supports `kind='test'`, device, local date, nullable tick sequence, token-free payload JSON, ticket/receipt/error metadata. No schema migration is needed.
- `delivery/push.py:PushMessage` currently has only `to` (repr hidden), `_contentAvailable` defaulttrue, `priority='high'`, `data`. `to_expo_dict()` and token-free projection emit only those fields. Sending `{data:{type:'test'}}` with the current model is not the documented visible test push: bounded optional title/body/sound and `_contentAvailable=false` need narrow support, preserving existing silent serialization/tests.
- `PushClient.send(messages: Sequence[PushMessage]) -> list[Ticket]`, `get_receipts(ticket_ids: Sequence[str]) -> dict[str,Receipt]`; real `ExpoPushClient` uses the configured Expo URL/access token and httpx, FakePushClient is available for tests. Main lifespan only creates the Expo client inside `if scheduler_enabled`; an authenticated test route needs an explicitly owned/injectable client even in scheduler-disabled acceptance, without starting scheduled ticks or leaking a client on shutdown.
- Scheduler receipt polling uses existing `push_notifications` ticket rows and is15-minute/opportunistic while the scheduler runs. Do not make the button wait15minutes, create a new polling service, or report a receipt when only a ticket was received. New test records must not increment day tick counters, produce wake evaluation/confirmation/delivery or masquerade as silent ticks.
- Existing network retries can exceed the phone's10-second HTTP budget. Define a bounded test-send attempt, coalesce UI taps, throttle server-side and report timeout as unknown rather than automatically sending duplicates. Missing registered token/configuration returns a specific sanitized unavailable state without outbound I/O. Expo error strings/tokens/tickets must not be echoed into UI.
- T2.2 `requestPushToken(): Promise<PushResult>` already gates physical iOS and configured project ID before lazily importing notifications, then requests alert permission only from explicit foreground action and PATCHes a genuine token. Reuse it. No fabricated Simulator token, EAS/Apple purchase, account/key creation or new notification permission on screen mount.

## 6. Constraints

- Existing settings/rules, renderer and native pins remain exact; proposed dependencies **none**, new tables/migrations **none**. No pipeline/asset fetch, account provisioning, scoring/retention redesign or general admin API.
- Whole-rule preservation is mandatory. Use a typed cloned baseline plus selected field edits, not rebuilding just the six defaults. Preserve unknown supported rule IDs, signals, thresholds, `requires`, conditions, penalties, holidays, boundary, cadence and document version; unsupported shapes are read-only/error states, not dropped data. No automatic normalization that turns an unchanged document into a new version.
- Proposal edits weekday/weekend start/end, confirm/strong and existing award rows/caps/bonus/reweight weights. Show remaining advanced configuration as preserved/read-only; do not silently expose destructive rule add/remove, condition editing, cadence or day-boundary changes. Numeric threshold values are distinct from the points awarded at them.
- Nonnegative integer weights/caps/bonuses, strong>=confirm and cap/row/reweight cross-field constraints must be communicated. Root-level validator errors may apply to a section rather than one input. The server remains authoritative and must reject invalid documents atomically; failed writes leave active version/cache unchanged.
- No fire-and-forget writes, offline mutation queue or automatic save on field edit. Each save requires an explicit button; apply changed content only, verify by GET, and expose newly active DB version separately from document version. A dirty draft survives temporary network failures; a save whose response was lost is unconfirmed until readback agrees.
- New config read/write models must have bounded enum/key/value projections, default rate limit, body limits and `extra='forbid'`. Preserve32KiB mobile limit; oversized legitimate historic/custom WakeRules must fail clearly without truncation or default reset.
- Test push is an explicit external side effect, so do not auto-retry a button after uncertain timeout. Use a stricter bounded send rate and a test-only fake client for Simulator integration; never fabricate genuine Expo/APNs delivery. Do not log or return credentials, token or provider payload/error. Alert denial is separate from silent delivery.
- Owner has no paid Apple membership and a broken USB port. No purchase/setup question is needed again. Real visible test-push delivery remains pending until a supported signed physical build exists; API fake-path/Simulator unavailable states can be proven now.
- Current Xcode is27.2 with Device Hub. Preserve the existing test device/data; do not create more simulators to troubleshoot. Recent low-disk framebuffer trouble required regeneration-cache cleanup/service restart; check available space before any needed build, and do not erase device data or unrelated files.

## 10. Open questions

1. **Prevent concurrent rule overwrites:** May T2.6 add optional SHA-based `If-Match` preconditions to `PUT /v1/config/wake`, checked atomically with activation, and use them for phone saves? **Recommendation:** yes. Preserve existing no-header callers and same-content no-op behavior; stale edited drafts receive a sanitized conflict and must be explicitly refreshed/reapplied. This is a narrow contract extension, with generated documentation and concurrency tests, not a rules/versioning redesign.
2. **Close the existing weight-validation gap:** May T2.6 narrowly enforce nonnegative integer rule awards and reweight values server-side, rejecting booleans, fractional/nonfinite values and numeric strings in award slots, while preserving the valid existing numeric/bool/enum threshold types, penalty semantics and scoring math? **Recommendation:** yes. Current validators do not fully enforce the documented nonnegative-weight rule. Cover structured422 errors and unchanged active version/cache on rejection; do not edit golden score expectations or perform unrelated rule-schema cleanup.
