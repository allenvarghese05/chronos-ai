# T2.2 Brief: Pairing flow, secure storage, and API client

## 1. Task

**ID:** T2.2

**Task (copied from `docs/11-implementation-plan.md`):** Pairing flow + secure storage + API client: `/pairing` screen (code + QR scan via `expo-camera`), `expo-secure-store`, generated client, `PATCH /device/me` with push token, cert trust instructions screen

**Size:** M

**Depends:** T1.2, T0.7

**Acceptance criteria (verbatim):** Pair with a code printed by the laptop; token persists across restarts; revoke → app returns to pairing

**M2 done when (verbatim):** on the owner's iPhone, silent pushes wake the app in the background, real CoreMotion history is posted, and the debug screen shows the server's breakdown.

This task supplies authenticated identity and transport for T2.3. M2's complete background
acceptance is not acceptance of this task alone.

## 2. Why it matters

The app currently cannot authenticate to the existing laptop API. T2.2 must exchange a short-lived
code for a device token, retain that credential across process restarts, attach it only to the
intended HTTPS API, and forget it when authentication is invalidated. If pairing is ambiguous or
token storage fails silently, later telemetry cannot reliably send or recover. If scanned URLs
or server responses can redirect credential use to another host, the pairing feature becomes a
token-disclosure path.

The owner cannot connect the iPhone by cable because its port is broken and uses MagSafe for
charging. It is not currently visible as a paired Xcode device. Simulator is the current manual
validation environment. Camera scanning and real APNs/Expo registration must not be claimed as
physically verified; manual pairing-code entry, Keychain persistence, and revocation can be
exercised in Simulator against the laptop API.

### Existing API contract and generated types

`apps/mobile/src/api/schema.d.ts` is generated and committed by T0.7. It exports `paths`,
`components`, and `operations`; use it rather than duplicating API DTOs. Relevant operation IDs:

- `pairing_create_pair` → `POST /v1/pair`.
- `device_get_device` → `GET /v1/device/me`.
- `device_patch_device` → `PATCH /v1/device/me`.
- `device_delete_device` → `DELETE /v1/device/me`.

Relevant exact generated component fields:

```ts
DeviceInfo: {
  app_version: string;
  ios_version: string;
  model: string;
  name: string;
  tz: string;
};
PairRequest: { code: string; device: components['schemas']['DeviceInfo'] };
PairResponse: { api_base: string; device_id: string; server_time: string; token: string };
DevicePatch: {
  app_version?: string | null;
  expo_push_token?: string | null;
  ios_version?: string | null;
  tz?: string | null;
};
```

`DeviceResponse` returns `device_id`, `name`, `model`, `ios_version`, `app_version`, `tz`,
`expo_push_token`, `status`, `created_at`, `last_seen_at`, and `revoked_at`; no bearer token.
`Problem` has `type`, `title`, `status`, `detail`, `instance`, optional `code`, and extensions.

The generated pairing operation currently declares only 201 and 422; its 422 is generated as
`HTTPValidationError` even though runtime exception handling returns RFC 9457. The runtime
400/409/410/429 cases exist but are not typed in that operation. Authenticated operations declare
401/403/422/429 with `Problem`, but generated content metadata uses `application/json` whereas
runtime errors use `application/problem+json`. A runtime boundary must narrow unknown response
errors and handle status independently; do not pretend compile-time types validate network JSON.
No backend/schema change is necessary just to implement a defensive client.

`scripts/gen-types.sh` exports `services/api/openapi.json` then invokes `openapi-typescript`.
CI independently regenerates/diffs both committed artifacts. Do not hand-edit generated files.

### Backend behavior already implemented

`services/api/src/chronos/api/pair.py` defines:

```python
class DeviceInfo(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: Annotated[str, Field(min_length=1, max_length=120)]
    model: Annotated[str, Field(min_length=1, max_length=80)]
    ios_version: Annotated[str, Field(min_length=1, max_length=20)]
    app_version: Annotated[str, Field(min_length=1, max_length=20)]
    tz: Annotated[str, Field(min_length=1, max_length=64)]
class PairRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    code: Annotated[str, Field(min_length=8, max_length=9)]
    device: DeviceInfo
```

Timezone is validated against `zoneinfo.available_timezones()`. POST returns 201 `PairResponse`;
the plaintext 43-character base64url token is returned only at pairing. The database stores
SHA-256 in `devices.token_hash`.

`chronos.auth.normalise_pairing_code(code: str) -> str` uppercases and removes dashes/spaces.
`PAIRING_ALPHABET = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'`; despite older prose saying 32 characters,
the client should use the actual alphabet, not assume every alphanumeric character is valid.
The request's raw 8–9-character length limit applies before server normalization, so the client
must normalize spaces before submission. The server selects the latest nonconsumed code,
expires it after 10 minutes, counts nonexpired submissions, and burns after five wrong attempts.
Six pairing requests inside the rate-limit window can receive 429 with `Retry-After`.

One active device is enforced **before** code validation. Existing active device → 409; no
automatic replacement. `chronos device revoke` or authenticated DELETE is the intended remedy.
`chronos.auth.require_device(...) -> Device` returns 401 `unauthorized` for unknown/invalid
tokens and 403 `revoked` for known revoked devices, updating `last_seen_at` at most once/60s.
`DELETE /v1/device/me` returns 204; future calls with that credential return 403.

`DevicePatch` permits all fields shown above. Passing `expo_push_token: null` currently does
not clear the stored token because the router updates it only if not None. T2.2 should omit
unavailable tokens, not assume null clears registration.

### Laptop QR and TLS bootstrap

`chronos pair-code` prints the code, API base, and terminal QR. Exact QR JSON:

```json
{"code":"7K2M-9QXD","api_base":"https://laptop-host.local:8443/v1"}
```

This is JSON, not a `chronos://` deep link and not Metro's development-client QR. Scanning must
decode this format explicitly. The payload contains no fingerprint, CA certificate, or token.
`CHRONOS_PUBLIC_BASE_URL` controls the value; if absent `Settings._derive_public_base_url`
derives it from bind host/port and TLS settings. A misconfigured dev server can emit HTTP;
the mobile production pairing flow must reject it and explain how to fix TLS configuration.

`scripts/certs.sh` writes gitignored `data/certs/chronos-lan.pem`,
`chronos-lan-key.pem`, and public `rootCA.pem`. It prints the **leaf** SHA-256 fingerprint via
`openssl x509 -noout -fingerprint -sha256`; it currently prints no root fingerprint in the QR.
Never expose the certificate directory through an app endpoint or broaden static serving;
it also holds the private key. Trust instructions must identify the public root only, install
the profile, then enable full trust in iOS Certificate Trust Settings. Simulator root trust can
be installed using supported `simctl keychain` tooling during manual validation.

The app's JS APIs do not expose the peer TLS certificate. Rendering a user-provided value is not
certificate pinning. T1.2 owner answer 4 explicitly omitted a fingerprint field; T0.6 supplies
manual cert setup, not an API for fetching fingerprints. See open question 2.

### Push setup

Installed `getExpoPushTokenAsync(options: ExpoPushTokenOptions = {})` resolves project ID from
`options.projectId`, `Constants.easConfig?.projectId`, then
`Constants.expoConfig?.extra?.eas?.projectId`. It throws

## 5. Inputs and outputs

| Input | Required output / boundary |
|---|---|
| Manual code + API URL copied from laptop | Normalize code, validate canonical HTTPS `/v1` base, show target host before sending; POST typed `PairRequest` without bearer |
| Camera QR string | Bounded JSON parse of exactly expected pairing fields; validate; populate the same confirmation/form path; no automatic network request on scan |
| Native device metadata | Bounded device name/model/iOS version, app version, current IANA timezone; valid nonempty simulator fallbacks without fabricated hardware identity |
| Successful 201 pairing response | Runtime-validated session persisted to SecureStore before authenticated navigation; clear entered code from active form state |
| Stored session on process launch | Hydrating/authenticated/unpaired/error state; no brief flash of protected content; authenticated GET `/v1/device/me` validates it when reachable |
| Authenticated HTTP request | Exactly one `/v1` path prefix; bearer only to the approved API origin; bounded timeout; sanitized errors |
| 401 unauthorized / 403 revoked | Clear session storage/in-memory identity and route to pairing; deduplicate concurrent invalidations |
| Offline/TLS failure/5xx/429 | Distinguish transient or trust failure from auth revocation; retain valid stored session; expose recovery/retry without a request storm |
| Successful Expo registration | PATCH `/v1/device/me` with actual `expo_push_token`, timezone and versions; retry separately from pairing when appropriate |
| Notification denied/missing project ID/Simulator | Explicit nonblocking status; no fabricated token or silent assertion of successful push setup |
| Revoke/unpair action | Revoke backend when explicitly requested, then clear local credential; local forgetting alone must not imply server revoke succeeded |

Proposed session envelope is one versioned SecureStore record containing credential and its
bound canonical endpoint/device ID. This avoids persisting a token and endpoint independently
into a mismatched state and requires no unencrypted general-purpose persistence dependency.
Zustand state can expose hydration/session/status; do not persist secrets through its default
storage or print them in devtools. A memory cache does not solve locked cold-start accessibility.

Generated `paths` already include `/v1/...`, while the advertised base already ends `/v1`.
For `openapi-fetch`, derive the validated origin as `baseUrl` and call the generated full paths;
otherwise `/v1/v1/pair` is a predictable integration bug. Do not concatenate arbitrary QR paths.

## 6. Constraints

- Token uses secure native Keychain, no AsyncStorage/plain JSON/.env/query parameter. Keychain
  accessibility follows the binding requirement unless owner explicitly approves question 1.
  No biometric prompt is required for every request; that would prevent background operation.
- HTTP is not a user-facing fallback. TLS failure routes to accurate trust instructions, not
  `rejectUnauthorized: false`, broad ATS exceptions, or a server change to test mode.
- The configured API is intentionally LAN/private, so the server's public-feed SSRF guard is
  not a reason to reject all LAN IPs on the mobile client. URL validation still rejects credentials,
  query/fragment confusion, malformed ports, non-HTTPS schemes, wildcard addresses, and paths
  other than the supported API base. QR input is untrusted, not an instruction to open a link.
- Bind any returned `api_base` to the approved origin. A changed origin needs explicit
  reconfiguration/reconfirmation; do not send a token to a replacement host automatically.
- Native fetch follows platform TLS trust; no promise of peer-fingerprint inspection or
  redirect-control features unsupported by React Native. Implement transport tests on the actual
  selected client and review redirect handling before credential-bearing requests are accepted.
- Never log raw tokens, codes, push tokens, auth headers, or raw pairing responses. Tests use fake
  credentials and assert sanitized failure output. UI avoids secret values in screenshots.
- QR scanning mounts camera only when requested, only scans QR, releases camera when leaving,
  ignores duplicate callbacks during submission, and retains manual input when permission denied.
- Camera plugin needs a specific usage explanation; do not request microphone/media permissions
  for QR scanning. No scanned images or camera frames are stored.
- Add only dependencies named with exact versions in the implementation plan. Candidate necessary
  packages: `expo-camera`, `openapi-fetch`, `zustand` per design, and `expo-device` for permitted
  metadata/physical-device detection. Avoid `expo-localization` if built-in Intl suffices.
- No backend DB migration or pairing-router change is assumed. Do not modify server-owned auth
  semantics, push scheduling, scoring, telemetry queue, full settings, feed/player, or T2.4 wake flow.
- Required verification is `just check`, `just check-mobile`, `just security`, schema staleness,
  native config/build after camera integration, and manual HTTPS Simulator pairing/relaunch/revoke.
  Security and API acceptance are not proved by mocked fetch alone.
- Physical camera/notification/locked-Keychain verification remains unperformed until a signed
  iPhone installation route is available. Realistic mocks and clear deferral are required.

## 7. Edge cases

| Case and concrete input | Expected outcome / test |
|---|---|
| Manual `7k2m - 9qxd` | Normalize to an allowed 8-character code before request length validation; no extra whitespace sent |
| `0000-OOOO`, 7/10 characters | Local validation; no pairing attempt consumed |
| QR is a Metro URL or arbitrary text | Reject as not a Chronos pairing QR; manual entry remains usable |
| QR oversized, invalid JSON, array/null, extra/unexpected fields | Bounded parse; deterministic visible validation error; no fetch |
| QR URL `http://host:8443/v1`, embedded credentials, unexpected path/query/fragment | Reject locally; do not downgrade transport |
| Same QR callback emitted repeatedly | One confirmation/submission; do not consume code or create duplicate sessions twice |
| 201 returns missing token/device ID or unrelated API origin | Do not store an untrusted/incomplete session or navigate authenticated; show recoverable failure |
| Expired code → 410; invalid/burned → 400 | Explain new code generation; no infinite auto-retry consuming attempts |
| Existing active Simulator device → 409 | Explain owner CLI/API revoke; do not automatically revoke another device |
| Pairing 429 with `Retry-After: 12` | Disable repeated submission/back off appropriately; no timer relying on a drifting real test clock |
| Server accepted pairing but response was lost | Remain unpaired; subsequent conflict gets explicit recovery instructions, not a silent retry loop |
| Keychain write fails after 201 | Never claim persistence/success; server may now have active device, so show revoke/retry recovery without exposing token |
| Relaunch with valid stored envelope | Hydrate before protected routing; token attaches to GET and persists without re-entry |
| Relaunch offline / untrusted or expired leaf | Keep credential; show offline/trust retry state rather than deleting it as revoked |
| Stored malformed/old envelope or missing endpoint | Do not make a request with an unbound token; recover to pairing/storage error with no secret logs |
| Keychain unavailable while locked | Do not interpret an accessibility error as absent/revoked token; reconcile question 1 before future background flow |
| 401 or 403 revoked from any authenticated method | Clear once and route pairing; a later response cannot restore the invalid session |
| Logout/re-pair during an in-flight request | Session generation prevents stale success/error from mutating the new identity |
| Device revoked on laptop while app idle | Foreground/startup GET detects invalidation; no claim of instantaneous server-to-app revocation notification |
| Camera permission denied or Simulator camera absent | Manual code + URL pairing still works; no modal trap or failed acceptance claim |
| Notification denied, Expo network failure, no project ID | Pairing remains successful; push unavailable state explicit, retry isolated, no fake PATCH token |
| Actual push token received twice or rotates | Idempotent PATCH of latest token; no log; no re-pair required |
| `expo_push_token: null` | Do not rely on this to clear backend registration; existing router ignores it |
| API returns HTML/non-JSON/empty error body | Bounded sanitized generic error; do not crash JSON parsing or display server HTML |
| Timezone changes from America/New_York | Use current device IANA value for PATCH; do not implement day-window logic here |
| Device clock wrong by >5 min | Pairing does not use telemetry skew logic; retain `server_time` if useful, no pretend automatic clock adjustment |
| Force-quit and restart | Persisted session restores; show accurate caveat that force-quit can prevent silent wakes, not claim T2.4 is implemented |
| New SDK dependency installed without native rebuild | Document rebuild requirement; JS export alone is insufficient evidence |

## 8. Proposed approach (for owner approval)

1. Add `/pairing` and a certificate-trust instructions route, with manual code and editable API URL as the primary Simulator flow.
2. Add opt-in QR camera scan using `CameraView`, feeding a pure bounded parser and explicit target confirmation rather than submitting automatically.
3. Build `openapi-fetch<paths>` around validated origin, generated full `/v1/...` paths, bounded requests, runtime response narrowing, and centralized auth invalidation.
4. Use a small Zustand session store plus injectable SecureStore adapter; hydrate a versioned credential/endpoint record before route guarding; no unencrypted secret persistence.
5. Load permitted metadata from existing Constants/React Native/Intl and planned `expo-device`, with explicit simulator-safe values.
6. Commit the secure session before navigating; validate it with GET on startup/foreground, preserving it during connectivity/trust failures and clearing it on confirmed 401/403.
7. Offer notification registration as a separate nonblocking action with project/device checks, actual token PATCH, and retry/status independent of pairing success.
8. Keep the home screen content and future sensor integration intact; provide only the minimum paired-state/recovery controls needed for T2.2 acceptance.
9. Add deterministic parser/client/store/permissions/navigation tests using injected fetch, storage and native mocks; include stale-request and storage-failure cases.
10. Verify native camera config, full CI/security checks and real HTTPS Simulator pairing/restart/revoke; document hardware-only tests as deferred.

## 10. Open questions

1. **Keychain accessibility:** `docs/09-security.md` mandates `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, but that prevents a freshly launched locked-phone worker from reading its token. May T2.2 introduce a binding ADR and update the security document to use `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` (still device-bound, readable only after the first unlock following reboot) for the paired session? **Recommendation:** approve that targeted policy change now so the credential design supports the planned wake engine; if declined, retain the current policy and explicitly defer locked-background authentication resolution to T2.4 rather than weakening it silently.
2. **Certificate fingerprint presentation:** neither the existing QR nor API provides the fingerprint, and JS cannot inspect the peer certificate. May T2.2 supply accurate out-of-band trust/fingerprint comparison instructions using the laptop's public certificate output, clearly stating that the app does not perform certificate pinning, without extending backend/QR schemas? **Recommendation:** yes; keep API/CLI changes out of this task and never display an invented or unverified fingerprint as if it authenticated the server.
3. **Push configuration/hardware:** no EAS project ID is configured and no physical iPhone installation route is available. May T2.2 implement and test the real registration/PATCH path behind a configured project ID, but leave missing-ID/Simulator push status nonblocking and defer actual token issuance/delivery to T2.4? **Recommendation:** yes; expose an optional documented project-ID configuration, create no Expo project or credentials automatically, and accept Simulator pairing/restart/revoke now with real push explicitly unverified.
