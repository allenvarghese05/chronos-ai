## 2. Why it matters

The owner currently sees a manually sampled native panel and only an evaluation ID/score. Diagnosing a morning requires relating the exact sampled signals to the server's stored rule contributions, queue state and actual tick history. A fresh local sample is not necessarily acknowledged, and an acknowledged outbox head may be older than the latest sample. Showing these as one current result would mislead tuning.

The debug screen must work after process restart, distinguish unavailable/stale/offline data from actual zero readings, and let the owner record ground truth without changing scoring or confirming the day. Existing day counters cannot identify missed silent ticks: `ticks_received` increments for every unique telemetry event, including manual and foreground samples.

## 4. Current state

### Mobile navigation and runtime

- `apps/mobile/app/_layout.tsx` declares `index`, `pairing`, `certificate`; there is no `/debug` route. `SessionProvider` wraps the Router stack. `ProtectedScene({ children })` redirects unless `phase === 'authenticated'`; hydrating renders a waiting state.
- `app/index.tsx` is setup/acceptance Home, not the planned reel feed. It mounts `TelemetryControls`, `WakePermissions`, a one-time `deviceState()` read and authorized `querySteps` read, connection/revoke/forget controls. Preserve these working flows and add clear debug navigation; do not implement T5's feed here.
- `src/ui.ts` provides shared readable styles. React Native `View`, `Text`, `ScrollView`, `TextInput`, `Button` and existing styles suffice for an accessible score visualization/list and `HH:MM` input. No chart/date-picker dependency is necessary for the proposal.
- `src/wake/bootstrap.ts` exports singleton `wakeRuntime`, `wakeSetupStatus(): { registrationStatus, scheduleStatus }`, `subscribeWakeSetup(listener)`. It defines TaskManager globally before Router, owns AppState subscriptions and the shared native refresh handoff. A screen must not define another task, foreground handler or sensor-polling loop.
- `createWakeRuntime(deps)` exposes `run(source: WakeSource, tick?: Tick, external?: AbortSignal): Promise<TelemetryOutcome>` and `foreground(isActive: boolean): void`. `run` bounds restore/sample/flush under one 18-second deadline and caches validated tick context by session identity/timezone/day. Prefer `wakeRuntime.run('manual')` for Send now so manual work shares this context/deadline rather than inventing a client window.

### Sampler, outbox and display data

- `src/wake/sample.ts`: `sample(sensors: Sensors, source: WakeSource, now: () => number, tz: string, appVersion: string, context?: WindowContext, tickSeq?: number | null): Promise<Sample>`, `Sample = { input: SampleInput; diagnostics: string[] }`. Captures one instant/timezone; actual authorization before queries; five-second native budget; no prompt. Missing context means zero window steps plus a diagnostic; no native bridge (`iosVersion === '0.0'`) is unavailable, not real zero.
- `src/wake/buildTelemetry.ts`: `buildTelemetry(input: SampleInput, seq: number): Telemetry`; generated `Signals` whitelist only, bounded normalization, original timestamp and optional tick correlation. `WindowContext = { windowStart: string; tz: string; localDate: string }` is validated, not guessed from weekday defaults.
- `src/telemetry/native.ts`: `nativeTelemetry(session: SessionController)` caches one controller per session owner in a WeakMap, shares one private SQLite outbox. Reuse this instance, never create a debug-specific sequence counter or queue.
- `createTelemetryController(deps)` exposes `sampleAndSend(source, context?, attempt?): Promise<TelemetryOutcome>`, `flush(attempt?): Promise<TelemetryOutcome>`, `status()`, `subscribe(listener)`, `refresh()`. `TelemetryOutcome = 'sent' | 'queued' | 'skipped' | 'failed'`; `WakeAttempt = { signal?: AbortSignal; deadline?: number; tickSeq?: number }`.
- `TelemetryStatus` currently contains `{ busy, count, lastSeq, lastResult, message, diagnostics, retryAt }`; **it does not retain the sampled Signals or the acknowledged sample/result pair**. `lastSeq` is set on enqueue and on ACK; `lastResult` may still describe an older ACK while another row is queued. There is no durable last-result cache beyond server DB. Extending status with identity-scoped, immutable latest-local and acknowledged-pair metadata is needed for accurate display; no extra token/raw-error storage.
- `src/telemetry/outbox.ts` exports `createOutbox(db): Outbox`: `enqueue(identity, now, build)`, `head(identity)`, `ack(identity, seq)`, `defer(identity, seq, retryAt, attempts)`, `prune(now)`, `count(identity)`, `retire(identity)`. Tables `telemetry_counters` and `telemetry_outbox`, max 256 rows/32 KiB body, two-hour local retention, FIFO original bodies. Tokens remain only in Keychain; server freshness is separately 300 seconds. `refresh()` reads current identity count. Mounting debug must not consume/alter queued bodies except existing explicit sample/retry behavior.
- `src/telemetry/controls.tsx` subscribes to status and shows count/last sequence/score plus sample and retry. It proves the integration seam but is not the requested full debug screen.
- `src/wake/permissions.tsx` exports `WakePermissions`, reads actual Motion/refresh/low-power/notification statuses and provides explicit foreground-only actions. Reuse it or its existing seams; no automatic permission prompt from debug rendering. The native bridge already exposes `hello`, `deviceState`, `pedometerAuthorization`, `backgroundRefreshStatus` and readiness/completion methods.

### Secure API client and session seams

- `src/session/store.ts`: `SessionLease = { identity: string; current(): boolean; run<T>(operation: (api: Api) => Promise<T>): Promise<T> }`. Identity is canonical API base plus device ID; `current()` includes generation. `lease.run` checks before/after and centrally invalidates confirmed authenticated 401/403 without waiting for noncancellable Keychain cleanup. A temporary network/TLS/body error does not clear pairing.
- `createApi(apiBase: string, transport: Transport, token?: string)` currently permits only exact `/v1/pair`, `/v1/device/me`, `/v1/telemetry`. Authorization is explicitly attached only to device/telemetry requests. It returns `pair`, `getDevice`, `patchDevice`, `revoke`, `telemetry`; no day/annotation/history/version methods. New methods need an explicit, method-aware bounded allowlist; do not broaden to arbitrary `/v1/*` or let UI supply an origin/path.
- Transport uses SDK57 `expo/fetch`, same-origin check, `redirect: 'error'`, omitted credentials, a maximum ten-second budget and 32-KiB streamed response limit; optional `RequestBudget = { signal: AbortSignal; timeoutMs: number }`. Preserve cancellation of fetch/body reads and immediate 401/403 handling. New structured debug models require bounded runtime validation as well as generated compile-time types.
- `deviceMetadata(): DeviceInfo` in `src/session/native.ts` supplies actual IANA `tz`, app version from `Constants.expoConfig?.version` (fallback `0.0.1`), actual iOS/model strings. `app.config.ts` version is `process.env.VERSION ?? '0.0.1'`; do not claim npm package version or native bridge `hello()` is the server version.

### Actual backend APIs, database and gaps

- `services/api/src/chronos/api/day.py` already implements authenticated `GET /v1/day/today`, `GET /v1/day/{local_date_str}`, `PUT /v1/day/{local_date_str}/actual-wake`. `ActualWakeBody` has `extra='forbid'` and accepts exact 24-hour `HH:MM`. PUT is an idempotent overwrite of `Day.actual_wake_local`; it returns `DayResponse`, no scoring or confirmation. A missing device/day returns 404. The existing router does not currently add the default rate-limit dependency; narrowly applying the documented limit to new debug access/annotation integration must be explicit in the plan.
- `DayResponse` fields: `local_date`, `kind`, `tz`, `window: dict[str,str]` (`HH:MM`), `state`, `confirmed_at`, `delivered_at`, `fallback_used`, `ticks_sent`, `ticks_received`, `reel`, `score_timeline: list[ScoreTimelinePoint]`, `actual_wake_local`. `ScoreTimelinePoint = { at: str, score: int }`. The timeline is **one local day**, unpaginated, and excludes `ignored_dedupe`/`already_confirmed`. It is not a rolling 24-hour diagnostics history and has no event/evaluation IDs or full breakdown.
- `/day/today` derives day from server UTC now + **stored `device.tz`** + current rules' boundary; the stored device timezone can differ from current phone metadata. Do not derive annotation targets by the Mac timezone or silently apply the phone's current zone to an older day. Display the explicit day date/timezone returned by the server.
- `api/telemetry.py` returns `TelemetryResponse` including evaluation ID, local date, gate, score, decision, confirm reason, thresholds, consecutive high, rule version, breakdown, penalties, day state and next-tick delay. It does not return sampled Signals, capture timestamp or `derived` facts. No GET evaluation/latest endpoint exists.
- `wake/service.py:ingest_telemetry(...)` writes `TelemetryEvent.raw_json` (validated Signals), `tick_seq`, `device_ts` (offset ISO string), `received_at`, `local_date`, and `WakeEvaluation.breakdown_json = json.dumps(evaluation.model_dump(mode='json'))`. The latter contains the complete stored `Evaluation`, including `derived`, notes, thresholds and rule version. It can be parsed/validated for a read-only diagnostics response without re-running scoring. **`day.ticks_received += 1` happens for every unique telemetry event**, not only silent pushes.
- Tables already suffice: `telemetry_events`, `wake_evaluations` (1:1 event), `days`, `rule_versions`, `push_notifications`. Query every join through authenticated `device.id`. There is no need for a new table, migration, job or retention policy in the proposed scope.
- `models/delivery.py:PushNotification` has `device_id`, `kind`, `local_date`, `tick_seq`, token-free `payload_json`, `ticket_status`, `receipt_status`, `sent_at`, `error`. `scheduler.py:_do_send_tick` records every attempt; only `ticket_status=='ok'` increments `day.ticks_sent`. The pair **`(local_date, tick_seq)`**, plus device, is the tick identity; seq resets daily. Error attempts are recorded but should not be silently conflated with accepted ticks that have no correlated telemetry. A receipt is still not proof of application execution.
- `api/report.py` serves Markdown from a prewritten file or `report/builder.py:build_day_report(session, device_id, local_date, now)`. It is a human report, not a typed/bounded debug API; parsing report prose to recover signals/ticks is inappropriate. Existing report subtraction/anomaly wording is not an authoritative missed-tick list and need not be redesigned here.
- `api/health.py:healthz() -> dict[str, Any]` returns `{ok, version}` at public `/healthz`, sourced from `chronos.__version__`; `/readyz` currently checks DB. A new authenticated debug response can include the same version directly, avoiding a token-bearing request to a public root endpoint. Never return settings/env, device records with push tokens, certificates, database paths or full push payloads.
- `main.py:create_app` wires existing routers and OpenAPI augmentation. `services/api/openapi.json` and `apps/mobile/src/api/schema.d.ts` already contain `DayResponse`, `ActualWakeBody`, `TelemetryResponse`, `Signals` but no debug history model. `just gen-types` regenerates committed contracts; `tests/test_openapi.py` fails stale export. The existing 32-KiB client cap requires genuinely bounded/paginated history; do not simply append 24 hours of full evaluations to `DayResponse` or relax the global body cap.

## 6. Constraints

- No second scoring engine, client-derived wake window, scheduler/cadence change, push credentials, T2.6 settings editor or content/media/reel work. Debug actions must not accidentally confirm a day except the existing normal server evaluation of an honestly labeled manual snapshot.
- New authenticated diagnostics reads and annotation integration use the existing same-origin TLS/lease boundary. Validate dates/cursors/limits and runtime response shapes; parameterized queries; no arbitrary SQL/path/origin. Keep maximum streamed response 32 KiB, cancellation and fixed sanitized error text. Bound page count, loaded points and render work; explicit paging/aggregation/completeness is required under high event volume.
- Rolling 24 hours means elapsed 86,400 seconds anchored to server UTC, not 24 wall-clock labels, midnight-to-midnight or today's single day. `device_ts` strings can carry different offsets: lexical SQL sorting/comparison is not chronological. Normalize aware instants and use stable timestamp+ID pagination; freeze the range during page loading and handle concurrent arrivals without duplication.
- A stale server snapshot is not live hardware. Show timestamp/source/age and distinguish fresh local sample, queued sample and server-acknowledged data. `null` battery/unknown state remain unknown; denied/unavailable motion zero values retain their diagnostic.
- Do not poll motion history continuously. Refresh on focus/foreground, explicit Refresh/Send now completion and current controller notifications, coalescing overlaps. Abort/ignore on blur/background/unmount or changed lease; clean subscriptions/timers. Screen viewing must not multiply automatic foreground samples already owned by global bootstrap.
- Manual annotation is exact `HH:MM`, tied to explicit server day/timezone. Current storage cannot distinguish repeated DST-fold times or store an offset; display that limitation rather than invent an instant or infer ground truth. No automatic save on opening/time-field edit and no new clear/null behavior without a separate decision. A failed/timeout response may follow a committed PUT: keep draft and verify saved value by readback; never claim success without confirmation.
- No new dependencies are proposed. Use existing React Native primitives plus accessible textual rows for scores and gaps, fixed 0–100 scale and empty intervals; do not draw a zero score where there was no sample. Large text/scrolling must work without reliance on color or tiny chart labels.
- Build and real native SQLite/TLS Simulator acceptance remain useful. No paid membership, USB fix, account creation or hardware purchase is requested. All T2.4 real-device debt stays pending and explicit; no diagnostics screen can prove why iOS did not wake the app.

## 7. Edge cases

| Concrete case | Expected behavior |
|---|---|
| Hydration pending/unpaired, then debug deep link | No sensor/API/outbox access until authenticated; protected route redirects appropriately. |
| Process restart after a previously acknowledged sample | Restore latest stored server Signals + Evaluation from diagnostics; do not show only empty in-memory result or claim a new sample was taken. |
| Latest sample seq 8 queued; flush ACKs older seq 7 | Label local seq 8 queued and server/ACK seq 7 separately; no pairing of seq 8 signals with seq 7 score. |
| Send now while global foreground/native wake already running | Shared runtime returns honest skipped/busy; no duplicate counter allocation, listeners or relabeled outcome; refresh available results. |
| Native unavailable / Motion denied / battery null | Explicit unavailable/authorization/unknown states, approved zero fallback with diagnostics; no automatic prompt or fabricated hardware success. |
| Laptop offline while Send now | Native snapshot remains queued with original seq/time; server history remains timestamped stale; queue count updates. Temporary error preserves pairing. |
| Queued row >300 seconds old but <2 hours locally | Existing terminal clock-skew drop occurs without rewriting timestamp; diagnostics distinguish drop from ACK and queue count refreshes. |
| Server 401/403 with hanging body | Immediate central session invalidation and debug state cleared; no retry under new identity. |
| Forget/re-pair while history/annotation/native sample resolves | Generation guard discards old results and drafts; no old score/queue count/annotation written or rendered for new pairing. |
| Response >32 KiB, malformed model, oversized notes/point arrays | Bounded rejection and sanitized unavailable state; no global cap increase or rendering unbounded remote text. |
| 25-hour DST day / 23-hour DST day / travel | Rolling range remains exactly24 elapsed hours; labels expose repeated-hour offset; server day/timezone retained for annotation. No Mac-local date calculations. |
| `2026-11-01T01:30:00-04:00` and `01:15:00-05:00` | Correct instant order despite misleading wall-clock/lexical order; stable ties by ID. |
| 02:30 local before configured03:00 boundary | Annotation target comes from server's explicit day, not phone calendar-date guess; label target date/timezone. |
| Rolling history crosses boundary while more pages load | Frozen server interval/cursor; no duplicated/missing rows from moving now; newly arrived data appears on explicit refresh. |
| Empty timeline versus real score0 outside window | Empty is no samples, not a plotted zero. Actual0 retains decision/source; deduped/already-confirmed points are labeled or explicitly excluded, never silently reinterpreted. |
| Two devices historically share day/seq | All reads and joins scoped to current authenticated device; no historic revoked-device leak. |
| Foreground/manual samples raise `ticks_received` above `ticks_sent` | Missed list uses explicit tick joins, never counter subtraction or negative “missed” count. |
| Accepted tick0 yesterday and tick0 today | Distinct `(device,local_date,tick_seq)` identities, no false matching across days. |
| Tick accepted10seconds ago, no telemetry yet | Awaiting correlation, not overdue; explicit grace policy below. |
| Tick accepted2minutes ago but phone queued snapshot offline | No matching telemetry yet / overdue, not proof of push loss or force-quit. Later replay can resolve status if accepted. |
| Push error/no token/scheduler disabled | Separate push-failed or no attempts; no invented expected ticks for periods with no recorded send. Receipt/error raw payloads/tokens not exposed. |
| Duplicate telemetry references same tick | Received tick counted once; multiple score evaluations remain separately identified. |
| `07:05`, `7:5`, `24:00`, whitespace, future-looking draft | Only deliberate exact valid `HH:MM` sent; server remains authoritative. No silent coercion or guessed offset. |
| Annotation save during network loss after commit | Do not claim saved/unsaved certainty from timeout; read back explicit day and preserve draft. Same valid PUT can be retried idempotently. |
| Permission changes in Settings then foreground | Read actual statuses through existing flow; global foreground sampling happens once; debug updates without background native polling. |

## 8. Proposed approach (for owner approval)

1. Add a protected `/debug` route and Home navigation using existing styles/primitives; keep pairing, permissions and manual acceptance controls working.
2. With owner approval, add a narrow authenticated, read-only wake diagnostics API under `/v1/debug` using existing tables: latest stored paired sample/evaluation, server/day/version metadata, bounded rolling24h score/tick history with explicit paging/completeness. Publish exact models and regenerate OpenAPI/TS.
3. Reuse existing actual-wake PUT, adding typed client methods and only the fixed safe route/method authorization needed; use existing lease/cancellation/body limits and documented rate limits.
4. Extend the shared telemetry display state with bounded identity-scoped immutable latest-local and acknowledged sample/result pairs; preserve queue semantics and sample/flush deadlines.
5. Implement a testable debug controller/view-model that coalesces focused/foreground/readback requests, clears on generation change and distinguishes stale server state from queued local data.
6. Send now calls the shared `wakeRuntime.run('manual')`, then refreshes diagnostics/outbox; it does not create a new runtime or repeatedly sample sensors for “live” display.
7. Render full original rule/penalty breakdown, fixed-scale24h score history with readable textual access, explicit tick correlations/statuses, actual permission/outbox state and labeled versions.
8. Provide explicit day/timezone-labeled `HH:MM` annotation form, save/readback/error state; never infer actual wake, confirm the day or modify rules.
9. Add fixture/component/controller/transport/backend/schema tests for the edge cases; run full checks/security and actual native Simulator Send now → values/ACK/history/queue update, plus isolated annotation/readback with no owner data mutation.
10. Record precise verified/pending evidence; physical APNs/Motion/locked-phone debt remains T2.4/M2 pending. Stop at implementation, review and push gates.

## 10. Open questions

1. **Narrow backend support for the debug screen:** May T2.5 add a bounded authenticated read-only wake diagnostics API under `/v1/debug`, using existing tables for latest stored Signals/evaluation, rolling24h score/tick history and server/day/version metadata, with generated contracts and safe typed client methods, while reusing the existing actual-wake PUT? **Recommendation:** yes. The existing day endpoints cannot supply the full breakdown after restart or a genuine rolling24h/tick history. No new tables/dependencies, scoring/counter changes, settings editor or general admin API are proposed; response pagination/bounds must preserve the current32-KiB client limit.
2. **Meaning of missed ticks:** May the debug screen define an overdue tick as a recorded Expo-accepted tick with no matching accepted `silent_push` telemetry for the same device/local day/tick sequence after **60seconds**, showing newer ticks as awaiting correlation and send failures separately? **Recommendation:** yes, label it “No matching telemetry yet”/“Overdue” and explain that queued/offline/throttled events can appear later. Do not use `ticks_sent - ticks_received`, infer unsent ticks, or claim confirmed APNs delivery/force-quit. This is diagnostics only and does not change scheduling or scoring.
