## 2. Why it matters

This task is the security and data boundary for everything the pipeline reads from the internet.
`chronos/http.py` is *the* outbound-fetch guard that T3.2's fetchers and later T4.1 asset/og:image
downloads must share (docs/09: "Every fetch is wrapped by the SSRF-guarded HTTP client"; the
IP-range guard is explicitly "mandatory and tested with a fake resolver" because no hostname
allowlist is possible). If the guard is wrong, a malicious feed entry or redirect can probe the
LAN/loopback/link-local router admin from the laptop; if `max_bytes` streaming abort is wrong, a
hostile server can exhaust the 16 GB laptop's memory/disk at 6 a.m. If fetchers parse feeds
incorrectly, T3.3 (dedupe/rank) and T3.4 (script) consume garbage; if health columns are not
maintained, a dead source silently starves a category with no observability. Conditional GET keeps
the 5-minute-adjacent prewarm cheap and polite (arXiv).

## 6. Constraints

- **SSRF guard (docs/09 §2, binding)**: scheme allowlist `http`/`https` only; resolve DNS *before*
  connect and reject private/loopback/link-local/multicast/ULA ranges for IPv4 **and** IPv6;
  re-resolve and re-check on **every** redirect (max 3); resolver must be injectable so tests use a
  fake resolver. Rejection happens pre-connect — no TCP connection to a rejected address.
- **Timeouts/bytes**: per-request 15 s (yaml-configurable); `max_bytes` streaming cap (default
  2 000 000) must abort mid-stream — reading a body of `max_bytes + 1` bytes raises/aborts and must
  not buffer the whole body first (acceptance criterion 3).
- **Content-type allowlist** per use: feeds → xml/json/html (images/video allowlists are T4.1 but
  the mechanism belongs to the shared client).
- **UA string** from `sources.yaml` `http.user_agent`
  (`Chronos-AI/0.1 (+https://github.com/allenvarghese05/chronos-ai; personal morning brief)`).
- **Failure isolation**: one source failing (any reason) must not fail the ingest of the others;
  it increments `consecutive_failures` and records bounded `last_error` (docs/06 §1).
- **16 GB laptop**: feeds capped at 2 MB; concurrent fetching (if any) bounded; nothing buffered
  unboundedly; HN Algolia lookups best-effort, 5 s timeout each, and bounded in count.
- **Security scanning**: ruff `S` rules + bandit + semgrep must pass; no `shell=True`; no new deps
  without owner approval (Open question 1). Feed content is untrusted: HTML stripped, length caps,
  never logged raw, never used as filename/shell arg.
- **Timezone/time**: `last_fetched_at`, `fetched_at` use aware-UTC ISO strings via
  `chronos/time.py`; tests inject a fixed clock.
- **Tooling pins**: pyright strict, ruff line-length 100, pytest markers unchanged (no new marker
  needed; fixtures are offline). `uv.lock` must stay consistent (`--locked` in CI).
- **Coverage**: docs/12 wants ≥ 85 % on `chronos/http`; the justfile currently only measures
  `chronos.wake` (Open question 5).

## 8. Proposed approach

**Proposal (owner may veto):**

1. `chronos/http.py` — `GuardedHttpClient` wrapping one `httpx.AsyncClient`: injectable
   `resolver: Callable[[str], Awaitable[list[str]]]` (default `socket.getaddrinfo` via
   `anyio`/asyncio), `is_public_ip()` helper using `ipaddress` (`is_private`, `is_loopback`,
   `is_link_local`, `is_multicast`, `is_reserved`, v4+v6), manual redirect loop (max
   `max_redirects`) re-resolving each `Location`, streaming `aiter_bytes` with a running byte count
   that aborts past `max_bytes`, per-use `allowed_content_types`, 15 s `httpx.Timeout`. Returns a
   frozen `FetchResult`; raises a small typed `FetchError` family (`SsrfBlocked`, `TooLarge`,
   `TooManyRedirects`, `FetchFailed`) with safe messages.
2. `chronos/content/sources.py` — Pydantic `SourcesConfig`/`SourceDef` (extra-forbid) +
   `load_sources_yaml(path) -> SourcesConfig`, plus `sync_sources(session, config, now)` upserting
   `sources` rows by `key` (definition fields from YAML; runtime/health fields preserved). New
   `Settings.sources_path` defaulting to `_PROJECT_ROOT / "config" / "sources.yaml"`, mirroring
   `wake_rules_path`.
3. `services/api/config/sources.yaml` — exactly the document in docs/06 §1.
4. `chronos/content/fetchers/` — one module per kind (`rss.py`, `hf_daily_papers.py`, `arxiv.py`,
   `hackernews.py`), each `parse(source: SourceDef, body: bytes, now) -> list[ParsedItem]`; a
   shared frozen `ParsedItem` model (`external_id, url, title, summary, author, published_at,
   image_url, extra_json`). HTML stripping per docs/06 (selectolax, subject to Open question 1).
5. `chronos/content/ingest.py` — `fetch_source(client, source, config, now) -> SourceFetchOutcome`
   handling conditional GET, 304, health-column updates, failure isolation;
   `fetch_all(...) -> IngestReport` iterating enabled sources. **No** registration of an `ingest`
   handler with the worker in this task unless the owner says otherwise (Open question 3).
6. Tests: `tests/fixtures/feeds/<key>.<ext>` recorded responses + `<key>.expected.json` golden
   items for all 8 sources; fake-resolver SSRF tests (table 7 rows 1–3); `httpx.MockTransport` for
   streaming/redirect/304/content-type cases; loader validation tests; DB sync/health tests with
   temp-file SQLite. Extend `chronos config validate` to also validate `sources.yaml`
   (Open question 4) and extend the justfile coverage flags (Open question 5).

## 9. Risks

| Risk | How a test catches it |
|---|---|
| DNS-check/connect TOCTOU: host re-resolves differently at connect time (rebinding) | Fake resolver returning public-then-private across calls; assert re-resolution per request/redirect and no connect after a private answer. (Full mitigation — connecting to the resolved IP with Host/SNI pinning — is a design point the implementer must address explicitly; the docs require "DNS resolution before connect and rejection … re-checked on every redirect".) |
| `max_bytes` enforced only after full download (memory spike) | MockTransport streaming 5 MB; assert abort at cap and that the client never materialised the whole body (chunk counting). |
| Redirect check applied only to the first hop | Chain: public → public → `169.254.169.254`; assert rejection on hop 3. |
| Conditional GET silently broken (etag never stored/sent) → re-ingest duplicates | Two-pass test with recorded headers; assert second request headers and 304 path writes zero items. |
| Golden items drift from real feeds | Golden fixtures per source are the source of truth (docs/12 §1: never edit expected values to pass); CI compares parsed output byte-for-byte. |
| Failure of one source aborts the pass | One MockTransport route raising; assert other sources' items present and only the failing row's `consecutive_failures` incremented. |
| New dependency sneaks in unpinned or unapproved | pyproject diff in PR; `pip-audit`; owner gate on Open question 1. |
| Health columns updated in a long transaction alongside network I/O | Keep DB writes in short transactions after the fetch returns (T3.1 rule: no network/heavy work inside DB write transactions); test concurrency with `busy_timeout`. |
| `last_error` stores raw response text with tokens/URLs | Bounded, sanitised error strings; log/DB scan test for canary strings. |

## 10. Open questions

1. **New dependencies.** docs/06 §1 names `feedparser` (RSS/Atom parsing), `selectolax` (HTML
   stripping) and `python-dateutil` (date parsing, §2.4), but none are in `pyproject.toml`/`uv.lock`
   and the task row lists no dependencies. AGENTS.md forbids adding a dependency the task plan does
   not list. May T3.2 add exact-pinned `feedparser` and `selectolax` (and is `python-dateutil`
   approved now or deferred to T3.3 where §2.4 lives)? If no, parsing falls back to stdlib
   `xml.etree.ElementTree` + `html.parser`, which is more code and more edge-case risk.
2. **T3.2/T3.3 boundary — what is a "golden item" and does T3.2 write to `items`?** The acceptance
   criterion says "Fixture responses → golden items for all 8 sources", but canonical URL,
   `url_hash`, `title_simhash`, summary truncation and `published_at` fallback are T3.3
   (`content/normalise.py`), and the `items` table has NOT NULL `url_hash` and `title_simhash`.
   Options: (a) T3.2 produces in-memory `ParsedItem`s only (golden = parsed output) and does not
   touch `items`; (b) T3.2 also persists with a minimal canonicalisation (sha256 of the raw URL,
   simhash 0) that T3.3 later replaces. Option (a) keeps the task smaller; option (b) makes the
   M3 "Done when" (`chronos run … ingest`) reachable earlier. Which does the owner want?
3. **Source sync and job wiring.** Should T3.2 sync `sources.yaml` → `sources` table at app startup
   (mirroring `ensure_initial_version` for wake rules) and/or register a real `ingest` handler with
   the worker — or is all job/pipeline wiring deferred to T3.5, leaving T3.2 as library code +
   loader + tests only? If sync is in scope: when a key disappears from YAML, disable the row or
   delete it?
4. **`chronos config validate` / startup validation.** D29 requires YAML schema validation on
   startup and in CI. Should `chronos config validate` (and app startup) be extended in this task
   to validate `sources.yaml` the way `wake_rules.yaml` is validated today (fail fast on invalid)?
5. **Coverage gate.** May the justfile `check-api` pytest flags be extended to
   `--cov=chronos.wake --cov=chronos.http --cov=chronos.content …` with the docs/12 thresholds
   (90 % wake stays, 85 % http/content)? This extends the gate; it does not weaken any check.
