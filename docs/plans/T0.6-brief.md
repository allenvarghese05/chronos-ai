## Why it matters

T0.6 is the first task that modifies the owner's macOS laptop itself—installation, daemon lifecycle, TLS certificates, model files, and automated deployment. Mistakes here range from inconvenient (scripts fail silently, manual recovery needed) to serious (private keys world-readable, firewall misconfigured, models deleted, auto-deploy breaks the running system). The brief must enumerate every side effect so the owner can review and approve each one before implementation. The acceptance criteria are *deferred post-merge* for the third one (deployment timing) since T0.6 is self-referential: only after it merges can we verify that merging a docs PR triggers a deploy.

The task also establishes the pattern for all future launchd agents and must be correct: `com.chronos.api` (KeepAlive API server), `com.chronos.deploy` (periodic CD pull), and later `com.chronos.scheduler-tick` (if needed). The model downloads and certificate generation are one-time setup operations; idempotency is critical.

## Governing decisions

- **D16** (network): API binds to LAN IP, HTTPS with mkcert root CA installed on phone. Bearer tokens and media URLs are signed and private.
- **D19** (CD): Pull-based deployment on the laptop via launchd `com.chronos.deploy` every 10 min; fast-forward main only, never runs scripts from untrusted branches.
- **D23** (secrets): `.env` gitignored; mkcert key and API certs mode 600; no secrets in logs.
- **D30** (models): Ollama models, Kokoro ONNX, whisper ggml files under `data/models/` fetched by `just models` with pinned URLs and SHA-256 verification.
- **D09** (eager render): Prewarm at window start − 30 min; laptop must be awake by 05:25 (via `pmset repeat`); if lid closed without external display or not on power, scheduled wake fails and pipeline runs late.

## Constraints

### System constraints
- **macOS 15+ (Sequoia/Sonoma)**: `pmset`, launchd, mkcert (via Homebrew), FireWall API commands available.
- **M1 Pro 16 GB**: Model memory OK; serial worker prevents OOM.
- **LAN interface availability**: `en0` or fallback detection (`ipconfig` may need sudo for some interfaces).
- **Sudo usage**: `pmset repeat` and firewall rule changes require sudo. `mkcert -install` (adding CA to keychain) also requires sudo.
- **Lid-closed scheduling limitation**: `pmset repeat wakeorpoweron` works with lid closed **only if** an external display/keyboard is connected AND on power. Otherwise the laptop must stay open or a Mac mini is needed. `chronos doctor` warns but does not fail.

### Security constraints (docs/09-security.md §2)
- mkcert root CA key (`data/certs/rootCA-key.pem`) never leaves the laptop; root CA profile installed on phone one-time via QR or AirDrop.
- Leaf cert and key must have mode 600 (readable only by owner). Validator in Settings rejects world-readable files.
- API binds to LAN interface IP only (never `0.0.0.0`); `/metrics` endpoint to loopback only.
- Deploy script verifies commits are on `main` (via `git verify-commit origin/main` if signed; warning if not) and never runs scripts from branches.
- Model files verified by SHA-256 after download; mismatch → fail with rollback.
- `.env` and `data/certs/` are in `.gitignore`; any accidental commit is caught by `gitleaks`.

### LaunchAgent constraints (docs/10-cicd-and-ops.md §5)
- **`com.chronos.api.plist`**:
  - `ProgramArguments: [uv, run, --locked, chronos, serve]` (no shell)
  - `WorkingDirectory: services/api` (relative to repo root)
  - `KeepAlive: true` (restart if it dies)
  - `RunAtLoad: true` (start on login)
  - `ProcessType: Interactive` (prevents App Nap throttling)
  - `StandardOutPath/ErrorPath: data/logs/api.log` (structured logs go to `data/logs/api.jsonl` via structlog, but stdout/stderr captured too)
  - `EnvironmentVariables: { CHRONOS_ENV: prod, ... }` (minimal env; PATH includes Homebrew)
  - Load with `launchctl load <plist>` (or `launchctl bootstrap gui/$(id -u) <plist>` on newer macOS); unload with `launchctl unload` (or `launchctl bootout`).

- **`com.chronos.deploy.plist`**:
  - `StartInterval: 600` (run every 10 min)
  - Program: `scripts/deploy.sh` (with full path or relative to repo)
  - Same EnvironmentVariables + WorkingDirectory

### Deploy window guard (docs/10-cicd-and-ops.md §4)
- Deployments must **never** happen between window start − 45 min and window end.
  - Weekday: 05:25 − 45 min = 04:40 to window end 11:00.
  - Weekend: 07:25 − 45 min = 06:40 to window end 14:00.
- `deploy.sh` checks the current time and local day; if inside the window, log the attempt, skip, and let launchd retry 10 min later.
- Guard logic: read local date from `chronos` CLI or hardcode the window times (propose hardcoded with a comment).
- Fallback deploy still runs after window end (e.g., if the morning woke late, deploy can run at 11:01).

### CI implications
- `just models` must be idempotent (skip download if file exists and SHA matches).
- `just certs` must be idempotent (check if cert already exists before mkcert).
- `just deploy` skips the actual deploy; it's only for testing the script locally (runs on launchd, not in CI).
- Model downloads do **not** happen in CI (marked `@pytest.mark.ollama` / `kokoro` / `whisper` and deselected).

## Edge cases

1. **First run, no `.env` file**: `just laptop-setup` must create `.env` from `.env.example` with a random `CHRONOS_SECRET_KEY` (using `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`). Owner should review and set `CHRONOS_API_BIND_HOST` manually or auto-detect via `ipconfig getifaddr en0`.

2. **Hostname mismatch**: If the mDNS name changes (owner renames the Mac), the cert is no longer valid. Doctor warns; owner must re-run `just certs` to regenerate with the new hostname.

3. **Cert expired**: mkcert certs last 2–10 years by default. Doctor checks expiry; if < 30 days remaining, warn. If expired, `just certs` regenerates.

4. **LAN IP changed (DHCP renewal)**: Cert SAN includes the IP; if the IP changes, the cert is technically invalid for HTTPS but may still work if the IP is in a SAN. Proposal: pin LAN IP via DHCP reservation or use hostname only in SAN and firewall rules. Doctor checks if the current IP matches the cert SAN; warn if mismatch.

5. **Models not found**: Ollama starts but model is not loaded. `just models` must explicitly run `ollama pull qwen2.5:7b-instruct` and store the digest. Doctor checks `ollama list | grep qwen2.5` and fails if missing.

6. **whisper-cli not found**: Formula installed via `brew install whisper-cpp` (in `just setup` or `just laptop-setup`). Doctor checks `which whisper-cli`.

7. **Launchd agent fails to load**: Plist XML syntax error or directory doesn't exist. `launchctl load` fails with a cryptic error. Doctor runs `launchctl load -F <plist>` (dry-run) to catch parse errors.

8. **Deploy script runs but Git merge fails**: e.g., local commits on `main` that aren't on `origin/main`. `git merge --ff-only` fails safely; script logs and exits. Launchd retries in 10 min.

9. **Deploy happens during a morning**: If a deploy kick happens at 06:50 (inside the window), the window guard blocks it. Next scheduled kick at 07:00 is also blocked. Deploy runs at 11:01 after window end. Morning is not interrupted.

10. **Firewall rule not applied**: Manual step or `sudo /usr/libexec/ApplicationFirewall/socketfilterfw` command needed. Doctor checks `/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate` and warns if firewall is on but rule is missing.

11. **File permissions wrong**: If `data/certs/chronos-lan-key.pem` is accidentally world-readable (mode 644 instead of 600), the Settings validator rejects it and API refuses to start. Doctor checks and fails.

12. **Multiple devices on the phone**: Pairing is one-device-at-a-time (re-pairing revokes the old device). If another iPhone is paired, the owner must revoke the first before pairing a new one. Not checked in doctor (data model constraint; enforced at pairing endpoint).

13. **Repo not found or wrong path**: Deploy script uses `~/Desktop/ai_news_brief` today or reads from an env var. If the path is wrong, `git fetch` fails. Proposal: script detects its own directory and uses that as the repo root.

14. **Ollama memory pressure**: Ollama model unloaded before render to fit in 16 GB (documented in architecture §6). Worker serializes jobs. If a job exceeds memory, it fails with a clear error; retry logic handles it.

15. **Time sync off by > 5 min**: Phone sends `device_ts` with offset. If server and phone clocks are out of sync, telemetry POST returns 422 `clock_skew`. Doctor checks `systemsetup -getusingnetworktime` (may need sudo; skip if unavailable) and warns if NTP is off.

## Proposed approach

1. **Certificate setup** (`scripts/certs.sh`, ~50 lines):
   - Check if `data/certs/chronos-lan.pem` exists; if yes, skip (idempotent).
   - Run `mkcert -CAROOT` to find/create the root CA (prompts for sudo to install in keychain if first time).
   - Run `mkcert -cert-file data/certs/chronos-lan.pem -key-file data/certs/chronos-lan-key.pem <hostname>.local <IP> localhost 127.0.0.1` (SANs for both mDNS and IP).
   - Chmod 600 on key file.
   - Print instructions to the owner: "Install the root CA on your iPhone: AirDrop or scan this QR" + `python3 -m http.server 8000 --bind 127.0.0.1` + point browser to `file://data/certs/rootCA.pem`.
   - (Proposal: print cert fingerprint and validity dates; owner checks against what iOS shows.)

2. **Model downloads** (`scripts/models.sh`, ~100 lines):
   - Accept `$1 = ollama_model` and `$2 = ollama_digest` (from justfile).
   - For Kokoro: `curl -fL <url> -o data/models/kokoro/kokoro-v1.0.onnx` with progress; verify SHA256 against hardcoded hash (or a `models.lock` file).
   - For whisper: same; `data/models/whisper/ggml-small.en.bin`.
   - For Ollama: `ollama pull $1` (no SHA check since Ollama handles it); extract digest from output or `ollama list --json | jq -r '.[] | select(.name=="'$1'") | .digest'`.
   - For Remotion: `cd packages/renderer && npx remotion browser ensure` (caches Chromium).
   - Log each step; exit non-zero on checksum mismatch (fail the whole setup).
   - (Proposal: create a `scripts/models.lock` file with URLs, SHA256, sizes; commit it; first run with `--pin` writes it; later runs verify against it.)

3. **Laptop setup** (`scripts/laptop-setup.sh`, ~150 lines):
   - Create `data/logs/`, `data/models/`, `data/certs/` directories.
   - Check if `.env` exists; if not, create from `.env.example`, generate random `CHRONOS_SECRET_KEY`, prompt owner to fill in `CHRONOS_API_BIND_HOST` (auto-detect en0 with `ipconfig getifaddr en0`).
   - Call `scripts/certs.sh` (which handles sudo for mkcert).
   - Install LaunchAgents: copy plist files to `~/Library/LaunchAgents/` and run `launchctl load` (or modern `launchctl bootstrap gui/$(id -u) <plist>`).
   - Run `brew services start ollama` (if not already running).
   - Run `pmset repeat` commands (which need sudo); if no sudo access, print the commands and ask owner to run them manually.
   - Verify `launchctl list | grep com.chronos` and report status.
   - (Proposal: print a summary of changes made and paths to monitor.)

4. **Deployment script** (`scripts/deploy.sh`, ~80 lines):
   - Repo root: detect from script location (`cd "$(dirname "$0")/.."`) or read `CHRONOS_REPO` env var.
   - CD to repo; `git fetch origin main --quiet`.
   - Guard: check if `$(date +%H%M)` is inside a deploy-window exclusion range (propose a simple time check with hardcoded windows as a comment; later T1.4 can read from config).
   - If inside window: log "deploy window active, skipping"; exit 0 (let launchd retry).
   - If not in window: `git rev-parse HEAD` vs `git rev-parse origin/main`; if same, exit 0.
   - Verify: `git verify-commit origin/main` if commit signing is configured; if not, log a warning "commit signing not yet configured (open question #9)" and continue.
   - Merge: `git merge --ff-only origin/main` (fails safely if there are local commits).
   - Sync: `(cd services/api && uv sync --locked)` and `(cd packages/renderer && pnpm install --frozen-lockfile)`.
   - Migrate: `uv run --locked chronos db migrate` (idempotent).
   - Restart: `launchctl kickstart -k gui/$(id -u)/com.chronos.api`.
   - Health check: `curl -fsS --cacert data/certs/rootCA.pem https://<api_bind_host>:8443/readyz` (read host/port from `.env` or Settings); if fails, rollback: `git reset --hard <prev-commit>` + `launchctl kickstart -k ...`.
   - Log: write JSON lines to `data/logs/deploy.jsonl` with timestamp, commit SHA, status (ok/skipped/failed), error message.

5. **LaunchAgent plists** (`scripts/launchd/*.plist`, ~100 lines total):
   - `com.chronos.api.plist`: KeepAlive, runs `uv run --locked chronos serve` from `services/api/`.
   - `com.chronos.deploy.plist`: StartInterval 600, runs `scripts/deploy.sh` from repo root.
   - Both set `CHRONOS_ENV=prod` and minimal env (PATH, HOME, locale). Load via `laptop-setup.sh`.

6. **Doctor command** (`chronos doctor` in `services/api/src/chronos/cli.py`, ~300 lines):
   - **Pins**: Print Python, Node, uv, pnpm, gitleaks, semgrep versions; compare to justfile pins (warn if mismatch).
   - **Models**: Check `data/models/kokoro/*.onnx`, `data/models/whisper/ggml-small.en.bin` exist; verify SHA256 against `models.lock` or hardcoded hashes (warn if mismatch).
   - **Ollama**: `curl -s http://127.0.0.1:11434/api/tags` and check `qwen2.5:7b-instruct` is present; extract digest and compare to justfile `ollama_digest` (warn if mismatch).
   - **Certs**: Check `data/certs/chronos-lan.pem`, `data/certs/chronos-lan-key.pem` exist; verify mode 600 on key (fail if not); check expiry (warn if < 30 days); verify SAN includes current LAN IP (warn if mismatch).
   - **LaunchAgents**: Run `launchctl list | grep com.chronos` (list loaded agents); for each, verify `~/Library/LaunchAgents/*.plist` exists and is valid XML; log status (running/loaded/not-loaded).
   - **pmset schedule**: `pmset -g sched | grep -i "wake"` (look for wakeorpoweron entries matching weekday 05:25 and weekend 07:25; warn if missing or wrong times).
   - **Firewall**: `/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate` (check if on); if on, API binding IP should have a rule (manual step; doctor just warns).
   - **FileVault**: `fdesetup status` (check if on; warn if off).
   - **Disk**: `df -h ~` (check free space ≥ 2 GB; fail if < 1 GB).
   - **Database**: `sqlite3 data/chronos.db "PRAGMA integrity_check"` (check for corruption; fail if issues found).
   - **Time sync**: Skip if requires sudo; else try `systemsetup -getusingnetworktime` or a quick NTP query.
   - **Last successful morning**: Query `days` table for most recent with `state='delivered'`; print date and time.
   - **Scheduler status**: Check if `scheduler_enabled` is true in config; check for pending jobs in `jobs` table.
   - **Output format**: Structured JSONL or human-readable checklist with colours (green/yellow/red for pass/warn/fail).
   - **Exit code**: 0 if all green/yellow, non-zero if any red (blocking).

7. **Integration with existing code**:
   - Settings class already has validators for `tls_cert` mode; doctor repeats the check.
   - `chronos config validate` (T1.4 stub) stays separate from doctor.
   - Deploy script reads `.env` via `source`, or doctor can extract host/port from a query to the running API.

8. **Test coverage** (for T0.6 acceptance):
   - Scripts are bash, not tested by pytest. Acceptance tests are manual: run `just laptop-setup` on the owner's Mac; verify `launchctl list` and `curl --cacert` work.
   - Doc/PR merge test: owner creates a test PR (e.g., typo fix in `docs/`), merges to main, waits ≤ 10 min, checks `data/logs/deploy.jsonl` for a new commit SHA. Recorded in task plan as post-merge verification.

## Risks

1. **Launchd agent fails silently**: `launchctl load` succeeds but the agent doesn't actually run. **Mitigation**: Doctor checks `launchctl list -x | grep com.chronos` (dump plist) and tests with `launchctl start com.chronos.api` to trigger an immediate run.

2. **Sudo prompt during setup blocks script**: `pmset repeat` and `mkcert -install` require sudo. **Mitigation**: Offer two flows—interactive (with prompts) or manual (print commands for owner to run). Document in README.

3. **Model SHA256 mismatch on network error**: Partial download corrupts the file. **Mitigation**: Download to a temp file, verify SHA256, then move to final location. On failure, delete temp and retry.

4. **Deploy guard logic wrong**: Off-by-one hour or misses DST. **Mitigation**: Hardcode times as a comment, test with `date` during the window, verify no deploys happen. Add a test case in the log (simulate a 06:50 deploy attempt and verify it's skipped).

5. **Multiple deploy attempts race**: If `launchd` starts two `deploy.sh` instances, Git operations conflict. **Mitigation**: Use `git merge --ff-only` (atomic, safe) and a lockfile (optional: `flock data/deploy.lock`).

6. **Rollback fails**: API doesn't restart after rollback. **Mitigation**: Test rollback locally; ensure `launchctl kickstart` works even if the service is stuck.

7. **Cert/key permissions wrong after `mkcert`**: Default `umask` creates world-readable files. **Mitigation**: Explicit `chmod 600` in `certs.sh` after generation.

8. **Hostname changes post-setup**: Cert SAN no longer valid. **Mitigation**: Doctor detects mismatch; owner re-runs `just certs` to regenerate (idempotent, safe).

9. **Firewall rule not applied**: Manual step; easy to forget. **Mitigation**: Doctor warns loudly; provide the exact command (`sudo /usr/libexec/ApplicationFirewall/socketfilterfw ...`).

10. **`scripts/deploy.sh` reads wrong `.env`**: If multiple `.env` files exist (repo + home + `/etc`), Bash sources the wrong one. **Mitigation**: Explicit path in the launchd plist `EnvironmentVariables` or script sources from a fixed location.

## Proposed approach (Summary)

This task creates four scripts (`certs.sh`, `models.sh`, `laptop-setup.sh`, `deploy.sh`) and two launchd plists that together enable:
- One-time certificate generation with mkcert (mode 600, proper SANs).
- Idempotent model downloads with SHA256 verification (with a `models.lock` file or hardcoded hashes).
- Automated deployment every 10 min via a pull-based CD script that fast-forwards `main`, syncs, migrates, and health-checks.
- The API running as a user LaunchAgent (KeepAlive) on a LAN IP with TLS.
- System setup (log dirs, `.env` generation, launchd loading, pmset scheduling, Ollama service).
- A real `chronos doctor` that checks all the above and reports status.

All scripts are idempotent, handle errors explicitly, and log results. The owner reviews and approves each side effect (LaunchAgents, firewall rules, sudo commands) before T0.6 is merged.

## Side effects on the owner's Mac (explicit enumeration for approval)

### Modifications to `~/Library/`
- **Added**: `~/Library/LaunchAgents/com.chronos.api.plist` — API runs at login, restarts if killed.
- **Added**: `~/Library/LaunchAgents/com.chronos.deploy.plist` — Deploy script runs every 10 min.
- **Consequence**: Two new processes (`chronos serve`, `scripts/deploy.sh`) run in the background. Use `launchctl unload` to stop them.

### Modifications to the repo (under `data/`, which is gitignored)
- **Created**: `data/certs/` with `rootCA.pem` (2 KB, mkcert root CA) and `chronos-lan.pem` + `chronos-lan-key.pem` (certs for LAN; key mode 600).
- **Created**: `data/models/kokoro/`, `data/models/whisper/` with downloaded files (~1.4 GB total).
- **Created**: `data/logs/` where API and worker write JSON logs (rotated automatically).
- **Created or modified**: `services/api/.env` (if missing, auto-created with random `CHRONOS_SECRET_KEY`; owner should review and set bind host).
- **Consequence**: ~1.5 GB of disk space used under `data/`. `git status` will never show these files (gitignored).

### macOS system changes
- **Installed**: Root CA certificate in the System keychain (via `mkcert -install`, requires sudo). iPhone will trust the leaf cert because the root CA is installed on it.
- **Modified**: Power management via `pmset repeat wakeorpoweron` (requires sudo). Laptop will wake at 05:25 on weekdays and 07:25 on weekends (times are set once; no persistence issues).
- **Modified** (manual step): macOS firewall rule to allow incoming connections to the API on port 8443 (not automated; doctor warns with the exact command).
- **Consequence**: Laptop wakes automatically in the morning; owner cannot sleep through the morning without manually disabling the wake schedule. Laptop must stay open or have external display to wake with lid closed. Firewall rule must be applied manually.

### Services and processes
- **Ollama service**: `brew services start ollama` (user LaunchAgent, not system-wide). Ollama listens on `http://127.0.0.1:11434`. Uses ~2 GB RAM at idle, peaks at ~8 GB during model execution.
- **API service**: Listens on `<LAN-IP>:8443` (mkcert TLS). Uses ~50 MB RAM at idle; database is SQLite on disk.
- **Deployment service**: Runs every 10 min; each run is < 10 s (fast-forward, no-op if no changes).
- **Consequence**: Laptop should not sleep while the API is running (controlled by launchd KeepAlive). Scheduler also prevents sleep during render jobs (via `caffeinate -i`).

### Network and connectivity
- **Phone on the same LAN**: Must connect to the laptop's API via `https://<hostname>.local:8443` or `https://<LAN-IP>:8443`. Requires the root CA certificate installed on the phone (one-time step after `just certs`).
- **Consequence**: Phone and laptop must be on the same Wi-Fi network. API is not accessible from outside the LAN (by design, D16).

### Log files and data storage
- **Logs**: `data/logs/api.jsonl`, `data/logs/worker.jsonl`, `data/logs/deploy.jsonl` (rotated by size 50 MB or time). Kept for 14 days.
- **Database**: `data/chronos.db` (SQLite WAL mode, ~1 MB initially, grows as data accumulates).
- **Media**: `data/media/<date>/<reel-id>/reel.mp4`, etc. (24-hour retention unless saved by owner; ~100 MB per morning reel).
- **Consequence**: Regular disk usage monitoring needed. `chronos doctor` warns if free space < 2 GB.

### Secrets and credentials
- **Local**: `.env` file (gitignored, mode 600 recommended) contains `CHRONOS_SECRET_KEY` (random, sensitive). Keychain stores the mkcert root CA.
- **External**: Expo push token (optional, from the phone); stored hashed in SQLite.
- **Consequence**: `.env` file must be treated as a secret. Backup strategy should include `data/` (not committed, owner's responsibility). On laptop compromise, rotate `CHRONOS_SECRET_KEY` immediately.
