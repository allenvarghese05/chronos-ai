# T2.2 implementation plan

## Summary

An iOS pairing form accepts the laptop code or its JSON QR, explicitly confirms the HTTPS host,
and persists one device-bound Keychain session before protected navigation. A generated typed
API client refuses redirects and credentials for any other origin. Startup/foreground validation
handles revoked credentials without deleting sessions during temporary connectivity failures.
Certificate setup is honest out-of-band guidance; push setup is optional and nonblocking.

## Design

- One versioned SecureStore envelope: `{version:1, apiBase, deviceId, token}`. Validate every field
  before use; serialize storage mutations and use session generations to reject stale completions.
- Zustand vanilla store with injectable storage/client/clock, React provider and route boundary.
  Read Keychain before protected rendering; GET on startup/foreground; 401/403 invalidates once.
- `openapi-fetch<paths>` uses origin as baseUrl and generated `/v1/...` paths. Transport uses
  installed `expo/fetch`, whose SDK57 iOS `NativeResponse.swift` redirect delegate explicitly
  returns nil for redirect:error. Never use RN global fetch as a security-equivalent substitute.
- Timeout10s, bounded32KiB responses, sanitized status errors, no secret payload logs. Pair response
  must return the exact approved canonical API base and valid ULID/token before storage.
- Pure bounded QR/URL/code validation. Scanning fills a confirmation form and never submits.
- Permissions requested only on explicit action. CameraView mounts only while scanner is open;
  manual form remains available on Simulator/denial. No microphone or media permission.
- Push uses physical-device/project-ID checks, explicit permission request and genuine Expo token;
  patch with current metadata, separate failure/status from successful pairing.
- Rejected: AsyncStorage secret persistence; token/host separate keys; implicit scanned-host trust;
  RN fetch redirect assumptions; automatic Expo project creation; backend QR/fingerprint changes.

## Ordered steps and public interfaces

1. **Approved ADR and dependencies.** Record owner answers; add D34 and policy; install exact pins
   above and camera config. Verify `expo config --type prebuild` camera-only permissions and
   optional project ID (no resource creation). Commit docs/config/dependency step.
2. **Pure validation and typed transport.** Export `canonicalApiBase(value:string):string`,
   `normaliseCode(value:string):string`, `parsePairingQr(raw:string):{apiBase:string,code:string}`,
   `parseSession(value:unknown):Session`, `parsePairResponse(value:unknown, approved:string):Session`.
   Session fields match design; no response error text is surfaced. Export `ApiError` with sanitized
   message/status/retryAfterSec, `createApi(apiBase, token?, transport?)` with generated pair,
   getDevice, patchDevice, revoke methods. Tests exact/v1 joining, no pair bearer, origin/redirect
   rejection, bounded malformed responses,401/403/409/410/429, timeout. Verify tsc/Jest; commit.
3. **Session state and adapters.** Export `createSessionStore(deps)` returning Zustand store and
   hydrate/pair/validate/forget/revoke/registerPush actions. Storage get/set/remove is injected;
   state phases hydrating/unpaired/authenticated/storage-error; status/error never contain secrets.
   Storage queue + generation keeps stale hydration, reads, pairing and invalidation from altering
   newer sessions. SecureStore failure never claims saved or cleared credential. Current identity
   remains after transient GET or push errors. Tests restart, concurrent401/403, stale success and
   late old-session invalidation, failed set/delete/read, one pairing flight, retryAfter fixed clock,
   push denied/missingID/Simulator/token rotation/PATCH. Verify tsc/Jest; commit.
4. **UI and lifecycle.** Root hydrates before routes; cert route accessible unpaired; index redirects
   unpaired, pairing redirects paired; foreground validates with request deduplication. Pairing form
   shows explicit normalized host confirmation before request; scanner unmounts after first valid
   QR and never submits. Manual input retained on permission denial. Minimal home retains current
   greeting and distinguishes local forgetting from confirmed server revocation. Tests guard states,
   permissions, duplicate scan/manual path. Verify mobile lint/types/Jest/export; commit.
5. **Integration and docs.** Run just check, just security, generated-schema staleness, native
   prebuild/build and isolated HTTPS Simulator pair/restart/revoke when feasible. No real owner
   records modified; isolate acceptance DB under gitignored data. Document hardware/port limits,
   cert root vs leaf commands and optional EXPO_PROJECT_ID. Commit evidence after verification.

## Acceptance check

Code/QR pairing: parser/client/store/UI tests plus HTTPS Simulator attempt. Persistence: store
reconstruction from fake secure envelope and real Keychain process restart if Simulator available.
Revoke routes to pairing:401/403 tests and foreground startup lifecycle; manual API revocation if
isolated Simulator integration succeeds. Camera/APNs/locked-device behavior explicitly T2.4.

## Out of scope

T2.1 integration/merge, sensor Core leftovers, telemetry/outbox/wake engine, backend auth/QR changes,
SDK upgrades, unrelated audit pins, real Expo credentials/project creation, real owner DB changes.

## Review focus

Transport redirect handling, exact origin+v1 binding, secure queue/session races, clear-vs-storage
failure semantics, camera/microphone scope, no code/token leakage, D34 approved accessibility.

## Device checklist (T2.4)

Install a signed iPhone build when available; trust public mkcert root over a trusted channel;
scan laptop pairing QR and confirm host; restart app and verify stored session; revoke from laptop
and foreground app; verify locked cold start after first unlock; notification registration with
configured project/APNs; no physical camera/APNs validation claimed in T2.2 Simulator evidence.
