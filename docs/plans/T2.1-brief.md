**Size:** L

---

## Why it matters

T2.1 implements the core signal-sampling layer that the wake engine depends on. Every morning, the iOS app must query CoreMotion history and device state (battery, lock status, app foreground) and post that data to the backend within ~30 seconds of being woken (silent push or background refresh). Without T2.1:

- The app cannot read step counts or motion-activity history (pedometer always returns 0 or unavailable).
- The backend cannot decide if the owner is awake (all signals are missing).
- Background refresh registration fails; the app never runs in the background.
- T2.3 (telemetry sampler) and T2.4 (wake handling) cannot proceed.

Correctness is critical: the duration summation from CoreMotion's change-point API (unsorted, possibly overlapping the query range, with multiple activity types per sample) is the most error-prone part. A bug here → consistent false negatives (score always too low) or false positives (wake at 3 a.m.). Tests must cover edge cases (empty activity list, range longer than CoreMotion's 7-day limit, samples with no dominant activity).

## Inputs and outputs

### Inputs

1. **From CoreMotion (C APIs):**
   - `CMPedometer.authorizationStatus()` → enum `.authorized`, `.denied`, `.restricted`, `.notDetermined`
   - `CMPedometer.isStepCountingAvailable` → bool (false on simulator)
   - `CMPedometer.queryPedometerData(from:to:withHandler:)` → `(CMPedometerData?, Error?)` containing `numberOfSteps` and `distance` (in meters, as float)

## Edge cases

Each with a concrete input and expected outcome:

1. **Query range: from > to**
   - Input: `querySteps(toMs=100, fromMs=200)`
   - Expected: Reject with "Invalid range" or similar error; clamp internally to from ≤ to
   - Test: `ActivitySummariser.durations([...], from=100, to=50)` → error or zero duration

2. **Query range longer than 7 days (CoreMotion limit)**
   - Input: `queryActivity(from, to)` where `to − from > 7 * 24 * 3600_000` ms
   - Expected: Clamp to 7 days; or CoreMotion rejects with error → propagate as "query_too_long"
   - Test: Call with 10-day range; verify CoreMotion error is handled gracefully

3. **Empty activity list**
   - Input: `queryActivityStarting(from:to:to:withHandler:)` returns empty array
   - Expected: All durations = 0; `walkingConf` = "low" (no walking samples to extract confidence from)
   - Test: `ActivitySummariser([], from, to)` → `{ walking: 0, running: 0, ..., walkingConf: "low" }`

4. **Activity list's first sample starts after `from`**
   - Input: Activities: `[{start: from+30s, stationary}, {start: from+60s, walking}]` for a range `[from, to]`
   - Expected: The first sample's duration is `60s − 30s = 30s`; the person was in the activity from start until the next sample; activity in effect at `from` is NOT included (CoreMotion only returns activities starting from `from` or after)
   - Test: `ActivitySummariser([{start: from+30s, ...}], from, to)` → duration includes the gap correctly
   - **Note:** CoreMotion docs state it returns activities "starting from" `from`; if an activity in progress before `from` is included, adjust logic

5. **Clamping: activity sample's startDate is before `from` but present in result**
   - Input: CoreMotion returns `[{start: from−10s, walking}]` (edge case if CoreMotion includes the ongoing activity)
   - Expected: Clamp the duration start to `from`; duration = `min(next.start, to) − max(start, from)`
   - Test: `ActivitySummariser([{start: from−10s, ...}], from, to)` → duration uses `max(from−10s, from) = from`

6. **Multiple boolean flags true in one sample**
   - Input: `CMMotionActivity(walking=true, stationary=true, confidence=high)` (unusual but possible)
   - Expected: Apply precedence: automotive > cycling > running > walking > stationary > unknown; pick the first true flag in order
   - Test: `ActivitySummariser([{walking: true, stationary: true, ...}])` → count as walking only

7. **Walking confidence maxed over mixed samples**
   - Input: Two walking samples: `{walking: true, conf: low}`, `{running: true, conf: high}`
   - Expected: `walkingConf` = "high" (max over walking + running samples, since running is a subset of walking)
   - Test: Verify the confidence extraction is the max, not the first

8. **Battery level −1 (unavailable)**
   - Input: `UIDevice.current.batteryLevel` is −1.0 (not set or disabled)
   - Expected: `batteryLevel: null` in the result
   - Test: `DeviceStateMapper(batteryLevel: −1)` → result has `batteryLevel: nil`

9. **Battery state unknown**
   - Input: `UIDevice.current.batteryState` is `.unknown`
   - Expected: Map to string `"unknown"` (not skipped or treated as unplugged)
   - Test: Verify all four states map correctly: `unknown`, `unplugged`, `charging`, `full`

10. **App in background**
    - Input: `UIApplication.shared.applicationState` is `.background`
    - Expected: `appState: "background"` (not "inactive")
    - Test: Mock `applicationState` to `.background` and verify the string output

11. **Protected data unavailable (phone locked)**
    - Input: `UIApplication.shared.isProtectedDataAvailable` is false
    - Expected: `isUnlocked: false`
    - Test: Call `deviceState()` when phone is locked (or mock the value)

12. **Low Power Mode enabled**
    - Input: `ProcessInfo.processInfo.isLowPowerModeEnabled` is true
    - Expected: `lowPowerMode: true`
    - Test: Enable LPM and verify the flag is set

13. **Timezone change mid-day**
    - Input: `TimeZone.current.identifier` changes from "America/New_York" to "Europe/London" between two calls
    - Expected: Each `querySteps`/`queryActivity` call uses the current timezone at that moment; no caching
    - Test: Not directly testable in T2.1 (depends on system state); document as a known behaviour

14. **`requestMotionPermission` on already-authorized device**
    - Input: Call `requestMotionPermission()` when authorization is already `.authorized`
    - Expected: Completes successfully (the 1-minute query runs without prompting again)
    - Test: Verify promise resolves; no error thrown

15. **`requestMotionPermission` on denied device**
    - Input: User taps "Don't Allow" on the motion permission prompt; call `requestMotionPermission()` again
    - Expected: The query fails with "pedometer_unavailable" or similar; promise resolves (doesn't reject); JS wrapper shows permission prompt
    - Test: Mock `authorizationStatus` to `.denied` and verify the query is rejected

16. **`pedometerAuthorization` when never requested**
    - Input: App is fresh, never called `requestMotionPermission()`; call `pedometerAuthorization()`
    - Expected: Returns `"not_determined"` (iOS hasn't prompted yet)
    - Test: Verify the status matches the enum value exactly

17. **Background refresh registration with wrong identifier**
    - Input: `registerBackgroundRefresh("wrong.identifier")` (not matching `app.config.ts` `BGTaskSchedulerPermittedIdentifiers`)
    - Expected: BGTaskScheduler may reject or silently not register; iOS will not wake the task
    - Test: Register with the correct identifier; verify the event fires on device (T2.4)

18. **`completeBackgroundRefresh` called without a pending task**
    - Input: `completeBackgroundRefresh(true)` is called when no task is in progress (or already completed)
    - Expected: No-op or error (implementation detail); should not crash
    - Test: Verify idempotent behaviour; multiple calls do not cause errors

19. **Query range is 0 seconds**
    - Input: `querySteps(now, now)` (from === to)
    - Expected: Both from and to are the same instant; any step at exactly `now` may or may not be included (depends on CoreMotion); durations are all 0
    - Test: `ActivitySummariser([], from, from)` → all zeros

20. **Pedometer availability changes between calls**
    - Input: First call: `isStepCountingAvailable === true`, second call: false (e.g., app backgrounded and system resets pedometer state)
    - Expected: First call returns steps; second call rejects with "pedometer_unavailable"
    - Test: Cannot easily reproduce; document as a graceful error path

## Proposed approach

**Shape of the solution (10–15 lines, not implementation details):**

1. **Pure-Swift core (in a separate SwiftPM package or plain Swift files):**
   - `ActivitySummariser` — takes an array of `CMMotionActivity` changes, clamped `[from, to]` range; returns durations per activity type and max walking confidence
   - `DeviceStateMapper` — takes UIDevice/UIApplication/ProcessInfo values and returns the JSON-serializable dictionary with proper type mapping (enum → string, nil handling)
   - Both are `@MainActor`-free, fully testable with Swift test without needing ExpoModulesCore

2. **Expo module wrapper (`ChronosSensorsModule.swift`):**
   - `pedometerAuthorization()` — wraps `CMPedometer.authorizationStatus()`; returns enum as string
   - `requestMotionPermission()` — makes a 1-minute `queryPedometerData` call to trigger the prompt; resolves when done
   - `querySteps(fromMs, toMs)` — calls `CMPedometer.queryPedometerData(from:to:)`; rejects with "pedometer_unavailable" if `!isStepCountingAvailable`; returns `{ steps, distanceM }`
   - `queryActivity(fromMs, toMs)` — calls `CMMotionActivityManager.queryActivityStarting(from:to:to:)`; uses `ActivitySummariser` to compute durations; returns the summary dict
   - `deviceState()` — calls `DeviceStateMapper(UIApplication, UIDevice, ProcessInfo)` on main thread; returns the dict synchronously
   - `registerBackgroundRefresh(identifier)`, `scheduleBackgroundRefresh(identifier, earliestInSec)`, `completeBackgroundRefresh(success)` — wrappers around `BGTaskScheduler`; emit "backgroundRefresh" events
   - Use Expo Modules API's `AsyncFunction` / `Function` / `Events` DSL

3. **XCTest harness:**
   - Option A (recommended): Create a SwiftPM package at `apps/mobile/modules/chronos-sensors/ios/ChronosSensorsCore` with `Package.swift`, test target, and pure-logic tests; run via `swift test --package-path ...`
   - Option B: Add an XCTest target to the generated Xcode workspace and test the Expo module directly with mocked CoreMotion protocols; run via `xcodebuild test`
   - T2.1 proposes Option A (simpler, no Xcode workspace dependency; `scripts/ios-test.sh` runs `swift test`)

4. **Mock protocols (for XCTest):**
   - `StepQuerying` protocol: `queryPedometerData(from:to:completion:) → (CMPedometerData?, Error?)`
   - `ActivityQuerying` protocol: `queryActivityStarting(from:to:to:completion:) → ([CMMotionActivity], Error?)`
   - Inject fakes into `ActivitySummariser` for testing without CoreMotion

5. **TypeScript bridge updates (`src/index.ts`):**
   - Extend `ChronosSensorsModuleType` interface with the new functions
   - Update `isModuleNotFoundError()` to re-verify the match string against expo-modules-core 57
   - Keep the fallback stub for Jest/Expo Go

6. **Background refresh registration via AppDelegateSubscriber:**
   - Update `expo-module.config.json` to declare an `AppDelegateSubscriber` (Expo modules can auto-register subscribers)
   - The subscriber's `applicationDidFinishLaunching()` hook calls `ChronosSensorsModule.registerBackgroundRefresh()` with the identifier from `app.config.ts`
   - Add an assertion/test: verify the identifier in Swift matches the plist constant

7. **Test coverage:**
   - `ActivitySummariser`: unit tests for duration math (clamping, change-point deltas, confidence max)
   - `DeviceStateMapper`: unit tests for enum mapping and nil handling
   - Integration test: mock a CoreMotion query and verify the full pipeline returns the correct JS dict

8. **`scripts/ios-test.sh`:**
   - Bash script that runs `swift test --package-path apps/mobile/modules/chronos-sensors/ios/ChronosSensorsCore`
   - Optional: add a smoke build of the app on the simulator to verify the module still links after changes
