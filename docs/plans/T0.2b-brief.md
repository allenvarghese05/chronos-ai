# T0.2b Brief: Deterministic expo-doctor in CI (hotfix)

## Task

**ID:** T0.2b
**Title:** Deterministic expo-doctor in CI
**Size:** S
**Dependencies:** T0.4 (versions governed by the SDK; see T0.4 owner answers)
**Acceptance criteria:**
- `just check-mobile` passes locally and in CI even when Expo publishes SDK patches
- CI job `mobile` remains required; no weakening of checks
- `expo-doctor` version check passes deterministically (no live registry consulted)
- Weekly advisory in `audit.yml` reports current vs. recommended Expo package versions
- ADR D32 records the policy: "Expo SDK pins are bumped deliberately in tasks; CI never consults live registries for pass/fail"

---

## Why it matters

The `mobile` job in CI runs `pnpm exec expo-doctor`, which by default consults Expo's LIVE SDK-57 manifest and fails if any pinned package is behind the latest patch. When Expo publishes patches (e.g., 57.0.28, 57.0.20, 57.0.26, 57.0.6) after T0.4 is completed, `main` and every PR fail **without any code change**—violating the principle that CI should be deterministic (only our repo's content decides pass/fail).

**Current state (2026-10-06 after T0.4):**
- `apps/mobile/package.json` pins: `expo@57.0.27`, `expo-dev-client@57.0.19`, `expo-router@57.0.25`, `jest-expo@57.0.5`
- `pnpm exec expo install --check` outputs the current Expo SDK-recommended versions: ~57.0.28, ~57.0.20, ~57.0.26, ~57.0.6
- `pnpm exec expo-doctor` exits non-zero with: `"packages match versions required by installed Expo SDK"` fails

**Without T0.2b:**
- CI is flaky (passes when no Expo patches exist, fails when they do)
- The team cannot distinguish real breakage from Expo registry changes
- Lock-step dependency pins (the foundation of D18 + D19) break because live data decides pass/fail
- Every Expo patch triggers "fix CI" work before any task can proceed

**Why making the check deterministic is NOT weakening it:**
- The current check (consulting Expo's live manifest) is a **linting recommendation**, not a correctness check. It flags "you're not on the latest patches" but does not catch genuinely wrong pins (outside the SDK's supported range).
- We replace live-registry consultation with a **deterministic, commit-pinned policy**: Expo pins are bumped deliberately in tasks (e.g., as part of T0.4, or a future T2.5 refactor). We never auto-sync to patches; we decide when to upgrade.
- **Visibility is preserved**: A weekly informational step in `audit.yml` prints the current vs. recommended versions so drift is never silently forgotten. When a decision is made to bump pins, the task plan and PR record it as a deliberate choice.
- **Genuine mistakes are still caught**: A pin outside the SDK's supported version range (e.g., `expo@56.x` when SDK is 57) will fail at build time (during `expo export --platform ios` or `expo prebuild`), proving the check's real value.

## Current state

**expo-doctor 1.20.4 configuration surface:**

The tool has **no configuration file** (no `.expo-doctor.json`, no `expo.doctor` in `package.json`). Its behavior is controlled entirely by environment variables. Query: `pnpm exec expo-doctor --help` shows only `-h`, `-v`, `--verbose`, no options to disable checks.

**Environment variables (from `node_modules/expo-doctor/build/utils/env.d.ts`):**

| Variable | Type | Purpose | Affects our case? |
|---|---|---|---|
| `EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK` | boolean | "Allow disabling InstalledDependencyVersionCheck" | **YES** — when set to `1` or `true`, the tool skips the version check that consults the live manifest |
| `EXPO_DOCTOR_ENABLE_DIRECTORY_CHECK` | boolean \| null | "Opt in to ReactNativeDirectoryCheck" | No — not relevant to version drift |
| `EXPO_DOCTOR_WARN_ON_NETWORK_ERRORS` | boolean | "If a test makes an online check and failures due to a network error, don't count it as failing the overall doctor check" | No — would hide real network errors |
| `CI` | boolean | "Is running in non-interactive CI mode" | No — already set in CI by GitHub Actions |
| `EXPO_DEBUG` | boolean | "Enable debug logging" | No — not needed |

**No package.json exclusion mechanism:**

Searching `node_modules/expo-doctor` and Expo SDK 57 docs finds **no `expo.install.exclude` field or similar** that would exclude packages from the version check. The check hardcodes the SDK's dependency set and compares pinned versions against it.

**Behavior of `expo install --check` (read-only command):**

```
$ cd apps/mobile && pnpm exec expo install --check
The following packages should be updated for best compatibility with the installed expo version:
  expo@57.0.27 - expected version: ~57.0.28
  expo-dev-client@57.0.19 - expected version: ~57.0.20
  expo-router@57.0.25 - expected version: ~57.0.26
  jest-expo@57.0.5 - expected version: ~57.0.6
Your project may not work correctly until you install the expected versions of the packages.
Found outdated dependencies
```

- Exit code: 1 (fails)
- Exit code would be 0 if all versions matched the "expected" tilde-range
- The "expected" versions come from Expo's live registry (SDK-57 manifest) at query time
- `expo install --fix` would bump the packages to the expected versions (atomic, writes to `package.json` and `pnpm-lock.yaml`)
- `expo install --check` is read-only and intended for auditing

**Exact current SDK-recommended versions (as of 2026-10-06 after Expo published patches):**

| Package | Pinned | Recommended | Delta | Notes |
|---|---|---|---|---|
| expo | 57.0.27 | ~57.0.28 | patch | SDK publishes 57.0.28 during T0.4 |
| expo-dev-client | 57.0.19 | ~57.0.20 | patch | SDK publishes 57.0.20 during T0.4 |
| expo-router | 57.0.25 | ~57.0.26 | patch | SDK publishes 57.0.26 during T0.4 |
| jest-expo | 57.0.5 | ~57.0.6 | patch | SDK publishes 57.0.6 during T0.4 |

**Files and commands affected:**

- `justfile` recipe `check-mobile`: line `pnpm exec expo-doctor` — this invocation fails if the env var is not set
- `.github/workflows/ci.yml` job `mobile`: step `just check-mobile (biome, tsc, jest, expo-doctor, expo export)` — this step fails when `expo-doctor` exits non-zero
- `.github/workflows/audit.yml` job `audit`: currently has a separate informational step that runs `pnpm audit` for JS but **does not currently** run `expo install --check` for SDK drift visibility

**How local and CI currently differ (root cause):**

- Developer runs `just check-mobile` locally with no special env vars → `expo-doctor` consults live manifest → check passes if dev machine has fetched recent packages, fails if Expo published patches before dev machine fetched them → **non-deterministic**
- CI runs `just check-mobile` on ubuntu-latest → same non-determinism
- Solution: set `EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK=1` **in the justfile recipe** (shared by local and CI) so both skip the live-manifest check consistently

## Constraints

| Constraint | Impact |
|---|---|
| **Deterministic CI (D18, D19)** | `EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK` must be set consistently in both local (`justfile`) and CI (inherited from recipe). Cannot be set only in CI (would break local consistency). |
| **No config file, only env var** | expo-doctor 1.20.4 does not support a `.expo-doctor.json` or `package.json` config field; env var is the only mechanism. If expo-doctor adds config support in a later version, this can be revisited. |
| **Version drift must remain visible** | The weekly audit step is mandatory; cannot simply remove the visibility of drift. If the advisory is ignored repeatedly, a future decision might escalate it to a failing check (but that would re-introduce flakiness unless tied to a task plan). |
| **Genuine build failures must still fail** | If a pin is truly outside the SDK's range (e.g., `expo@56.0.0` when SDK is 57), the check `expo export --platform ios` or `expo prebuild` will fail during that step. The deterministic version check we skip is **not** the only safeguard. |
| **No weakening of security or quality checks** | D22 governs security scans; this brief only affects a linting signal. Removing the check from CI is acceptable because the check is not a correctness gate; a weekly advisory replaces it. |

## Edge cases

1. **Expo publishes a patch with a breaking change (e.g., 57.0.28 breaks iOS builds).**
   - Input: Expo SDK 57 publishes 57.0.28 with a regression. We skip the version check in CI. A developer bumps pins to 57.0.28 in a task.
   - Expected: The task's test step (local `just check-mobile` or CI `expo export --platform ios`) catches the build failure. The task is fixed or pins are reverted.
   - Safety: The skip env var does not hide the failure; it only hides the "you're behind" advisory.

2. **A developer manually edits `package.json` to an invalid Expo version outside the SDK range (e.g., `expo@56.0.0`).**
   - Input: `apps/mobile/package.json` has `"expo": "56.0.0"` but `expo-modules-core` expects SDK 57.
   - Expected: `pnpm install` may succeed (fetching expo 56), but `just check-mobile` fails at `pnpm exec expo export --platform ios` with a clear error about incompatible SDK.
   - Safety: The skipped version check is not the primary safeguard here; build failures are.

3. **CI passes with `EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK=1` but local `just check-mobile` fails.**
   - Input: Developer runs `just check-mobile` locally with an outdated env from an old terminal session that somehow unsets the env var.
   - Expected: Recipe script sets the env var explicitly, so this should not happen. If it does, the discrepancy is visible (local fails, CI passes), and the developer checks the recipe and resets their env.
   - Test: Run `unset EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK && just check-mobile` locally; it should still pass because the recipe sets it.

4. **A minor-version drift in Expo packages (e.g., developer has `expo@57.0.28` locally but `package.json` pins `57.0.27`).**
   - Input: `apps/mobile/pnpm-lock.yaml` has `expo@57.0.28` (fetched before the commit) but `package.json` pins `57.0.27`.
   - Expected: `pnpm install --frozen-lockfile` in CI will fail because the lockfile does not match `package.json`. This is a CI safeguard independent of expo-doctor.
   - Safety: Lockfile validation catches this; the skipped expo-doctor check is not relied upon.

5. **Developer runs `pnpm exec expo install --fix` locally, intending to bump pins, but commits the change without a task plan.**
   - Input: `apps/mobile/package.json` is edited to `57.0.28, 57.0.20, 57.0.26, 57.0.6`; committed without a task plan or decision record.
   - Expected: The PR review catches the unexpected change. The brief records that bumps must be deliberate; unplanned changes should be questioned.
   - Safety: Code review and CI do not prevent this, but D32 records the policy so reviewers can enforce it.

6. **Expo SDK 57 is skipped (SDK 58 is released, but we do not upgrade yet); SDK 57 patches keep arriving.**
   - Input: We remain on Expo SDK 57 with pinned versions; the weekly audit reports drift against SDK-57 manifest.
   - Expected: The weekly audit continues to show "expo@57.0.27 → 57.0.35" (hypothetical). The team decides whether to bump within SDK 57 or upgrade to SDK 58. Either way, it is deliberate.
   - Safety: No degradation; the advisory is informational.

## Proposed approach

1. **Identify the root cause:** expo-doctor 1.20.4 checks pinned versions against Expo's live SDK manifest; when patches are published, CI fails without code changes, violating determinism.

2. **Choose the mechanism:** Use `EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK=1` environment variable (confirmed to exist in expo-doctor 1.20.4) in the `justfile` recipe `check-mobile`. This:
   - Applies to both local and CI runs (consistency)
   - Removes the non-deterministic live-registry check
   - Does NOT hide real build failures (expo export, prebuild still validate)
   - Requires one line added to the recipe

3. **Add weekly visibility:** Extend `.github/workflows/audit.yml` with a new informational step after the `security-web` step that runs `expo install --check` and logs the drift report. Make it non-failing (exit 0) so the audit workflow is informational.

4. **Record the policy:** Create `docs/decisions/D32-expo-pins-policy.md` documenting:
   - Why the check is skipped (determinism, not correctness)
   - How drift is made visible (weekly advisory)
   - When pins are bumped (deliberately, as part of task plans)
   - Trade-offs of the three options

5. **Optional: Bump pins now** (if decision is yes):
   - Edit `apps/mobile/package.json` to the current SDK-recommended versions (57.0.28, 57.0.20, 57.0.26, 57.0.6)
   - Run `pnpm install` to update the lockfile
   - Commit as `chore(mobile): bump Expo SDK patches to current SDK-57 recommendations`
   - Include this commit in T0.2b

6. **Test locally and in CI:**
   - Run `just check-mobile` locally; should pass with the env var set in the recipe
   - CI job `mobile` should pass without additional changes (inherits the recipe)
   - Weekly audit should print the drift advisory without failing

## Open questions

1. **Should Expo pins be bumped NOW (T0.2b) as a one-off, or left as-is and bumped later in a deliberate task?**
   - Recommended: Yes, bump now to 57.0.28, 57.0.20, 57.0.26, 57.0.6. This eliminates immediate drift and aligns with SDK-57 at the moment T0.2b is complete. The env var skip remains so future patches do not re-introduce CI flakiness.
   - Alternative: No, leave as-is. The env var skip handles future flakiness; bumping can wait for a task that needs new Expo features.

2. **Should the weekly audit advisory be visible in the workflow run, or sent as a push notification to the owner?**
   - Recommended: Visible in the workflow run log (current proposal). It is searchable and does not spam notifications.
   - Alternative: Send a daily/weekly push via `POST /v1/admin/notify` (would require T5.2 infrastructure). More intrusive; only if drift is discovered to be a blocker.

3. **If Expo publishes a patch that actually breaks the build, how should the team respond?**
   - Recommended: A task explicitly pinning an older patch version is added to the plan. The fix is recorded in the task so it is not accidental. Example: task description: "T2.5b: Pin expo 57.0.28 due to regression in 57.0.29 (see Expo SDK issue #XXXX)."
   - Alternative: Use a patch override in `pnpm-lock.yaml` or `.npmrc`. Less transparent; less preferred.

4. **Should local developers have the option to opt-in to the strict version check (e.g., `EXPO_STRICT=1 just check-mobile`)? Or is the skip always applied?**
   - Recommended: Always skip (the recipe sets it unconditionally). If a developer wants to see the drift advisory, they can run `pnpm exec expo install --check` manually.
   - Alternative: Add a flag (adds complexity; probably unnecessary).

## Summary

**T0.2b fixes a CI flakiness problem introduced by Expo's live-registry version checks.** By skipping the check via an env var in the `justfile` recipe and adding a weekly informational advisory in `audit.yml`, we preserve determinism (core principle of D18/D19) while keeping version drift visible. An ADR D32 records the deliberate policy: Expo pins are bumped only as part of task plans, never automatically. The skip env var does not hide real build failures (expo export, prebuild still validate).
