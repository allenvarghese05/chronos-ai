# T1.4 Brief: Rules loader `wake/rules.py`

## Task

**ID:** T1.4
**Title:** Rules loader `wake/rules.py`: `WakeRules` schema, YAML load, DB override, versioning, `chronos config validate`, `GET/PUT /v1/config/wake`
**Size:** M (≈ 1 day)
**Depends:** T1.1 (tables: `rule_versions`, `settings`)
**Acceptance criteria** (from the plan):
1. Invalid YAML (cap < max points) rejected with field path.
2. PUT creates version n+1 and activates atomically.
3. Previous versions retained.

---

## Why it matters

T1.4 **delivers the schema and lifecycle for all wake-engine configuration**. It controls:

- **Scoring rules** (D06): every evaluation depends on rules being valid, loaded, and versioned so the owner can replay and tune.
- **Startup safety** (D29): rules are schema-validated on app startup; invalid config is rejected before the first evaluation.
- **Tuning workflow** (docs/03 §7): the owner can call `PUT /v1/config/wake` on the app's debug screen to override rules; a new version is created atomically and takes effect immediately.
- **Replay and debugging** (docs/01 §6 + D06): stored evaluations reference a `rule_version_id`, so the owner can `chronos wake replay --from 2026-10-01 --to 2026-10-14 --rules <file>` to see what would have happened under old or new rules.

**If T1.4 is wrong:**
- Invalid rules pass startup → scoring engine crashes or produces inconsistent results → morning workflow breaks.
- Rules do not version correctly → multiple `active=1` rows or version gaps → `effective_rules()` returns stale or ambiguous rules → same morning as above.
- PUT is not atomic → a partial rule update is applied → scores are unpredictable.
- Canonical JSON SHA is computed wrong → replay shows the wrong version as identical when it is not, or vice versa.
- Field paths in error responses are absent → the owner cannot debug which rule is invalid without reading the full traceback.

## Governing decisions

| ID | Binding constraint |
|---|---|
| D06 | **Scoring**: rules in `config/wake_rules.yaml` with a DB override; every evaluation stored with full breakdown. Rules are immutable per version; a new override creates a new version in the DB. |
| D29 | **Config**: Pydantic Settings with `CHRONOS_` prefix; YAML for rules/sources; schema-validated on startup; `chronos config validate` in CI. YAML is the source of truth; DB rows override at runtime. |

## Inputs and outputs

### Input: YAML file `services/api/config/wake_rules.yaml` (source of truth)

The complete v1 spec (from docs/03-wake-engine.md §4), with exact semantics:

```yaml
version: 1
window:
  weekday: { start: "06:00", end: "11:00" }
  weekend: { start: "08:00", end: "14:00" }
  day_boundary: "03:00"
  holidays_as_weekend: []        # optional; ISO dates like "2026-12-25"
  tick_interval_min: 5
thresholds:
  confirm: 70                    # score ≥ confirm on 2 consecutive ticks → confirmed
  strong: 85                     # score ≥ strong on 1 tick → confirmed
  dedupe_min: 2                  # ignore 2nd snapshot < 2 min after last (same wake)
rules:
  - id: steps_10m
    signal: steps_10m
    points: [[35, 30], [20, 18], [10, 8]]     # [threshold, points]; first match wins
    cap: 30
  - id: walking_10m
    signal: walking_sec_10m
    points: [[60, 20], [30, 12]]
    requires: { walking_conf: [medium, high] } # optional; enum constraint
    cap: 20
  - id: unlocked
    signal: is_unlocked
    points: [[true, 15]]
    bonus_consecutive: { ticks: 2, points: 10 }  # optional; bonus if true for 2+ ticks
    cap: 25
  - id: charger_disconnect
    signal: charger_disconnected                 # server-derived; not in telemetry
    points: [[true, 15]]
    cap: 15
  - id: steps_window
    signal: steps_since_window
    points: [[100, 5]]
    cap: 5
  - id: foreground
    signal: wake_source
    points: [["foreground", 40]]  # enum value match
    cap: 40
penalties:
  - id: stationary_dominant
    when: { stationary_sec_10m: ">= 540", steps_10m: "< 10" }  # mini-language for conditions
    points: -20                   # penalty (negative)
  - id: pedometer_denied
    when: { pedometer_auth: ["denied", "restricted"] }         # list = "any of"
    points: 0
reweight_without_pedometer:  # if pedometer unavailable, scale these to keep max ≤ 100
  unlocked: 35
  charger_disconnect: 30
  foreground: 40
```

**Semantics:**
- `window` is a `WindowConfig` (frozen pydantic from T1.3): `weekday_start/end`, `weekend_start/end` are `HH:MM` strings (converted to `datetime.time`), `day_boundary` is optional (default 03:00), `holidays_as_weekend` is optional list of ISO date strings.
- `thresholds`: `confirm` (≥ on 2 consecutive ticks), `strong` (≥ on 1 tick), `dedupe_min` (minutes).
- `rules` list: each rule has `id` (unique), `signal` (from signal set or server-derived), `points` (list of `[threshold, points]` rows; first satisfied wins; `>=` for numbers, `==` for bool/enum), `cap` (max points), optional `requires` (enum constraints), optional `bonus_consecutive` (bonus for N consecutive ticks).
- `penalties` list: each has `id`, `when` (condition map), `points` (negative or zero).
- `reweight_without_pedometer` map: keys are rule IDs; values are replacement weights if pedometer unavailable.

## Constraints

### Security and validation (from docs/09-security.md §2)

**Input validation for WakeRules:**
- **Weights ≥ 0**: all point values (rule points, bonus, penalty) must be non-negative. Exception: penalties can be negative (e.g., -20).
- **Caps ≥ max achievable points**: for each rule, `cap ≥ points[0]` (first/max threshold). Globally, the sum of all caps (excluding foreground, or including depending on the rule) must equal or exceed 100 when fully satisfied. (See edge case #1 and open Q#2.)
- **Thresholds ∈ [1, 100]**: `confirm`, `strong`, `dedupe_min` must be in valid ranges.
- **Window constraints** (from T1.3, enforced by `WindowConfig` validation):
  - `weekday_start < weekday_end`
  - `weekend_start < weekend_end`
  - `tick_interval_min ∈ [2, 30]`
- **Penalties `when` conditions**: must parse correctly (see open Q#3).
- **Reweighting**: keys in `reweight_without_pedometer` must refer to existing rule IDs; reweighted sum must be ≤ 100. (See open Q#10.)

**No SSRF, no remote loading:**
- YAML is read from a local file only (`services/api/config/wake_rules.yaml`).
- No HTTP calls to download rules.
- No shell execution of rule content.

### Pydantic strictness

- **`extra="forbid"`** on every model (`WakeRules`, `Rule`, `Penalty`, `Thresholds`, `WindowConfig`): unknown fields in YAML or API requests raise a 422 error with field paths.
- **Type coercion**: minimal; types are strict (int, str, bool, list). YAML parser coerces `06:00` to string; T1.3's `WindowConfig` converts `HH:MM` strings to `datetime.time` via Pydantic.

### Atomicity and consistency

- **Activation is atomic**: a `PUT /v1/config/wake` must:
  1. Validate the rules document (raise 422 if invalid; no DB writes).
  2. Compute `version = max(version) + 1` (under a transaction).
  3. Compute canonical JSON SHA-256 (deterministic: `json.dumps(..., sort_keys=True, separators=(',', ':'))`).
  4. Insert a new `rule_versions` row with `active = 0`.
  5. **Atomically**: `UPDATE rule_versions SET active = 0 WHERE active = 1; UPDATE rule_versions SET active = 1 WHERE id = (new row id)` in a single transaction.
  6. Return the new version.
- **Partial unique index**: the partial unique constraint `(active) WHERE active = 1` guarantees exactly one active row.

### Caching and state (single-process API)

- **In-memory cache** of the currently active rules: `_effective_rules: Optional[WakeRules]` module variable + `effective_rules() -> WakeRules` function. Cache is invalidated on `PUT /v1/config/wake` (set to None; re-fetch from DB on next call).
- **Startup**: on app startup:
  1. If no `rule_versions` row with `active = 1`: load YAML, validate, insert version 1 `source="yaml"`, set `active = 1`, cache it.
  2. If a row with `active = 1` exists: load it, cache it; do NOT reload the YAML file (unless explicitly asked by `chronos config apply-yaml`).
  3. If YAML file changed since the active version was sourced from YAML: log a warning (not fatal); expose `yaml_sha` in GET response so the owner can see the mismatch.

### Rate limiting

- `require_device` dependency applies the default rate limit (120 req/min per IP).

## Proposed approach

### Module structure

**`services/api/src/chronos/wake/rules.py`** (new file):

1. **Pydantic models** (with `extra="forbid"` everywhere):
   - `PointsRow`: one `[threshold, points]` entry.
   - `Rule`: a rule with `id`, `signal`, `points`, `cap`, optional `requires`, optional `bonus_consecutive`.
   - `Penalty`: a penalty with `id`, `when` (condition map), `points`.
   - `Thresholds`: `confirm`, `strong`, `dedupe_min`.
   - `WakeRules`: root schema with `version`, `window`, `thresholds`, `rules`, optional `penalties`, optional `reweight_without_pedometer`.
   - Validators:
     - Unique rule IDs.
     - Cap validation: cap ≥ max points per rule.
     - Threshold ranges: `confirm`, `strong` ∈ [1, 100]; `strong ≤ confirm`.
     - `reweight_without_pedometer`: keys ⊆ rule IDs; sum ≤ 100.
     - Boolean rules: exactly one points row.
     - Numeric points: strictly descending thresholds.
     - Empty rules list: reject.
     - Holiday dates: parse as ISO dates; reject invalid.
   - Signal registry: define which signals exist and their types (numeric, bool, enum). Validate `points` thresholds against signal type.

2. **YAML loader function**:
   ```python
   def load_rules_from_yaml(path: Path) -> WakeRules:
       """Load and validate wake_rules.yaml."""
       with open(path) as f:
           data = yaml.safe_load(f)
       return WakeRules.model_validate(data)
   ```

3. **Canonical JSON function**:
   ```python
   def canonical_json(rules: WakeRules) -> str:
       """Return deterministic JSON for SHA-256 (sort_keys=True, separators=(',', ':'))."""
       return json.dumps(rules.model_dump(), sort_keys=True, separators=(',', ':'))
   ```

4. **In-memory cache**:
   ```python
   _effective_rules: Optional[WakeRules] = None

   def effective_rules() -> WakeRules:
       """Return cached active rules; fetch from DB if cache is empty."""
       global _effective_rules
       if _effective_rules is None:
           # Query DB for active row; deserialize rules_json; cache
       return _effective_rules

   def invalidate_cache() -> None:
       """Called after PUT /v1/config/wake."""
       global _effective_rules
       _effective_rules = None
   ```

5. **Startup function** (called in `main.py` lifespan):
   ```python
   async def startup_load_rules(engine: Engine, yaml_path: Path) -> None:
       """On app startup: ensure an active rule version exists."""
       with Session(engine) as session:
           active = session.exec(select(RuleVersion).where(RuleVersion.active == 1)).first()
           if active:
               # Load from DB, cache
           else:
               # Load from YAML, validate, insert version 1, activate, cache
   ```

    from pathlib import Path
    from chronos.wake.rules import load_rules_from_yaml

    config_dir = Path("config")
    if not config_dir.exists():
        typer.echo("config/ directory not found", err=True)
        raise typer.Exit(code=1)

    yaml_files = list(config_dir.glob("*.yaml"))
    if not yaml_files:
        typer.echo("No YAML files found in config/", err=True)
        raise typer.Exit(code=1)

    errors = []
    for yaml_file in yaml_files:
        try:
            if yaml_file.name == "wake_rules.yaml":
                load_rules_from_yaml(yaml_file)
            # elif yaml_file.name == "sources.yaml": ... (T3.2)
            typer.echo(f"✓ {yaml_file.name} valid")
        except Exception as e:
            errors.append((yaml_file.name, str(e)))
            typer.echo(f"✗ {yaml_file.name}: {e}", err=True)

    if errors:
        raise typer.Exit(code=1)

## Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | **Multiple `active=1` rows despite partial unique index** | Low | GET / PUT return ambiguous results; scoring uses wrong version. | Ensure SQLite is in `PRAGMA foreign_keys=ON` mode (checked in T1.1 tests); test the partial unique constraint with T1.1's migration; never manually UPDATE `active` without a transaction. |
| 2 | **Canonical JSON differs between Python versions or JSON libraries** | Low | SHA-256 mismatch; replay shows rules as different when identical. | Use `json.dumps(..., sort_keys=True, separators=(',', ':'))` (deterministic); test that the same `WakeRules` object produces the same SHA across multiple runs. Do NOT use `json.dumps(default=...)` hooks that vary. |
| 3 | **Pydantic validation error has no field paths** | Low | User gets a traceback instead of a clear "field X is invalid" message. | Ensure all models have `extra="forbid"` and Pydantic v2; capture `ValidationError` in the 422 handler and extract field paths via `error["loc"]` tuple. | 4 | **Startup fails silently or hangs** | Low | App does not start; owner does not know why. | Log the YAML load step and any validation errors to stderr (not JSON); print a clear message "Failed to load wake rules: <error>" and exit 1. Test startup with invalid YAML. |
| 5 | **Cache invalidation is incomplete** | Medium | After PUT, old rules are still cached; scoring uses stale rules. | Invalidate cache in the same transaction as the UPDATE (or immediately after commit); add a test that PUTs new rules and verifies the next GET returns the new version. | 6 | **Atomic update is not atomic** | Medium | Two concurrent PUTs both see `active=1` and try to update it; one fails, rules are in an inconsistent state. | Use a single `BEGIN TRANSACTION ... ## Open questions

1. **YAML library and type stubs**: Pinning exact version of `pyyaml` and `types-PyYAML` (e.g., `pyyaml==6.0.2`, `types-PyYAML==6.0.5`)? Or does Pydantic have built-in YAML loading? Answer: use `pyyaml` (`safe_load`); Pydantic's YAML support is opt-in and requires a separate install.

2. **Signal registry and points validation**: Should the task define a signal registry (e.g., `SIGNALS: dict[str, SignalSpec]` in a new `chronos/wake/signals.py`) with type info (numeric, bool, enum)? Or should signal validation be inline in the `WakeRules` validator? The registry will be consumed by T1.5 (scoring). **Proposal:** Create `chronos/wake/signals.py` with a `SIGNALS` dict; use it in both `rules.py` (validation) and `scoring.py` (T1.5). This avoids duplication.

3. **Penalty condition mini-language**: How to parse conditions like `">= 540"`, `"< 10"`, `["denied", "restricted"]` (list = "any of")? Implement a `Condition` class with `.matches(signal_value) -> bool`? Or keep as strings and parse in the scoring engine (T1.5)? **Proposal:** Implement a simple `Condition` dataclass with a parser and a `.matches()` method in `rules.py`; test thoroughly; ensure T1.5 can call it without re-parsing.

4. **Canonical JSON for SHA-256**: Use `json.dumps(rules.model_dump(), sort_keys=True, separators=(',', ':'))`? This is deterministic but loses the `datetime.time` objects (Pydantic converts them to strings like `"06:00"`). Ensure the round-trip is lossless: unmarshalling the JSON produces the same `WakeRules` object. **Proposal:** Test that `WakeRules.model_validate_json(canonical_json(rules))` equals the original `rules`.

5. **Version monotonicity and transaction semantics**: Under concurrent PUTs, how to ensure `version` increments by exactly 1 without gaps? Use `BEGIN TRANSACTION; SELECT MAX(version); INSERT version=max+1; COMMIT;`? This is correct under SQLite's SERIALIZABLE isolation (the default with `BEGIN EXCLUSIVE`). **Proposal:** Use `INSERT ... SELECT` atomically: `INSERT INTO rule_versions (version, ...) SELECT MAX(version) + 1, ...; COMMIT;` (or equivalent Pydantic/SQLAlchemy syntax).

6. **Effective rules caching strategy**: For a single-process API, is a module-level variable sufficient, or should caching be in `Settings` or a singleton class? **Proposal:** Module-level variable (`_effective_rules: Optional[WakeRules]`) in `chronos/wake/rules.py`, with `effective_rules()` and `invalidate_cache()` functions. Simple, fast, sufficient for the single-process constraint (D10).

7. **`GET /v1/config` (generic effective settings)**: Should the task include a generic `GET /v1/config` that returns `render_mode`, `llm_provider`, `pexels_enabled`, etc., from the `settings` table? The plan row says only `GET/PUT /v1/config/wake`. **Proposal:** Defer to T2.6 (which includes "Settings screen" and theme/render-mode toggles); T1.4 focuses on wake rules only.

8. **`chronos config apply-yaml` CLI command**: The task mentions (in open question notes) that if YAML changes and an API-sourced version is active, the owner should call `chronos config apply-yaml` to promote the YAML. Should this command be in T1.4 or deferred? **Proposal:** Defer; T1.4 logs a warning and exposes the mismatch via GET; T6.2 (tuning after 7 real mornings) will write the new rules via PUT and may introduce the CLI command then.

9. **Error response for 422**: Should `rules_invalid` errors include a `validation_errors` array with `[{field, message}]` entries, or should they use Pydantic's standard `detail` format? RFC 9457 does not mandate a specific sub-schema; Chronos can define its own. **Proposal:** Include a `validation_errors` array (as shown in the edge cases); extract from `ValidationError.errors()` in the exception handler.

10. **`reweight_without_pedometer` semantics**: The YAML spec says "if pedometer is unavailable, redistribute to keep max 100". But the rule caps already sum to < 100 (e.g., 30+20+25+15+5=95). When pedometer is unavailable, we disable `steps_10m` and `steps_window` and scale up `unlocked`, `charger_disconnect`, `foreground`. The reweighted max must be ≤ 100. Should the validator check that reweighting is numerically consistent? **Proposal:** Validator checks that `sum(reweight_without_pedometer.values()) ≤ 100` and that each key is a valid rule ID. T1.5 (scoring) applies the reweighting when needed.

None of these are blockers; all have reasonable defaults. The implementer should confirm #2 (signal registry) and #3 (condition parser) with the owner early so T1.5 can depend on them.

## Summary (8 lines)

T1.4 builds the schema and API for wake-engine rules: a Pydantic `WakeRules` model (strict validation with `extra="forbid"`), YAML loader, atomic versioning with DB persistence (partial unique index `(active) WHERE active = 1`), and two endpoints (`GET/PUT /v1/config/wake`). On startup, if no active version exists, loads `services/api/config/wake_rules.yaml` and inserts version 1; if active exists, caches it. PUT validates the full document, rejects 422 with field paths, creates version n+1 atomically, or returns 200 no-op if SHA identical. Edge cases: cap validation, duplicate IDs, signal type checking, threshold ordering, holidays as ISO dates. Risks: concurrent PUT races, JSON determinism, cache invalidation, atomic transactions. Open questions: (1) pyyaml version pinning, (2) signal registry location (T1.5 dependency), (3) penalty condition parser, (4) canonical JSON round-trip, (5) version atomic INSERT, (6) caching strategy, (7) defer `GET /v1/config`, (8) defer `chronos config apply-yaml`, (9) 422 error detail format, (10) reweight validation semantics.
