# T0.4 Brief: Mobile scaffold `apps/mobile` — Expo SDK, TypeScript strict, dev-client, chronos-sensors module

## Task

**ID:** T0.4
**Title:** Mobile scaffold `apps/mobile`: Expo SDK pinned, TypeScript strict, expo-router, dev-client, Biome, jest-expo, `app.config.ts` with bundle id and placeholders for background modes, `expo-doctor` clean, empty `modules/chronos-sensors` Expo module compiling (`hello()`), `.nvmrc` shared
**Size:** M
**Dependencies:** T0.1
**Acceptance criteria:**
- `just check-mobile` green
- `npx expo prebuild --platform ios` succeeds locally
- `expo run:ios --device` installs on the owner's iPhone and shows the module's `hello()` result

---

## Why it matters

T0.4 establishes the mobile app's foundational build and development environment. It provides:
- A working Expo project that can be type-checked, linted, and tested in CI (ubuntu-latest), satisfying the required `mobile` CI job and the `just check-mobile` recipe
- The Swift Expo Module skeleton (`chronos-sensors`) that will later implement CoreMotion queries, background task handlers, and device-state getters; the module must compile cleanly and export `hello()` to prove the linking and bridge works
- `app.config.ts` with iOS bundle identifier and placeholders for push notifications, background fetch, and local networking (HTTPS with mkcert) that T2.2–T2.4 will populate
- A pinned Expo SDK version (57.0.27 as of 2026-10-06) and matching dependencies (expo-router, expo-dev-client, expo-modules-core, React Native, TypeScript) so all three apps (mobile, renderer, API) can be developed against locked, reproducible versions
- CI integration: the `mobile` job in `ci.yml` will run `biome ci`, `tsc --noEmit`, `jest --ci`, `expo-doctor`, and `expo export --platform ios` on every PR, catching configuration and build errors early

Without T0.4, the mobile app cannot be tested in CI, background features cannot be prototyped, or the owner can validate the Expo dev-client workflow on their iPhone. The device-facing acceptance criterion (running on iPhone) is critical because the app must prove it can install via Expo dev-client and call the native module before telemetry, pairing, or push handling are attempted in T2.1–T2.4.

## Constraints

| Constraint | Impact |
|---|---|
| **iOS 17+ only (D01)** | `app.config.ts` does not define Android config; minimum iOS version must be set to 17.0 in the build config (Expo auto-detects or explicit in infoPlist) |
| **Xcode 16 required for device install** | `expo prebuild` and `expo run:ios --device` cannot run on this machine (currently Command Line Tools only); these steps are in the acceptance criteria but are deferred to a moment when Xcode is installed (open question #1). The `just check-mobile` recipe (linting, formatting, types, jest, expo-doctor, expo export) can run on ubuntu-latest in CI without device access. |
| **Expo SDK 57.0.27 pinned** | All expo-* packages must be compatible with this version; creating a new Expo project at this version locks the dependencies; upgrading requires retesting the entire app. Recorded in task plan and README. |
| **TypeScript strict mode** | No `any` without escape hatches; `tsconfig.json` sets `"strict": true` and `"skipLibCheck": false` (do not skip library definitions); every module must satisfy the compiler; tests must also be strictly typed |
| **React Native 0.87.1** | Peer dependency of Expo 57; cannot be overridden; uses the NativeModule bridge for Swift |
| **Bundle identifier `dev.allenvarghese.chronos`** | Hardcoded in `app.config.ts`; must match the iOS provisioning profile and APNs certificate (set up in T2.2); changing it requires reprovisioning |
| **Expo dev-client** | Required for the custom Swift module; incompatible with Expo Go; builds to a dev-client binary that can be installed on a real device via Xcode or EAS Build |
| **`modules/chronos-sensors/` gitignored for build artifacts** | `ios/` generated folder inside the module is created by `expo prebuild` and must not be committed; the TypeScript bridge and Swift source remain in git |
| **CocoaPods** | Required by `pod install` during `expo prebuild`; will be installed as a side-effect of Xcode or via `brew install cocoapods` |
| **`pnpm-lock.yaml` frozen** | `pnpm install --frozen-lockfile` in CI and on developer machines ensures reproducible installs; the lockfile must be committed; running `pnpm install` (unfrozen) will be flagged by CI |
| **`expo-doctor` must pass** | The tool checks for config errors, missing tools, and build readiness; a clean report is required in the `just check-mobile` recipe and CI; common failures are outdated Expo SDK or missing CocoaPods |
| **Memory (16 GB laptop)** | Expo SDK and Xcode builds are memory-intensive; no resource constraints in T0.4 but noted for M0 planning; render and TTS are more critical (T4) |
| **iOS push entitlements** | `entitlements: { 'aps-environment': 'development' }` is set in `app.config.ts` for dev-client; wired to an APNs development certificate in T2.2; production certificate setup is out of scope |

## Edge cases

1. **`apps/mobile/package.json` with mismatched `packageManager` field**
   - Input: `package.json` has `"packageManager": "pnpm@12.9.0"` but `.nvmrc` expects Node 22.22.2 and corepack installs a different pnpm version
   - Expected: CI job `mobile` runs corepack pin check, prints the mismatch, and fails
   - Test: CI step `corepack enable; expected="$(node -p "require('./apps/mobile/package.json').packageManager")"; actual="pnpm@$(cd apps/mobile && pnpm --version)"; test "${actual}" = "${expected}"` catches this

2. **`app.config.ts` with syntax error or missing bundle identifier**
   - Input: `app.config.ts` has a typo in `bundleIdentifier: "dev.allenvarghese.chornos"` (typo: "chornos" instead of "chronos")
   - Expected: `expo-doctor` detects config is malformed or `expo export --platform ios` fails with a clear error; CI fails
   - Test: break the bundle id on a branch; CI mobile job should fail at the export step

3. **Swift module name mismatch between `expo-module.config.json` and `ChronosSensorsModule.swift`**
   - Input: `expo-module.config.json` declares `"moduleName": "ChronosSensors"` but `ChronosSensorsModule.swift` declares `Name("WrongName")`
   - Expected: autolink breaks during `expo prebuild`; the module is not found by the JS bridge; runtime error when `hello()` is called
   - Test: build locally with the mismatch; `expo run:ios --device` shows `ChronosSensors is not a NativeModule`; CI cannot fully test this on ubuntu-latest (no prebuild) but the error would appear in `ios-build.yml`

4. **`tsconfig.json` in strict mode but dependencies are not strictly typed**
   - Input: `@types/react` is missing or outdated
   - Expected: `tsc --noEmit` fails with "Cannot find module or its types"; CI job fails
   - Test: remove `@types/react` from `package.json`, run `jest --ci`; TypeScript fails

5. **Biome config missing or contradicts package.json settings**
   - Input: `biome.json` sets JavaScript target to `ES2015` but `tsconfig.json` sets `target: "ES2020"`
   - Expected: they can coexist (Biome is a formatter/linter, tsc is a type-checker), but test both: `biome ci .` and `tsc --noEmit` both pass
   - Test: this is not really an edge case if both tools are independent; ensure both configs are explicitly set

6. **`expo-doctor` warns about outdated tools or missing build dependencies on ubuntu-latest**
   - Input: CI runs `expo-doctor` on ubuntu-latest (no Xcode, no CocoaPods)
   - Expected: `expo-doctor` prints warnings (e.g., "Xcode not found", "CocoaPods not installed") but exits 0 if the warnings are non-blocking for the export step
   - Test: CI job runs `expo-doctor` and does not fail on warnings; the step logs the output for review

7. **`hello()` function in Swift module not callable from JS**
   - Input: TypeScript bridge imports the module but the native module has not been linked (did not run `expo prebuild`)
   - Expected: Runtime error: `ChronosSensors is not a NativeModule` when the app tries to call `hello()`
   - Test: Manually after `npx expo run:ios --device`, tap the screen and observe the error if linking is broken; CI cannot test this on ubuntu-latest

8. **Jest test fails due to missing Expo test utilities**
   - Input: `jest.config.js` does not use `jest-expo/universal` preset
   - Expected: `jest --ci` fails with module resolution errors (e.g., `Cannot find module 'react-native'`)
   - Test: remove `jest-expo/universal` preset, run `jest`; it fails immediately

9. **`modules/chronos-sensors/ios/` directory persists in git after being gitignored**
   - Input: Developer accidentally commits `apps/mobile/ios/`, violating `.gitignore`
   - Expected: File is already in git; `.gitignore` does not remove it retroactively
   - Test: `git check-ignore apps/mobile/ios/` returns exit 0; if the directory exists in git, `git ls-files apps/mobile/ios/` should return empty

10. **`version` in `app.config.ts` reads `process.env.VERSION` but `VERSION` file is missing**
    - Input: `app.config.ts` has `version: process.env.VERSION || '0.0.1'`, but environment does not set it and the root `VERSION` file is not read
    - Expected: App defaults to version 0.0.1; later in T0.4's task plan or in CI, the `VERSION` file is read and passed as an env var
    - Test: Run `(unset VERSION && npm run prebuild)` locally; the app should still build with version 0.0.1

## Proposed approach

**Shape of the solution (not yet implementation details):**

1. **Create the Expo project skeleton** using `create-expo-app --template` or manual setup:
   - Initialize `apps/mobile/` with `package.json`, `app.config.ts`, `tsconfig.json`, `biome.json`, `jest.config.js`
   - Pin Expo SDK 57.0.27 and matching dependencies in `package.json`; record the pnpm version in `packageManager` field
   - Set `tsconfig.json` to strict mode (`"strict": true`)
   - Configure `biome.json` for TypeScript/JSX linting and formatting
   - Configure `jest.config.js` to use `jest-expo/universal` preset

2. **Create the Expo module `modules/chronos-sensors/`** using `create-expo-module --local` or manual setup:
   - Initialize the module structure with `expo-module.config.json`, `app.plugin.js`, `ios/ChronosSensorsModule.swift`, `ios/ChronosSensors.podspec`, `src/index.ts`
   - Implement the `hello()` function in Swift (returns a simple string)
   - Create the TypeScript bridge that exposes `hello()` to JavaScript
   - The module must be autolinked by Expo (no manual CocoaPods edits needed)

3. **Populate `app.config.ts`** with iOS config:
   - Set `bundleIdentifier: 'dev.allenvarghese.chronos'`
   - Add iOS background modes: `UIBackgroundModes: ['remote-notification', 'fetch']`
   - Add background task scheduler identifier: `BGTaskSchedulerPermittedIdentifiers: ['dev.allenvarghese.chronos.refresh']`
   - Add ATS exception for LAN: `NSAppTransportSecurity: { NSAllowsLocalNetworking: true }`
   - Add APNs development entitlement: `entitlements: { 'aps-environment': 'development' }`
   - Register the chronos-sensors module plugin: `./modules/chronos-sensors/app.plugin.js`

4. **Implement minimal root screen** (`src/app.tsx`):
   - Export a Stack navigator with a simple screen
   - Import and call `ChronosSensors.hello()` on mount
   - Display the result on the screen (proves the bridge works)
   - No routing logic yet (that is T2.5+)

5. **Run `just check-mobile` locally:**
   - `biome ci .` — check for lint violations
   - `biome format .` — format check (or format in place)
   - `tsc --noEmit` — type-check in strict mode
   - `jest --ci` — run minimal unit tests
   - `expo-doctor` — verify the Expo project is healthy
   - `expo export --platform ios` — bundle compile test (on ubuntu-latest, no actual linking, just JS validation)

6. **On a macOS machine with Xcode installed (deferred):**
   - Run `npx expo prebuild --platform ios` to generate the native Xcode project (requires full Xcode, not Command Line Tools)
   - Run `pod install` to link the Swift module
   - Run `npx expo run:ios --device` to install and run on the owner's iPhone
   - Verify the app launches and displays `hello()` result

7. **Commit all files:**
   - `apps/mobile/package.json`, `pnpm-lock.yaml`, `app.config.ts`, `tsconfig.json`, `biome.json`, `jest.config.js`
   - `apps/mobile/src/app.tsx`
   - `apps/mobile/modules/chronos-sensors/expo-module.config.json`, `app.plugin.js`, `ios/ChronosSensorsModule.swift`, `ios/ChronosSensors.podspec`, `src/index.ts`
   - `apps/mobile/__tests__/module.test.ts`
   - `.gitignore` already excludes `apps/mobile/ios/` and `apps/mobile/android/`

**Key principle:** The task is split into two parts:
- **Part A (ubuntu-latest CI):** `just check-mobile` green (linting, formatting, type-checking, unit tests, expo-doctor, expo export)
- **Part B (macOS with Xcode, deferred):** `expo prebuild` + `expo run:ios --device` on the owner's iPhone (device-specific, cannot run in CI, requires open question #1 to be answered about deferral)

## Risks

| Risk | Likelihood | Mitigation | Test |
|---|---|---|---|
| `expo prebuild` fails on macOS due to CocoaPods or Xcode version mismatch | Medium | CocoaPods is installed as a side-effect of Xcode or via `brew install cocoapods`; the task plan records the Xcode version (16) required; `expo-doctor` catches common issues | Run `expo-doctor` locally on macOS; it reports missing tools and versions |
| Swift module does not autolink or the JavaScript bridge is broken | Medium | `expo-module.config.json` must declare the correct module name; `app.plugin.js` must be syntactically valid; the TS bridge must call `requireNativeModule` with the exact module name; unit tests in `__tests__/` catch import errors early | `jest --ci` runs import tests on ubuntu-latest; `expo run:ios` fails immediately if linking is broken (error message is clear) |
| `app.config.ts` has a typo in `bundleIdentifier` | Low | Type-checking and linting catch many typos; `expo-doctor` validates the config on build; CI step `expo export` will fail if the identifier is malformed | `expo export --platform ios` on ubuntu-latest catches syntax errors (though not linking errors) |
| Biome and tsc have conflicting formatting rules | Low | They are independent tools (Biome handles style, tsc handles types); as long as both config files exist and do not contradict each other, they coexist | Run both `biome ci .` and `tsc --noEmit`; if there is a true conflict, the team decides which tool has authority for that rule |
| `tsconfig.json` `strict: true` breaks existing code | Low (fresh project) | This is a new project with minimal code (one file + module); strict mode should be easy to satisfy; if there are type errors, they are in dependencies (add `@types/*` packages) or in the module bridge (cast or annotate return types) | `tsc --noEmit` must pass; add `// @ts-ignore` only as a last resort and document why |
| Xcode Command Line Tools are not sufficient to run `expo prebuild` on this machine | High (known blocker) | This is documented in open question #1 and constraints; the task plan defers device install to when Xcode is installed; `just check-mobile` (CI part) is not blocked | CI job `mobile` runs on ubuntu-latest and does not require Xcode; device install is manual on a Mac with Xcode; `ios-build.yml` (manual/weekly) will catch Xcode issues later |
| CocoaPods is not installed before `expo prebuild` runs | Medium | Xcode installation includes CocoaPods; if not, `brew install cocoapods` is a one-time step; `expo-doctor` reports if missing | `expo-doctor` on macOS; if CocoaPods is missing, its output is clear |
| pnpm lockfile is not regenerated when dependencies change | Low | `pnpm install --frozen-lockfile` enforces reproducibility; if `package.json` is edited, `pnpm install` (without `--frozen-lockfile`) must be run before commit; CI checks the lock file is up-to-date with `git diff --exit-code` after a hypoetical future update | Edit `package.json`, run `pnpm install`, commit; `pnpm-lock.yaml` is updated and commit is clean |
| jest-expo version does not match Expo SDK version | Medium | `package.json` must pin `jest-expo@57.0.5` to match `expo@57.0.27`; if mismatched, tests fail with module resolution errors | `jest --ci` runs in CI and fails if jest-expo is incompatible; local `npm install` also catches this |
| Module name in Swift differs from module name in app.config.ts plugins | High | The three must match exactly: `expo-module.config.json` `moduleName`, `ChronosSensorsModule` class name, and the `./modules/chronos-sensors/app.plugin.js` plugin path; a typo breaks the bridge at runtime | Unit tests import the module and call `hello()`; runtime test on device also checks this |
| `VERSION` environment variable is not set when building, causing version to default to 0.0.1 | Low (by design) | `app.config.ts` defaults to `0.0.1` if `VERSION` is not set; the root `VERSION` file or a build step (in CI or pre-commit) can set it; T0.6 and beyond may wire this more tightly | Build without `VERSION` set; app should still export successfully with version 0.0.1 |
