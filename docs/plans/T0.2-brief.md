## Why it matters

T0.2 establishes repository-level controls that prevent:
- Unreviewed pushes to `main` (PR required, conversation resolution)
- Merging without passing CI (required checks: api, mobile, renderer, secrets)
- Accidental deletion or force-push to `main`
- Secrets being accidentally committed (push protection)
- Broken workflows deploying to production

Without these controls, T0.3+ can commit code that fails CI, and T0.6's CD pipeline could deploy broken services. The ruleset and push protection are the primary guards; CI checks on every PR and the agents' never-push-to-main rule are secondary controls when the primary (ruleset) is unavailable.

## Edge cases

1. **Bootstrap script run twice (idempotent check)**
   - Merge settings, labels, environment, Dependabot config are idempotent
   - Ruleset creation fails with 403 (already fails on first run for private free plan)
   - Secret scanning enable fails with 403 (expected, caught and printed)
   - Expected: no errors, no state changes on second run
   - Test: `scripts/bootstrap-github.sh chronos-ai private` from the repo root twice; both runs report same state

2. **PR opened before ruleset is created**
   - Ruleset does not exist (private free plan)
   - CI job `api`, `mobile`, `renderer`, `secrets` still run (they are GitHub Actions workflows, not ruleset checks)
   - Expected: PR shows CI jobs running but no "required" label in the UI (because no ruleset enforces them)
   - Test: open a PR on a branch with a CI failure; PR can be merged even with red CI (because no ruleset blocks it), but agents follow the never-push-to-main rule

3. **Dependabot PR with security update (security-only filter)**
   - Dependabot groups all security updates per ecosystem into one PR
   - Standard/minor/major updates are NOT created (groups has `patterns: ["*"]` only for `security-updates`)
   - Expected: only security update PRs are created, not version bumps
   - Test: check `gh pr list -R allenvarghese05/chronos-ai` for Dependabot PRs; verify they are for security-update semver changes only

4. **Someone tries to push directly to main (agents' control only)**
   - No server-side ruleset to block force-push or deletion
   - Expected: git command succeeds locally, but CI pipeline agents will not merge it, and no PR means the owner doesn't see it
   - Test: agents' never-push-to-main rule is a hard block in the `push` prompt; direct push would require bypassing the agent

5. **Workflow touches `.github/**` with insecure action (zizmor catches it)**
   - zizmor runs on PR and push touching `.github/workflows/`
   - Expected: zizmor fails, PR is visible but CI has a red annotation
   - Test: commit an unpinned action to a workflow, push to a branch; zizmor should fail with a pedantic finding

6. **PR title does not follow conventional-commit format**
   - `pr-title.yml` uses `amannn/action-semantic-pull-request` (pinned)
   - Expected: PR title check fails, blocking merge (if ruleset existed; currently blocks only by policy)
   - Test: open a PR with title "fix the thing" (no type/scope); pr-title job should fail

7. **Merge commit allowed by accident (merge settings tampered)**
   - Bootstrap sets `allow_merge_commit: false`, but someone changes it in GitHub UI
   - Expected: CI would still pass, but the PR history would show a merge commit (not squash)
   - Test: manually change `allow_merge_commit` to true in GitHub settings; open a PR, merge it with the merge button; inspect history with `git log --oneline --graph`

## Proposed approach

T0.2 is a **verification and documentation task** rather than an implementation task. The bootstrap script already exists (from T0.1), the GitHub repo is already set up, and PR #1 demonstrates that CI works. The implementer should:

1. **Verify bootstrap idempotency:** Run `scripts/bootstrap-github.sh chronos-ai private` locally and confirm the script completes with expected errors (ruleset, secret scanning not available on private free plan).

2. **Confirm GitHub state matches expected:** Use `gh` queries to verify merge settings, labels, environment, Dependabot config are all in place.

3. **Document the private free-plan limitation:** Update `docs/11-implementation-plan.md` T0.2 acceptance criteria and `docs/13-open-questions.md` #10 to reflect that ruleset and push protection cannot be created until the repo goes public or the account upgrades. Link to D20 ("Branch protection" ADR).

4. **Verify CI on PR #1:** Confirm via `gh` that all 4 required checks (api, mobile, renderer, secrets) passed on PR #1, and that zizmor found zero security issues.

5. **Update `.github/workflows/ci.yml` comment:** Add a note that the required check job names must remain fixed (api, mobile, renderer, secrets) because they are referenced in the ruleset JSON, even though the ruleset itself is not yet deployed.

6. **Add a launchd integration test (future):** The laptop deploy script (T0.6) will pull and merge from `main`; a final check should verify that `git verify-commit origin/main` works (once commit signing is configured).

The task is **not** to create new workflows (codeql.yml, dependency-review.yml) because they are not applicable to a private free-plan repo and would not provide value anyway (gitleaks and semgrep cover the same risks).

## Risks

| Risk | Likelihood | Catch with test |
|---|---|---|
| Ruleset accidentally deleted from `scripts/github-ruleset.json` | Low | `git diff scripts/github-ruleset.json` in pre-commit or CI verifies the file is committed |
| CI job names changed (e.g., `api` → `api-checks`) without updating ruleset | Medium | Ruleset JSON still references old names; CI jobs would run but ruleset would not recognize them. When repo goes public, ruleset is applied and PRs would merge without required checks. Guard: pre-commit hook verifies job names match ruleset. |
| Bootstrap script run with wrong arguments (e.g., public instead of private) | Low | Script defaults to `private`; mistakes result in HTTP 403 or wrong settings, which are visible in `gh repo view --json` |
| Dependabot PRs group standard updates with security updates (defeats the filter) | Low | Dependabot config explicitly sets `security-updates` in the groups; behavior is deterministic. Test by checking Dependabot PRs over a week. |
| Zizmor finds a security issue and PR is blocked before T0.3 (no app code, only workflows) | Low | Workflows are boilerplate; zizmor should pass. If it fails, it is catching a real issue (e.g., unpinned action). |
| Deploy script (T0.6) attempts `git verify-commit origin/main` before commit signing is set up | Medium | Script checks `if git config --get user.signingkey` and skips verification if not set; failing safely until signing is configured. |
