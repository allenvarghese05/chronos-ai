# T0.2d Brief: Dependabot security-only for pip/npm; allow `deps` PR scope

## Task

**ID:** T0.2d
**Title:** Dependabot: security-only for pip/npm; allow `deps` PR scope
**Size:** S
**Dependencies:** T0.2
**Acceptance criteria:**
- `.github/dependabot.yml` pip and npm ecosystems: only security updates opened (no version bumps)
- GitHub Actions SHA pins still bumped weekly
- `pr-title.yml` accepts all Dependabot PR titles (security, actions, build)
- Three open action-bump PRs (#7, #10, #17) have pr-title checks green
- Policy documented (ADR or comment + docs/10)

---

## Why it matters

The current `.github/dependabot.yml` intends security-only updates for pip and npm (D19 "lockfiles otherwise change on purpose"), but is misconfigured. The `groups` filter with `applies-to: security-updates` only **groups** security PRs; it does NOT disable version updates. As a result, Dependabot opens both security updates **and** standard version bumps (11 closed this week: sqlalchemy 2.1.4, zod 4.6.6, expo-dev-client 58.x, etc.), requiring the owner to manually close them every week.

Additionally, GitHub Actions SHA bumps (wanted per D19) are failing the `pr-title` check because Dependabot generates titles `ci(deps): …` and the `deps` scope is not in `.github/workflows/pr-title.yml`. This blocks legitimate infra dependency updates until the title is manually fixed or the scope list is updated.

Without this fix:
- Weekly Dependabot noise (unnecessary version PRs to triage)
- GitHub Actions security updates cannot merge (pr-title blocker)
- Policy is implicit (comment only), hard to track if misconfigured again

## Current state

**`.github/dependabot.yml` (lines 1–47):**
```yaml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    commit-message:
      prefix: ci
      include: scope
  - package-ecosystem: pip
    directory: /services/api
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
    commit-message:
      prefix: build(api)
    groups:
      python-security:
        applies-to: security-updates
        patterns: ["*"]
  - package-ecosystem: npm
    directory: /apps/mobile
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
    commit-message:
      prefix: build(mobile)
    groups:
      mobile-security:
        applies-to: security-updates
        patterns: ["*"]
  - package-ecosystem: npm
    directory: /packages/renderer
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
    commit-message:
      prefix: build(renderer)
    groups:
      renderer-security:
        applies-to: security-updates
        patterns: ["*"]
```

**Problem:** The `groups` key with `applies-to: security-updates` **groups** all security updates into a single PR but does **not** prevent standard version updates from being opened. Each group still respects `open-pull-requests-limit`, but the limit applies per group. Standard (non-security) updates are a separate "group" and still open PRs.

## Edge cases

1. **Security update arrives while `open-pull-requests-limit: 0` is set**
   - GitHub's Dependabot docs state: security updates ignore `open-pull-requests-limit` (verified per task facts)
   - Test: manually trigger Dependabot for pip, verify a fake security update opens (or use a fixture in CI if possible)

2. **Prefix `ci(deps)` vs `ci(ci)` / `ci(actions)`**
   - Option A: Add `deps` to pr-title scopes (minimal, semantic: "deps" is a sub-scope under `ci`)
   - Option B: Change Dependabot's `commit-message.prefix` from `ci` to `ci(ci)` or `ci(actions)` (requires testing Dependabot config behavior; may not support nested scope syntax)
   - Test: verify Dependabot actually emits the exact format expected after config change

3. **Three open PRs with stale pr-title status**
   - After merging the fix, pr-title re-runs on synchronize events
   - Options to trigger re-run: `@dependabot rebase` (if owned by dependabot bot), close and reopen, or force-push a fix commit
   - Must verify which method Dependabot allows (likely `@dependabot rebase`)

4. **Dependabot group behavior with limit 0**
   - `groups` with `patterns: ["*"]` groups all updates; `open-pull-requests-limit: 0` applies to each group
   - Result: one grouped PR per security issue, new security updates appended to an existing open PR (or new PR if all are closed)
   - Test: leave `groups` intact, only change limit to 0; verify security updates still group and appear

5. **Drift: limit changed back to 5 without updating policy docs**
   - Policy should be in ADR or docs/10 with a clear rationale so it is not accidentally overridden
   - Recommendation: ADR D33 (new) with reason "lockfile changes on purpose per D19"

## Proposed approach

1. **Update `.github/dependabot.yml`:**
   - For each of `pip` (services/api) and `npm` (apps/mobile, packages/renderer): change `open-pull-requests-limit: 5` → `open-pull-requests-limit: 0`
   - Keep `groups.python-security.applies-to: security-updates` (this groups security updates; the limit 0 only prevents standard version updates)
   - Add or clarify comment above the groups block explaining the mechanism

2. **Update `.github/workflows/pr-title.yml`:**
   - Add `deps` to the scopes list (simplest option, one word)
   - Or test changing Dependabot's `commit-message.prefix` from `ci` to `ci(ci)` (more complex; verify Dependabot syntax supports this)

3. **Document policy:**
   - Option A: Create ADR `docs/decisions/D33-dependabot-security-only.md` (formal, survives future refactoring)
   - Option B: Amend `.github/dependabot.yml` comment and `docs/10-cicd-and-ops.md` § 3 with mechanism note
   - Recommended: both (ADR for binding policy, docs comment for quick reference)

4. **Re-trigger pr-title on open PRs:**
   - For each of PRs #7, #10, #17: comment `@dependabot rebase` to force a PR sync event
   - Verify pr-title then passes (no commit change, but title validation re-runs on synchronize)
   - If `@dependabot rebase` does not trigger pr-title, try close/reopen (last resort; will lose comment history)
