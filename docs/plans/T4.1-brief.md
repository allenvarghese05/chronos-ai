# T4.1 — Reels tables and the assets job (brief)

Branch `t4-1-assets`, stacked on `t3-5-pipeline` (#46).

| ID | Task | Size | Depends | Acceptance criteria |
|---|---|---|---|---|
| T4.1 | Tables + migration 0004: `reels`, `reel_assets`; assets job: og:image resolution, Pillow processing (EXIF strip, resize), optional Pexels b-roll, ffmpeg re-encode, limits | M | T3.5 | Image with EXIF GPS → output has no metadata (test); 10 MB limit enforced; SVG/HTML rejected; Pexels path skipped without key; fixture reel gets ≥ 1 asset per story |

Decisions made overnight under the owner's go-ahead:

1. **Migration number.** This is migration **0005**; 0004 was used by T3.2.
2. **Dependency.** `pillow==13.0.0`, which the task text names.
3. **Images.** Feed image first, then the article's `og:image`/`twitter:image`. A feed thumbnail whose longest side is under 800 px also triggers the og:image fetch, and the larger image wins (BBC thumbnails are 240 px). Downloads go through the guarded client: HTML ≤ 2 MB, images ≤ 10 MB, allowlist jpeg/png/webp/gif (SVG and HTML are rejected).
4. **Processing.**
   - A decompression-bomb guard of 40 MP; "max 4096 px" is implemented as a downscale, not a rejection.
   - EXIF orientation is applied, then the image goes to RGB, is cover-cropped to 1080×1350 and saved as JPEG q85.
   - The image is rebuilt from raw pixels, so no metadata of any kind survives.
5. **No image means a gradient:** no file and no row, and the renderer draws its themed background.
6. **Pexels b-roll is not implemented.** Since D37 the script code assigns every story `visual: "image"`, so b-roll is never requested. A `broll` scene without Pexels logs and takes the image path (the AC). Downloading and ffmpeg-re-encoding Pexels clips is left for when b-roll is turned on.
7. **No browser user-agent.** Some CDNs refuse our honest User-Agent (NDTV returns HTML); we don't spoof a browser, so those scenes get a gradient.
8. **Idempotent.** A scene whose image row exists and whose file is on disk is not downloaded again.
