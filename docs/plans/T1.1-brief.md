# T1.1 Brief: Tables + migration 0001

## Task

**ID:** T1.1
**Title:** Tables + migration 0001: `devices`, `pairing_codes`, `rule_versions`, `telemetry_events`, `wake_evaluations`, `days`, `day_transitions`, `settings`
**Size:** M (≈ 1 day)
**Depends:** T0.3 (API scaffold with engine, Alembic, conftest patterns)

**Acceptance criteria** (from the plan):
1. Migration up and down both work (test).
2. Unique indexes present.
3. `PRAGMA foreign_keys` enforced in a test.

---

## Why it matters

T1.1 is the foundation of the entire backend: without these eight tables and the migration, no telemetry endpoint, state machine, or reply pipeline can be built. The schema *is* the contract: `docs/04-data-model.md` §2 defines every column, type, constraint and index; the migration must implement these exactly or subsequent tasks will fail. Foreign keys and unique indexes are correctness constraints (D10: no Redis; single-user; the DB is the source of truth). Timezone handling (D25) is built into every telemetry row: the phone sends `tz` and `device_ts`, the server derives `local_date` at insertion time; if the schema is wrong, day boundaries and window logic (T1.3, T1.5) will fail.

3. **`rule_versions`** — every rule set ever in effect:

4. **`telemetry_events`** — one row per snapshot from phone:
   - PK: `id` INTEGER

   - **UNIQUE(device_id, seq) for idempotency**
   - Indexes: `(device_id, received_at)`, `(local_date)`

5. **`wake_evaluations`** — score for one telemetry event:
   - PK: `id` INTEGER
   - FK UNIQUE: `telemetry_event_id` → `telemetry_events(id)` **(1:1 relationship)**
   - FK: `rule_version_id` → `rule_versions(id)`
   - `local_date`, `gate` TEXT (`open` | `closed`)
   - `score` INTEGER (0–100)
   - `breakdown_json` TEXT (`[{rule_id, input, points, cap, note}]`)
   - `decision` TEXT (`outside_window` | `low` | `high` | `confirm` | `ignored_dedupe` | `already_confirmed`)

   - `evaluated_at` TEXT (UTC ISO-8601)

6. **`days`** — one row per local date per device:
   - **Composite PK: (local_date, device_id)**

   - FK: `device_id` → `devices(id)`
   - `tz` TEXT (frozen at creation)
   - `kind` TEXT (`weekday` | `weekend` | `holiday`)

   - `state` TEXT (`idle` | `monitoring` | `confirmed` | `fallback` | `delivered`)

   - FK NULL: `confirm_evaluation_id` → `wake_evaluations(id)`
   - `fallback_used` INTEGER (bool)
   - `ticks_sent`, `ticks_received` INTEGER
   - FK NULL: `brief_id`, `reel_id` (future M3/M4; can be NULL)
   - `created_at`, `updated_at` TEXT

7. **`day_transitions`** — audit log:
   - PK: `id` INTEGER
   - FK: `local_date`, `device_id` → `days(local_date, device_id)` (composite FK)
   - `from_state`, `to_state`, `cause` TEXT
   - FK NULL: `caused_by_evaluation_id` → `wake_evaluations(id)`
   - `at` TEXT (UTC ISO-8601)

8. **`settings`** — key/value for runtime toggles:
   - PK: `id` INTEGER
   - `key` TEXT UNIQUE (e.g., `render_mode`, `pexels_enabled`, `llm_provider`)
   - `value` TEXT (validated by `Settings` model at boundary)
   - `updated_at`, `updated_by` TEXT

## Constraints

### Schema constraints from design

- **`devices.token_hash`**: SHA-256 of 32 random bytes, base64url (T1.2 choice). Hashing must happen before insert; migration stores the hash only, never plaintext. Test must verify a hash cannot be reversed.
- **`pairing_codes.code_hash`**: SHA-256 of 8-character alphanumeric code. Stored hashed; plaintext only shown once to the user (T1.2 responsibility).
- **`telemetry_events.local_date`**: derived from `device_ts` and `tz` **at insert time** (server-side, in the endpoint logic T1.6, not migration). Format `YYYY-MM-DD`. Must support queries by date.
- **`wake_evaluations.breakdown_json`**: Pydantic `List[BreakdownItem]` validated at endpoint; stored as `TEXT`. Migration does not validate; app does.
- **`rule_versions.active`**: exactly one row = 1 (others are 0 or NULL). **Partial unique index `UNIQUE(active) WHERE active = 1`** enforces this at the DB level.
- **`days` composite PK**: `(local_date, device_id)`. Foreign key from `day_transitions` must reference both columns.
- **Timestamps**: all `*_at` columns are TEXT, ISO-8601 UTC (`2026-10-06T07:12:04Z`). Never timestamps or datetime objects in SQLite.
- **Timezone**: stored as TEXT (IANA identifier, e.g., `Asia/Kolkata`). Validation left to app (T1.2, T1.6 responsibility).

### iOS/functional constraints

- D25: Phone sends `tz` on every event; server must store and use it to derive `local_date` at each time zone (not hardcoded UTC dates).
- D24: Telemetry must never store precise location, Wi-Fi MACs, contact info. Only the 14 fields listed in `docs/03-wake-engine.md` §3.
- D04: Silent pushes every 5 min; clock skew up to ±300 s must be tolerated (validation in T1.6, not schema).

### Database/performance constraints

- **WAL mode**: Migration must not bypass `render_as_batch=True` in `env.py` (SQLite ALTER TABLE requires batch mode).
- **Foreign keys must be ON**: `PRAGMA foreign_keys=ON` in `db.py`, applied at connect time. Migration tests must verify this.
- **Composite FK from `day_transitions` to `days`**: SQLAlchemy/Alembic batch mode handles this.
- **No indexes on telemetry**: the schema spec lists only `(device_id, received_at)` and `(local_date)` for `telemetry_events`.

### Security constraints

- **Token hashing**: both `devices.token_hash` and `pairing_codes.code_hash` must be SHA-256. Migration enforces uniqueness; the app does hashing (T1.2 responsibility).
- **No sensitive data in `raw_json`**: the raw telemetry payload should not include location or identifiers beyond `device_ts` + `tz`.

## Edge cases

### 1. Downgrade must clean up in FK order

**Input:** Migration up succeeds; downgrade is called.
**Constraint:** `PRAGMA foreign_keys=ON` means SQLite will reject drops that violate FK chains.
**Expected:** downgrade() drops tables in order: `day_transitions`, `wake_evaluations`, `telemetry_events`, `days`, `rule_versions`, `pairing_codes`, `devices`, `settings`. Exactly one transaction, no intermediate error.
**Test:** `test_downgrade_base_no_error()` in conftest patterns already checks this; reuse.

### 2. Composite FK on `day_transitions`

**Input:** `day_transitions` has `(local_date, device_id)` referencing `days(local_date, device_id)`.
**Constraint:** SQLAlchemy/Alembic must generate the FK correctly in batch mode; SQLite requires both columns.
**Expected:** `alembic upgrade head` succeeds; `inspect(engine)` shows a FK constraint with two columns.
**Test:** Insert into `day_transitions` with correct FK → succeeds. Insert with only `local_date` matching but wrong `device_id` → `IntegrityError`.

### 3. Partial unique index on `rule_versions.active`

**Input:** Two rows with `active=1`; or one with `active=1`, others with `active=0`.
**Constraint:** `UNIQUE(active) WHERE active = 1` allows multiple rows with `active=0` or NULL but forbids two with `active=1`.
**Expected:** Insert row A with `active=1` → succeeds. Insert row B with `active=1` → `IntegrityError`. Insert row C with `active=0` → succeeds. Insert row D with `active=NULL` → succeeds.
**Test:** `test_partial_unique_index_on_rule_versions_active()` with explicit inserts and assertion on the second insert.

### 4. One-to-one FK: `wake_evaluations.telemetry_event_id`

**Input:** Two evaluations attempt to reference the same `telemetry_event_id`.
**Constraint:** UNIQUE constraint on the FK column enforces 1:1.
**Expected:** First insert succeeds. Second insert with same `telemetry_event_id` → `IntegrityError`.
**Test:** `test_wake_evaluation_telemetry_event_id_unique()` — insert two evaluations with same FK.

### 5. Timezone change mid-day does not affect `days.tz`

**Input:** Day created with `tz='Asia/Kolkata'`; phone travels to `America/New_York` (tz changes mid-morning).
**Constraint:** `days.tz` is frozen at creation (the schema, migration, and app logic all freeze it); new events after 03:00 local time start a new day with the new tz.
**Expected:** `days` row has `tz='Asia/Kolkata'`; next day's row has `tz='America/New_York'`. Both are keyed correctly.
**Test:** Edge case test in T1.3 (window logic), not migration itself; but schema must allow different `tz` values in different rows with same `device_id`.

### 6. UNIQUE(device_id, seq) on `telemetry_events`

**Input:** Phone sends event with `device_id=1, seq=42`, then sends it again (retry/dedup).
**Constraint:** UNIQUE enforces idempotency at the DB level.
**Expected:** First insert succeeds. Second insert with identical `(device_id, seq)` → `IntegrityError`.
**Test:** `test_telemetry_seq_unique()` — insert, then insert again with same FK and seq.

### 7. Batch mode for SQLite ALTER

**Input:** Migration uses Alembic with `render_as_batch=True`.
**Constraint:** SQLite cannot ALTER TABLE directly; Alembic's batch mode recreates the table.
**Expected:** All upgrades work without manual SQL; downgrades too. PRAGMAs remain in effect.
**Test:** Already covered by `test_upgrade_head_no_error()` and `test_downgrade_base_no_error()`.

### 8. Foreign key constraint on `days.confirm_evaluation_id`

**Input:** `days` has an optional FK to `wake_evaluations` (a day is confirmed by *one* evaluation).
**Constraint:** FK is nullable; if set, it must point to a valid evaluation.
**Expected:** Insert a day with `confirm_evaluation_id=NULL` → succeeds. Insert a day with a valid evaluation id → succeeds. Insert a day with a bogus id → `IntegrityError`.
**Test:** `test_days_confirm_evaluation_fk()` — test both NULL and invalid cases.

## Proposed approach

1. **Define SQLModel table classes** in `src/chronos/models.py` (or split into `models/__init__.py` and import for metadata discovery):
   - Use SQLModel for type safety and Pydantic integration (D10, T0.3 T pattern).
   - Add `extra="forbid"` to any Pydantic mixins if the models also serve as request/response DTOs (separate issue; don't let models be both).
   - Use `Column(...)` for enums: either as `String` with a `CheckConstraint` or rely on app-level validation. (**Open question 2** below).
   - Use `ULID` (python-ulid library or uuid7; **open question 3** below) for public IDs.

2. **Generate migration via `alembic revision --autogenerate -m "0001_init"`**:
   - Alembic reads `SQLModel.metadata` (set in `env.py`).
   - Hand-review the generated migration for correctness, especially:
     - Composite FKs and PKs correct.
     - Partial unique index syntax: `Index(..., unique=True, sqlite_where=...)`.
     - Enum handling (CHECK constraints or just storage as TEXT).
   - Add any manual constraints not auto-generated.

3. **Or hand-write migration** if autogenerate is incomplete:
   - Follow `script.py.mako` template style.
   - Use `op.create_table()`, `op.create_index()`, `op.create_foreign_key()`.
   - Test both up and down immediately.

4. **Add tests to `test_migrations.py`**:
   - Reuse `_alembic_cfg()` and `build_migration_engine()` patterns.
   - `test_upgrade_0001_creates_all_tables()`: query `sqlite_master` for 8 table names.
   - `test_downgrade_0001_drops_all()`: downgrade, query again, all 8 gone.
   - `test_foreign_keys_enforced()`: insert invalid FK → IntegrityError.
   - `test_rule_versions_partial_unique_index()`: two active rows → IntegrityError.
   - `test_telemetry_event_id_unique()`: two evaluations, same FK → IntegrityError.
   - `test_composite_pk_days()`: insert duplicate `(local_date, device_id)` → IntegrityError.

5. **Verify in `test_db.py` or `test_migrations.py`**:
   - PRAGMA foreign_keys is ON during migrations (already in test_migrations.py).
   - Indexes are present: `SELECT name FROM sqlite_master WHERE type='index'`.

6. **No app-level code yet**: the migration is schema-only. The Pydantic models for the request/response DTOs come later (T1.2 for `POST /v1/pair` request, T1.6 for `POST /v1/telemetry`, etc.).

## Risks

### 1. Composite FK in Alembic + SQLite batch mode

**Risk:** Alembic auto-generate may not produce the correct composite FK syntax for the `(local_date, device_id)` reference in `day_transitions`.
**Mitigation:** Hand-review autogenerated DDL. Test it explicitly: insert a valid composite-keyed `days` row, then insert a `day_transitions` with matching FK; verify no error. Insert with one correct, one wrong → IntegrityError.

### 2. Partial unique index syntax in Alembic

**Risk:** `UNIQUE(active) WHERE active = 1` on SQLite uses `sqlite_where=`, but Alembic's autogenerate may not produce this.
**Mitigation:** Hand-write the index if autogenerate omits it. Alembic 1.20 supports it; verify in docs or test immediately after migration.

### 3. Enum storage (TEXT vs CHECK vs app-only)

**Risk:** If enums are stored as bare TEXT, the app can insert invalid values. If CHECK constraints are used, the constraint name must be deterministic (no Alembic-generated names). If app-only, a bug in the app corrupts the DB.
**Mitigation:** Decide now (**open question 2**). Recommendation: store as TEXT, validate in the app (Pydantic model). Add CHECK constraints only if strong guarantees are needed (low overhead, catches some bugs). Test both valid and invalid enum values and check the error message.

### 4. ULID generation strategy

**Risk:** If ULID generation is deferred to the app, the migration must not generate any ULIDs. If the DB should generate them, `python-ulid` or uuid7 must be pinned and a server-side trigger (SQLite) or app-side generation must be consistent.
**Mitigation:** Decide (**open question 3**). Recommendation: generate in the app (Python); store as TEXT. Simpler, testable, no DB-specific UDF. Test that the format is correct.

### 5. Migration autogenerate vs hand-write

**Risk:** Autogenerate may miss edge cases or produce suboptimal DDL. Hand-writing is safer but more error-prone.
**Mitigation:** Decide (**open question 5**). Recommendation: autogenerate, then hand-review and compare to `Base.metadata` using SQLAlchemy `inspect()` (see open question 5). This ensures the model and schema stay in sync.

### 6. Timestamp storage as TEXT

**Risk:** TEXT ISO-8601 strings are harder to query than Unix timestamps or database timestamp types. Lexicographic comparison works by accident but is fragile.
**Mitigation:** D25 mandates TEXT UTC ISO-8601 (`2026-10-06T07:12:04Z`). The app must parse these consistently. Add a test: insert a timestamp, query by `timestamp > ?`, verify the comparison works. Use a shared helper function for formatting.

### 7. Foreign key constraint on `settings.key`

**Risk:** `settings` has no FK; it's a standalone key-value table. If a `key` is referenced elsewhere (future), the table must support it or a new column is needed.
**Mitigation:** This task does not add an FK to `settings`. Future tasks (T3.1 for `jobs`, etc.) will add rows to `settings` via the app logic. No risk in T1.1.

## Open questions

1. **SQLModel table classes vs plain SQLAlchemy ORM declaratives?**
   The scaffoldchoice was SQLModel 0.0.47 (T0.3). It integrates Pydantic v2 but has quirks: pyright strict mode sometimes reports false positives on relationships and computed properties. Should T1.1 define full SQLModel classes (with relationships for FKs) or plain `Table()` via SQLAlchemy Core? If SQLModel, should we use `Relationship` helpers or plain FK columns? This affects how T1.2–T1.6 import and type-check the models.

2. **How are enum fields stored: TEXT with CHECK constraints, or app-level validation only?**
   `wake_source` (silent_push, bg_refresh, foreground, manual), `walking_conf` (low, medium, high), `battery_state` (unplugged, charging, full, unknown), `app_state` (active, background, inactive), `pedometer_auth` (authorized, denied, restricted, not_determined) appear in `telemetry_events` and `days.kind` (weekday, weekend, holiday). CHECK constraints in the DB catch invalid inserts early but add complexity (constraint naming, Alembic rendering). Pydantic models in the app are the single source of truth for valid values anyway. Recommendation: store as TEXT, no CHECK, validate in the app. But if you want DB-level enforcement, we must decide on constraint-naming strategy now.

3. **ULID generation library: `python-ulid` pinned, or `uuid.uuid7()` (Python 3.13), or server-side SQLite?**
   `devices.public_id`, `reels.public_id` must be ULID (spec in `docs/04-data-model.md`). Python 3.12 is the target, so `uuid.uuid7()` is not available (added in 3.13). Options: `pip install python-ulid==2.3.0`, use uuid4 + encode as ULID format (lossy), or a SQLite extension (overkill). Recommendation: `python-ulid` library, generated by the app before insert. No schema-level ULID generation. This task does not generate test data, so it's not critical for T1.1, but T1.2 (pairing, device creation) will need it.

4. **Timestamp column naming and shared helper: confirm `*_at` convention and ISO-8601 UTC format.**
   `docs/04-data-model.md` uses `created_at`, `updated_at`, `confirmed_at`, `received_at`, `consumed_at`, `evaluated_at`, `sent_at`, etc. The format is always "UTC ISO-8601 string" in TEXT columns. Should T1.1 add a helper function (e.g., `chronos.db.utc_now()` returning `datetime.utcnow().isoformat() + "Z"`) to be used consistently in T1.2–T1.6? Or does each endpoint define its own? Recommendation: add a shared helper in `db.py` (or a new `chronos.types` module) and export it; test that it produces the expected format.

5. **Migration generation strategy: `alembic revision --autogenerate` + hand-review, or fully hand-written?**
   T0.3 set up Alembic with `target_metadata = SQLModel.metadata`, so autogenerate is available. The risk is that autogenerate may miss edge cases (partial unique indexes, composite FKs, CHECK constraints). The mitigation is to autogenerate, then manually verify by comparing `Base.metadata` to the migrated schema using SQLAlchemy's `inspect(engine)` API. Recommendation: autogenerate, hand-review DDL, add any missing constraints or indexes, test both up and down, then commit. If autogenerate consistently misses something, switch to hand-written for future migrations. This task should decide and document the pattern for T1.2–M2 tasks.

6. **Do `settings` and `pairing_codes` belong in migration 0001, or do they belong in later migrations?**
   `docs/04-data-model.md` §2.1 lists both as part of the core schema. `pairing_codes` is required by T1.2 (pairing endpoint). `settings` is used by T1.4 (rules override storage) and T2.6 (app settings screen). No other task depends on them before T1.4–T1.5. Should they be in migration 0001 (monolithic) or split into migration 0002 (incremental)? Recommendation: include both in 0001. They are small, early dependencies, and splitting adds no benefit in a single-user system.

7. **Retention columns (`expires_at` on `pairing_codes`, `reels`, `push_notifications`) are mentioned in the data model but not in the T1.1 scope. Confirm nothing from M3+ tables belongs here.**
   `pairing_codes.expires_at` (10 min expiry) is in T1.1's scope. `reels.expires_at` (24 h) and push_notifications retention are M3–M4 (T3.1, T4.1). This task should define `pairing_codes` with `expires_at` but **not** create the `reels` or `push_notifications` tables. Confirm by reading the acceptance criteria: "device, pairing_codes, rule_versions, telemetry_events, wake_evaluations, days, day_transitions, settings" — no reels, no push_notifications, no briefs. Correct.

8. **How to test "PRAGMA foreign_keys enforced" and "partial unique index on `rule_versions.active`"?**
   These are the tricky bits of the acceptance criteria. For foreign_keys:
   - Insert a device with `id=1`.
   - Insert a telemetry event with `device_id=1` → succeeds.
   - Insert a telemetry event with `device_id=999` (not in devices) → `IntegrityError` (with `PRAGMA foreign_keys=ON`).
   Test name: `test_telemetry_foreign_key_enforced()`. For the partial unique index:
   - Insert `rule_versions` row A with `active=1` → succeeds.
   - Insert row B with `active=1` → `IntegrityError` (violates the partial unique index).
   - Insert row C with `active=0` → succeeds (partial index ignores it).
   Test name: `test_rule_versions_partial_unique_index()`. Both test in `test_migrations.py` using a temp DB and the actual migrated schema.
