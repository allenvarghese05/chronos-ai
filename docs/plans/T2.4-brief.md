## 2. Why it matters

T2.3 can collect and durably send a manually requested snapshot, but currently no silent-push, native background-refresh or automatic foreground entry point calls it. The server can send ticks without receiving the corresponding evidence. T2.4 connects those lifecycle entry points to the existing secure sampler/outbox, including when React has not mounted.

Cold-start handling and completion are correctness requirements: losing a native event before the JS listener exists, waiting on foreground hydration, or completing a newer native job from an older callback would produce misleading monitoring gaps. Permission denial must reach telemetry as its actual enum so the server can reweight. A successful Simulator screen cannot establish locked-phone execution or APNs delivery.

### Secure session and transport

- `src/session/native.ts` exports singleton `sessionController`, `deviceMetadata()` and a private `requestPushToken(): Promise<PushResult>`. Metadata supplies validated IANA timezone, bounded OS/app/device strings and no precise location. The secure record is `chronos.session.v1` with D34 accessibility.
- `src/session/store.ts` exports `createSessionStore(deps: SessionDeps)` and `SessionController = ReturnType<typeof createSessionStore>`. Methods include `hydrate`, `retryHydration`, `pair`, `validate`, `forget`, `revoke`, `registerPush`, `lease` and `store`. `hydrate(): Promise<void>` memoizes the Keychain restore and then awaits `validate()` for an existing session. The existing startup GET can consume a significant part of a background budget; a headless local restore must not accidentally add a full validation request before bounded sampling/flush.
- `SessionLease` is `{ identity: string; current(): boolean; run<T>(operation: (api: Api) => Promise<T>): Promise<T> }`; identity is canonical API root plus device ID. Generation checks invalidate work after logout/re-pair. Only confirmed authenticated 401/403 clears a session; temporary TLS/network failures preserve it. Recent T2.3 body-cancellation and immediate generation invalidation must be preserved.
- `src/api/client.ts` uses SDK57 native `expo/fetch`, explicit redirect rejection, bounded bodies/deadlines and sanitized errors. No alternate insecure transport belongs in a background handler.
- Push token registration first rejects Simulator (`!Device.isDevice`) and missing/invalid project ID; only then does a typed Metro `require('expo-notifications')`. This avoids known eager native Keychain reads on unsupported builds. Current registration checks/requests notification permission and PATCHes a genuine token using the existing session; no placeholder token. Background processing must never prompt.

### Existing sampler and durable queue

- `src/wake/sample.ts` exports `sample(sensors: Sensors, source: WakeSource, now: () => number, tz: string, appVersion: string, context?: WindowContext, tickSeq?: number | null): Promise<Sample>`, where `Sample = { input: SampleInput; diagnostics: string[] }`. It reads actual pedometer authorization before queries, never prompts, rejects the native stub (`iosVersion === '0.0'`), shares a five-second monotonic sensor budget, and freezes late native results out of the snapshot. Running time is included in walking activity as approved in T2.3.
- `src/wake/buildTelemetry.ts` uses generated API Signals types, including `WakeSource = silent_push | bg_refresh | foreground | manual`. `WindowContext` is `{ windowStart: string; tz: string; localDate: string }`. `windowStart(...)` checks current timezone, local date, parseable offset timestamp, not-future start and bounded age. Missing/invalid context gives zero window steps plus a diagnostic; it does not invent the configured wake window. `tick_seq` already exists on the API schema.
- `src/telemetry/controller.ts` exports `createTelemetryController(deps: TelemetryDeps)`, returning `sampleAndSend(source: WakeSource, context?: WindowContext): Promise<void>`, `flush(): Promise<void>` and state/subscription methods. It uses one in-flight sample/flush per controller, a five-second sample and eight-second flush deadline. It catches failures into status, so a resolved promise or `.finally()` alone does **not** establish successful upload. T2.4 needs this-run outcome/completion semantics, not stale status from a previous request.
- `src/telemetry/native.ts` exports `nativeTelemetry(session: SessionController)`. It caches `SQLite.openDatabaseSync('chronos-telemetry.db')`/outbox but returns a **new controller per call**. A single app-runtime owner is needed across headless, foreground and manual paths. Its call into `sample(...)` currently passes window context but not the optional `tickSeq`; wire that through deliberately.
- `src/telemetry/outbox.ts` already provides atomic durable sequence allocation, immutable original JSON/timestamps, origin/device partitions, FIFO replay, 256-row/32-KiB bounds and two-hour retention. No bearer token is stored in SQLite. Retryable failures retain events; terminal errors retire them according to the existing tested policy. Confirmed 401/403 retires only the affected identity. API freshness is 300 seconds, so retained older rows can still receive terminal clock-skew rejection.
- `src/telemetry/controls.tsx` mounts a controller on authenticated Home and exposes manual sample/retry/status. Preserve those acceptance controls and their real native behavior; do not replace SQLite with a mock queue in device tests.

### Native refresh bridge and cold-start gap

- `modules/chronos-sensors/src/index.ts` exposes `hello(): string`, `pedometerAuthorization(): Promise<PedometerAuthStatus>`, `requestMotionPermission(): Promise<void>`, queries, `deviceState(): DeviceState`, `registerBackgroundRefresh(identifier: string): void`, `scheduleBackgroundRefresh(identifier: string, earliestInSec: number): void`, `completeBackgroundRefresh(success: boolean): void`, and `addListener('backgroundRefresh', listener): EventSubscription`. Current `BGRefreshEvent = { id: string }` identifies the task kind, not a unique execution.
- `ios/ChronosSensorsAppDelegateSubscriber.swift`, registered through `expo-module.config.json`, calls BGTaskScheduler registration at launch on main for `dev.allenvarghese.chronos.refresh`. It posts a transient NotificationCenter event containing the `BGAppRefreshTask`. If the module observer is absent, that event has no replay buffer. Its initial expiration handler completes false.
- `ios/ChronosSensorsModule.swift` owns MainActor `BackgroundRefreshState`; on observing a task it replaces/completes the prior task, installs an identity-checked expiration handler and 25-second failure timer, then emits JS `backgroundRefresh`. If JS has not subscribed, that emitted event is also transient. The 25-second safety begins only after the module receives a task. `completeBackgroundRefresh(success)` targets the currently pending task without a caller execution ID. Cold-launch retention, JS readiness and stale completion need an explicit launch-owned handoff, including a safety deadline before JS exists; verify how the Expo bridge is actually started rather than assume a pending NotificationCenter notification starts JS.
- Schedule is opportunistic and currently logs submit errors; it does not grant execution or establish Background App Refresh availability. A permission screen needing actual refresh status will need a narrow UIKit-backed status surface; Background App Refresh is a system setting, not a third requestable permission prompt.

### Silent-push contract and installed SDK behavior

- `services/api/src/chronos/scheduler.py` sends `data = {type: 'tick', local_date, tick_seq, window_start}`; `window_start` is an offset ISO timestamp in the device's timezone. There is **no `tz` field** in this payload. Bind context to actual device metadata and validate local date/time; never treat arbitrary push data as configuration or credentials.
- `services/api/src/chronos/delivery/push.py` defines `PushMessage` with `content_available: bool = Field(default=True, alias='_contentAvailable')`, `priority: str = 'high'`, and `data: dict[str, Any]`. `to_expo_dict()` sends token, `_contentAvailable`, priority and data. T1.7 records token-free payload/ticket evidence; ticks are five minutes apart and the scheduler/receipt retry behavior is already implemented. Do not rewrite that architecture here.
- Installed `expo-notifications@57.0.22/src/registerTaskAsync.ts` requires a module-scope TaskManager definition and early registration because headless execution loads the JS bundle without mounting React. Its result enum is `BackgroundNotificationTaskResult` (`NewData = 0`, `NoData = 1`, `Failed = 2`). Use that actual export, not a similarly named example enum.
- Installed `NotificationTaskPayload` is a notification-response union or `{notification: Record<string, unknown> | null; data: {dataString?: string; [key: string]: unknown}; aps?: Record<string, unknown>}`. The native `BackgroundEventTransformer` puts custom APNs fields under `data` and normalizes `body` into `dataString`; it does **not** guarantee the design sketch's `notification.request.content.data` path. Parse the installed SDK envelope, bound any JSON string before parsing, reject visible/action responses and non-ticks, and fixture-test the native-normalized form.
- `expo-notifications/src/index.ts` exports `DevicePushTokenAutoRegistration.fx`, whose module initialization reads persisted registration info and may emit `ERR_NOTIFICATIONS_KEYCHAIN_ACCESS` in an improperly signed/entitled build. Define the task globally while gating notification-native registration/import appropriately for physical supported builds; preserve Simulator startup without suppressing LogBox/errors. T2.2/T2.3 acceptance required normal signing, not `CODE_SIGNING_ALLOWED=NO` or invented Keychain groups.
- Apple requires priority 5 for background pushes; Expo maps `normal` to APNs 5 and `high` to 10. Current server `high` therefore needs an owner-approved narrow correction. Expo still accepts deprecated `_contentAvailable`; changing unrelated delivery schema is unnecessary. Sources: [Apple background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), [Expo push request fields](https://docs.expo.dev/push-notifications/sending-notifications/).

## 6. Constraints

- Design budget is **less than 20 seconds end to end**, with existing five-second sensors/eight-second flush and native 25-second safety. Measure the total including cold credential restore, SQLite initialization, scheduling and completion. A Promise timeout does not cancel native Keychain work; late callbacks must have no stale identity/job effects.
- iOS decides when refreshes and pushes execute. Force-quit can prevent silent wakes until reopening; Low Power Mode, disabled Background App Refresh and throttling may delay/suppress them. Show a persistent honest caveat; there is no reliable app API proving that the last termination was a user force-quit. Never promise five-minute execution. Apple's suggested background-push frequency is much lower than this design's five-minute cadence; changing D04 cadence is outside this brief.
- No background permission requests, full settings/rules editor, feed/player, pipeline/media generation, location service, owner-DB mutation, cloud opt-in or automatic credentials/resource provisioning. Notifications alert denial is distinct from Motion authorization and background execution eligibility; the design states silent pushes do not require alert permission, so do not invent that prerequisite for every wake.
- Reuse single-user API auth, body limits, redirect rejection, sequence allocation, clock-skew policy and after-first-unlock Keychain security. Push content is untrusted; bound strings/numbers/JSON and whitelist the supported tick shape. Ignore untrusted URL/token-like fields.
- Physical iPhone: owner charges using MagSafe because the USB port is broken, and the phone is not currently available as a network-paired Xcode device. Scanning Metro's QR does not install a native app. Previous USB connection alone does not prove present wireless pairing. Simulator permits app/API/SQLite tests but no real pedometer/APNs/locked-device claim.
- A wireless internal-distribution dev build is a possible path: a paid Apple Developer team, registered phone UDID, ad-hoc provisioning and Expo project/APNs configuration are required. Developer Mode can be enabled on the phone after installing a development build without a USB connection. The owner must establish account access/authorization; no such access is assumed. See [Expo internal distribution](https://docs.expo.dev/build/internal-distribution/) and [iOS Developer Mode](https://docs.expo.dev/guides/ios-developer-mode/).
- Stay within the M1 Pro/16-GB laptop; reuse an available Simulator rather than create more unnecessarily. Automated Xcode UI control currently lacks its required device-interaction skill, so use permitted read/build tools and explicit owner manual steps when needed; do not synthesize unsupported UI operations.

## 7. Edge cases

| Concrete case | Expected outcome |
|---|---|
| Headless tick before any React screen mounts | Restore the existing secure session through a bounded runtime path and use the same native outbox; do not wait for provider effects or request permissions. |
| BG task arrives before module initialization, or module exists before JS subscribes | Launch-owned pending execution survives to readiness; safety/expiration can still finish false without JS; eventual delivery is at most once. |
| Task A expires, task B begins, A's JS promise resolves later | A cannot complete B; native expiry, timeout and JS completion are identity checked and exactly once. |
| Callback error, visible notification response, `{type:'news'}`, huge `dataString`, negative/noninteger tick sequence | Return appropriate no-data/failure without a motion query, JSON memory spike, enqueue or API-origin change. |
| Valid normalized tick `{type:'tick', tick_seq:3, local_date:'2026-10-30', window_start:'2026-10-30T06:00:00-04:00'}` on same local morning | Preserve tick 3, use valid window context, send `silent_push` source and current sample timestamp. |
| Yesterday's tick, future window start, malformed timestamp, timezone changed since context | Do not query an invented/wrong window; reject invalid tick/context as appropriate and expose approved zero-window diagnostic for a legitimate sample without usable context. |
| Duplicate delivery of the same tick; push overlaps foreground/BG/manual | Do not create multiple listeners/controllers, fabricate several acknowledgments from one coalesced operation, or lose tick identity. Distinct real snapshots may be stored; existing server consecutive-tick dedup remains authoritative. |
| Open app at 05:59:50, sample timestamp 06:00:10 | Server window is based on actual `device_ts` and IANA timezone; no client naive-time gate. |
| Spring/fall DST, weekend, holiday, travel | Phone supplies actual timezone; server retains its day-row rules. Context validation must tolerate legitimate offset changes and reject cross-day context. No hardcoded weekday window in JS. |
| Motion denied/restricted/not determined; Simulator unavailable | No unauthorized queries; exact `pedometer_auth` enum and zero motion fallback; explain settings on a foreground screen. Native unavailable stub is not claimed as a successful device sample. |
| Permission changes in Settings while app backgrounded | Refresh actual statuses on foreground, then sample with the new authorization. Never request a prompt in a background callback. |
| Notifications alert denied, Background App Refresh denied/restricted, Low Power Mode on | Display separate accurate statuses and caveats; retain valid pairing and allowed foreground sampling. No fake permission grant or claim that silent delivery succeeded. |
| Reboot, locked before first unlock | Keychain unavailable: complete safely without plaintext/anonymous telemetry or treating read failure as a server revocation. After first unlock normal locked operation can resume. |
| Laptop offline, foreground returns | Durable original snapshot remains queued and can retry within budget; Wi-Fi restoration/next wake flushes FIFO. API rejects >300-second skew without rewriting old timestamps. |
| Forget/revoke/re-pair during sensor query, body read or SQLite wait | Generation invalidation prevents old credentials/context/rows from being submitted to the new identity; already confirmed 401/403 invalidates immediately. |
| Sensor deadline/transport stall/hydration stall/JS exception | Total wake deadline bounds work; this-run result is honest; native completion and reschedule occur on all appropriate paths, including failure. Late work cannot mutate expired job state. |
| Force-quit overnight; next normal open | No invented silent events; show force-quit guidance and take a true foreground sample. Server fallback/one-delivery rules remain server-owned. |
| Failed schedule submission or repeated app active/render events | Surface useful bounded status, avoid task request storms/listener leaks and do not report a scheduled date as guaranteed execution. |
