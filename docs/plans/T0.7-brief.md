## Why it matters

Type safety across three languages (Python, TypeScript in mobile, TypeScript in renderer) is only possible if a single source of truth — the API's OpenAPI schema — is consistently converted to native schemas. Without this automation, Python model changes silently desynchronize from mobile and renderer, causing runtime failures in production (e.g. the renderer receives an unexpected field, Remotion fails mid-render; the mobile client sends a telemetry payload the API rejects). The pipeline must be deterministic so that CI (running on Linux) produces byte-identical output to local development (macOS), catching stale schemas at merge time, not in production. Once this infrastructure is in place, T3.4 can extend it to generate the renderer's zod schema from the ReelScript/ReelProps Pydantic models (currently hand-written).

## Governing decisions

- **D18**: Monorepo (`apps/mobile`, `services/api`, `packages/renderer`); `just gen-types` is the single schema distribution entry point.
- **D10**: Single Python 3.12 process with FastAPI; OpenAPI schema is generated from the app factory.
- **D02**: Expo SDK with TypeScript strict; mobile types must be generated from a canonical source to avoid drift.
- **D14**: Remotion renderer; schema validation against zod is critical for catching script errors before render.

## Constraints

### Environment and tooling

- **Python 3.12**: FastAPI and Pydantic model export must use the same Python version locally and in CI (ubuntu, same version).
- **Node/pnpm**: `openapi-typescript@7.x` (latest v7 stable, currently 7.13.0) pinned in `apps/mobile/devDependencies`.
- **FastAPI OpenAPI generation**: `app.openapi()` method returns a Python dict; must be serialized to JSON with `json.dumps(sort_keys=True)` for determinism.
- **Zod version**: `4.5.4` already pinned in `packages/renderer/package.json`.
- **Line endings**: All generated files must use LF (not CRLF); CI runs on Ubuntu, local dev on macOS — git should handle this via `.gitattributes` or `core.autocrlf=input`.

### Determinism requirements

- **Python side**: No random elements in OpenAPI export. Version from VERSION file must be read into the export. All dict serialization must use `sort_keys=True`.
- **npm side**: `openapi-typescript` output must be stable. Check that pnpm lock is frozen (CI uses `--frozen-lockfile`). The tool's version string in the generated file header is acceptable if pinned.
- **Test**: The export function must be run twice in a test, producing byte-identical output both times (with the same system time/clock; use `time-machine` or `freezegun` to mock time if needed).

### Security and validation

- **Bearer scheme**: Must be present in OpenAPI `securitySchemes` with type `http` and scheme `bearer` so clients can introspect it.
- **Problem+json schema**: The RFC 9457 structure should be in `components.schemas` with fields `type`, `title`, `status`, `detail`, `instance` and optional `code` and extension members. Error response examples should reference this schema.
- **No secrets in output**: OpenAPI export must never include hardcoded tokens, API keys, or certificate paths.

### Committed vs. transient

- **services/api/openapi.json**: COMMITTED. Changes to API routers are tracked by this file; a PR that modifies routers but doesn't update the schema is blocked by CI diff.
- **apps/mobile/src/api/schema.d.ts**: COMMITTED. Mobile TypeScript can be type-checked against it pre-build.
- **packages/renderer/src/schema.json**: COMMITTED (stub/hook file, will be populated in T3.4).

### CI timeline and environment

- **api job**: Runs on `ubuntu-latest`. Python environment from `uv sync --locked`. The step `just gen-types` must export `services/api/openapi.json` and is checked with `git diff --exit-code`.
- **mobile job**: Runs on `ubuntu-latest`. Node environment from setup-node. T0.7 does NOT require changes to the mobile job; openapi-typescript runs locally by the developer and CI just diffs the output.
- **Artifact stability**: Output must be identical whether generated on macOS (M1) or Ubuntu (x86-64). Test this in CI by generating twice.

## Edge cases

1. **Route name collision in operationId generation**:
   - **Input**: Two different routers define endpoints with the same summary/name (e.g., two `get_device` functions in different files).
   - **Expected outcome**: FastAPI generates operationIds like `get_device` and `get_device_1`, or uses the full function path. T0.7 must ensure operationIds are stable and unique. If FastAPI's default is not stable, use `generate_unique_id_function` parameter in `FastAPI()` to provide a deterministic mapping.
   - **Test**: Export the schema twice and verify operationId values are identical.

2. **OpenAPI spec includes extra fields not in the acceptance criteria**:
   - **Input**: A router includes `response_model_exclude_none=True` or custom response models with extra Pydantic config.
   - **Expected outcome**: The generated OpenAPI schema includes all fields with their correct types and constraints. `openapi-typescript` generates TypeScript types that match; no surprises at type-check time.
   - **Test**: Check that the generated `schema.d.ts` compiles without errors (`tsc --noEmit`).

3. **Security scheme not propagated to all endpoints**:
   - **Input**: A router endpoint has no explicit `security=` parameter.
   - **Expected outcome**: If the app-level default is bearer auth, the generated schema should mark that endpoint as requiring bearer. Alternatively, `/v1/pair` and health endpoints (`/healthz`, `/readyz`) must explicitly opt out of auth.
   - **Test**: Inspect `services/api/openapi.json` and verify `security: [...]` is present on protected endpoints and absent on public ones.

4. **Problem+json response not in schema**:
   - **Input**: An endpoint raises `ProblemException(status_code=422, code="validation", ...)`.
   - **Expected outcome**: The OpenAPI spec should document a 422 response with the RFC 9457 problem+json schema, not a generic error. Example response bodies in the spec should include `type`, `title`, `status`, `detail`, `instance` fields.
   - **Test**: Generate the schema and grep for `problem`, `urn:chronos:error` in the JSON; verify a 422 response model exists.

5. **VERSION file changes between `gen-types` invocations**:
   - **Input**: The developer bumps VERSION during development (e.g., `0.0.1` → `0.0.2`), then runs `just gen-types`.
   - **Expected outcome**: The exported `openapi.json` has `info.version: "0.0.2"`. A second run of `gen-types` (without bumping VERSION) produces identical output. CI does not fail due to version mismatch between VERSION file and the generated schema; the schema is idempotent given a fixed VERSION.
   - **Test**: Mock VERSION file in test, generate schema, change VERSION, regenerate, and verify only the version field changed (test is resilient).

6. **npm package `openapi-typescript` version mismatch between local and CI**:
   - **Input**: Developer has `openapi-typescript@7.10.1` locally, CI picks up `7.13.0` from the lock file.
   - **Expected outcome**: Both generate byte-identical `schema.d.ts` for the same `openapi.json` input (pinning ensures this). If the tool has a breaking output change, CI fails and the lock must be updated locally before push.
   - **Test**: Run `pnpm list openapi-typescript` to confirm version; CI uses `pnpm install --frozen-lockfile`, ensuring no surprise upgrades.

7. **Biome reformats the generated TypeScript file on commit**:
   - **Input**: `openapi-typescript` generates `schema.d.ts`; then Biome or another tool reformats it.
   - **Expected outcome**: The generated file should be compatible with the project's Biome config (indent style, line width, etc.). Either configure the generator to match Biome's style, or exclude the generated file from formatting (mark as `@generated` in a comment).
   - **Test**: Generate the file, run `biome ci`, and verify no changes are suggested.

8. **Hand-written `packages/renderer/src/schema.ts` diverges from the API**:
   - **Input**: A developer edits `schema.ts` (hand-written) to add a new field, but the corresponding Pydantic model in the API is not updated.
   - **Expected outcome**: This task does NOT police this (until T3.4 auto-generates the renderer schema). But documentation in the file must be clear: "If you edit this file, also edit the Python model." T0.7 should not change this file at all.
   - **Test**: A test that imports and validates the hand-written schema against a fixture to ensure it parses correctly (vitest in `packages/renderer`), but no check for API alignment (that's a design choice for T0.7, implemented in T3.4).

9. **OpenAPI schema change triggers false-positive in CI**:
   - **Input**: A developer makes a non-functional change to a router (e.g., rewording a docstring) that changes the OpenAPI spec.
   - **Expected outcome**: The diff is visible in `git diff -- services/api/openapi.json`, and the developer must decide: is this intentional (e.g., a clarification in the description)? If not, revert the router change. This is the desired behavior — the generated schema is a checksum of the API contract.
   - **Test**: Modify a router docstring, regenerate the schema, and verify it changes in an expected way (e.g., description field).

10. **Empty ReelProps schema (before T3.4)**:
    - **Input**: T0.7 has no Pydantic ReelProps model yet (will exist in T3.4). T0.7 creates an empty `packages/renderer/src/schema.json` placeholder.
    - **Expected outcome**: CI passes because the file exists and diffs cleanly. The schema is not used for validation in T0.7 (renderer still uses hand-written zod). T3.4 replaces the placeholder with the generated schema.
    - **Test**: Verify `schema.json` exists and is valid JSON (even if empty, e.g., `{}`).

## Risks

1. **Determinism broken by Python's json module or FastAPI internals**:
   - **Risk**: `json.dumps()` or FastAPI's `.openapi()` method includes non-deterministic fields (e.g., timestamp, random operationId, dict insertion order).
   - **Mitigation**: Test by running the export twice on the same machine and asserting byte-identical output. If dict order is an issue, explicitly sort keys in the export function. FastAPI operationIds should be stable (based on function names); if not, use `generate_unique_id_function`.

2. **openapi-typescript version or behavior changes**:
   - **Risk**: A new minor version of `openapi-typescript` changes the output format, breaking CI even though the schema is unchanged.
   - **Mitigation**: Pin the exact version in `apps/mobile/devDependencies`. Use `pnpm list openapi-typescript` to verify locally. If a version bump is needed, test locally first and commit both lock file and generated `schema.d.ts` together.

3. **Bearer scheme not recognized by openapi-typescript**:
   - **Risk**: The security scheme is added to OpenAPI but `openapi-typescript` does not generate the right TypeScript for it.
   - **Mitigation**: Test the generated `schema.d.ts` with `tsc --noEmit` in the mobile job. If types are wrong, inspect the security scheme in the OpenAPI spec and adjust the FastAPI code or the generator options.

4. **CI differences between macOS and Linux**:
   - **Risk**: Line endings (CRLF vs LF), floating-point precision, or locale settings cause the schema to differ.
   - **Mitigation**: Use `--sort-keys` and `--no-ensure-ascii` flags consistently. Set `LC_ALL=C` or use a deterministic locale in the export function. Test by running `just gen-types` on both platforms (or simulate with Docker).

5. **Merge conflicts in openapi.json**:
   - **Risk**: Two PRs modify different endpoints, both regenerate `openapi.json`, and Git cannot auto-merge.
   - **Mitigation**: This is expected and acceptable. The developer who rebases must run `just gen-types` to resolve the conflict. Document in CONTRIBUTING that `openapi.json` should not be manually edited.

6. **Hand-written schema.ts accidentally changed**:
   - **Risk**: T0.7 accidentally modifies `packages/renderer/src/schema.ts` when it should not.
   - **Mitigation**: Make `scripts/gen-types.sh` explicitly skip `schema.ts` (do not touch it). Only generate `schema.json`. Add a comment and a test to verify `schema.ts` is unchanged before/after a `gen-types` run.

## Open questions

1. **Should `services/api/openapi.json` be committed, or only generated transiently?**
   - Option A: Commit it; API contract changes are visible in every PR; developers must run `just gen-types` and commit the result.
   - Option B: Transient (gitignored); only checked in CI to be up-to-date.
   - **Proposal**: Commit it. This makes the contract change history visible and is easier for code review.

2. **Who runs `openapi-typescript` — in the api job or the mobile job?**
   - Option A: `api` job exports `openapi.json` and runs `openapi-typescript` to generate `schema.d.ts` (requires Node in the api job; adds ~1 min for `pnpm install`).
   - Option B: `api` job exports only `openapi.json`; `mobile` job runs `openapi-typescript` (requires it to run on Linux as well; schema.d.ts checked in mobile job).
   - **Proposal**: Option B. The api job is Python-only; mobile job already has Node and pnpm installed. Split the work by domain.

3. **How to ensure the security scheme (bearer) is in the OpenAPI?**
   - Option A: Add a FastAPI `HTTPBearer()` dependency to a dummy endpoint or the app globally.
   - Option B: Manually add the security scheme in the export function after calling `app.openapi()`.
   - Option C: Use `app.openapi_schema` and patch it before serializing.
   - **Proposal**: Option B. Explicitly add it in the CLI export function so it's always present and visible.

4. **Should the problem+json response schema be auto-generated or hand-written in OpenAPI?**
   - Option A: Hand-write a Problem model (Pydantic BaseModel) and reference it in endpoint responses.
   - Option B: Document the shape in the export function and inject it into the schema.
   - **Proposal**: Option B (inline in the export function for now). T3.4 or later can refactor into a proper Pydantic model if needed.

5. **Test determinism: use time-machine or freezegun?**
   - **Proposal**: `time-machine` (already pinned in `services/api/pyproject.toml`). Use it to freeze the system clock during export if any timestamp is ever added.

6. **Should openapi.json be formatted with indent=2 or compact?**
   - **Proposal**: `indent=2` for readability and smaller diffs in reviews.

7. **What about operationId stability if routers are reorganized?**
   - **Proposal**: Use a `generate_unique_id_function` that generates operationIds from the full route path and method, not the function name. Test this by moving a router and verifying the operationId does not change.
