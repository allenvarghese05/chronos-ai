# T1.3 Brief: Window and local-day computation

## Task

**ID:** T1.3
**Title:** Window and local-day computation `wake/window.py`: weekday/weekend/holiday, `day_boundary`, DST days, tz change rules
**Size:** S (≤ ½ day)
**Depends:** T1.1 (tables + migration; `days` table with `tz`, `kind`, `window_start_utc`, `window_end_utc`)

**Acceptance criteria** (from the plan):
1. Parametrised tests for Asia/Kolkata, America/New_York DST days, 03:00 boundary, 23:59 → next day.
2. 100% coverage of the module.

---

## Why it matters

T1.3 is the **foundation of time and timezone handling in the wake engine**. Every decision about whether a signal is in-window, what the "local day" is, when the window starts and ends, and whether it's a weekday or holiday depends on pure, testable, timezone-aware functions that can be called from T1.5 (scoring), T1.6 (telemetry endpoint), T1.7 (scheduler), and replayed (T1.8). A bug here breaks:

- **Window gate logic**: if `day_boundary` is wrong, a 23:59 signal on one calendar day may be attributed to the wrong local day, opening the window at the wrong time.
- **DST transitions**: if spring-forward or fall-back handling is wrong, a configured window start (e.g., 08:00) may not exist or be ambiguous, causing crashes or missed ticks.
- **Timezone freezing** (D25): if the logic does not enforce that a `days` row keeps its original timezone, a travel scenario (timezone change mid-day) will compute the wrong window when replayed.
- **Scoring and state machine**: scoring rules (T1.5) depend on being able to compute the window for a given local date; the state machine (T1.6) depends on knowing when the window starts and ends to transition in/out of `monitoring`.

## Governing decisions

| ID | Binding constraint |
|---|---|
| D07 | **Window**: weekdays 06:00–11:00, weekends 08:00–14:00, phone's IANA timezone; fallback delivery at window end. Owner's specification; configurable per-weekday and holidays list in the YAML (which T1.4 will load). |
| D25 | **Timezone**: phone sends IANA `tz` on every event; server derives local date and window; **day boundaries at 03:00 local** to avoid midnight edge cases. "Day" is local to that timezone; the `tz` is frozen in the `days` row. |
| D04 | **Background wake**: server-sent silent pushes every 5 min (D07, 03 §4: `tick_interval_min`). Tick scheduling depends on knowing window start and end. |
| D06 | **Scoring**: every evaluation is stored with its full breakdown so the owner can replay and tune. Pure functions (no I/O) return the score; no DB access inside `wake/window.py`. |

### Output: Core pure functions

#### 1. `local_date_for(instant: datetime.datetime, tz: ZoneInfo, boundary: datetime.time) -> datetime.date`

**Purpose:** Given a UTC instant, a timezone, and a day-boundary time, return the local calendar date.

**Signature:**
```python
def local_date_for(
    instant: datetime.datetime,
    tz: ZoneInfo,
    boundary: datetime.time,
) -> datetime.date:
    """Compute the local calendar date for an instant in a given timezone, using a custom day boundary.

    The "local date" shifts to the next calendar date at `boundary` local time (not midnight).

    Args:
        instant: A UTC-aware datetime (must have tzinfo).
        tz: IANA timezone (ZoneInfo object).
        boundary: Local time (HH:MM) at which a new day begins.

    Returns:
        A datetime.date in the local calendar (the date to use in telemetry_events.local_date,
        days.local_date, etc.).

    Raises:
        ValueError: If instant is not UTC-aware or tz is invalid.

    Example:
        >>> instant = datetime.datetime(2026, 10, 6, 5, 59, 50, tzinfo=datetime.UTC)
        >>> tz = zoneinfo.ZoneInfo("Asia/Kolkata")
        >>> boundary = datetime.time(3, 0)
        >>> local_date_for(instant, tz, boundary)
        datetime.date(2026, 10, 6)  # Because 05:59:50 UTC ≈ 11:29:50 IST; still after 03:00

        >>> instant = datetime.datetime(2026, 10, 6, 1, 0, 0, tzinfo=datetime.UTC)
        >>> tz = zoneinfo.ZoneInfo("Asia/Kolkata")
        >>> local_date_for(instant, tz, boundary)
        datetime.date(2026, 10, 5)  # Because 01:00 UTC ≈ 06:30 IST; after 03:00 (already 10/6),
                                     # but if before boundary time... needs recalculation.
    """
```

**Implementation notes:**
- Convert `instant` to the local timezone: `local_dt = instant.astimezone(tz)`.
- If `local_dt.time() < boundary`, the local date is the previous calendar date.
- Return `(local_dt.date() if local_dt.time() >= boundary else local_dt.date() - timedelta(days=1))`.

#### 2. `day_kind(local_date: datetime.date, cfg: WindowConfig) -> DayKind`

**Purpose:** Given a local date and config, determine if it is a weekday, weekend, or holiday.

**Signature:**
```python
def day_kind(local_date: datetime.date, cfg: WindowConfig) -> DayKind:
    """Determine the day classification (weekday, weekend, or holiday).

    Args:
        local_date: A local calendar date.
        cfg: WindowConfig with holidays_as_weekend set.

    Returns:
        DayKind.weekday (Mon–Fri, not in holidays)
        DayKind.weekend (Sat–Sun, or any date in holidays_as_weekend)
        DayKind.holiday: NOT USED IN T1.3; the schema has it, but holidays fall into weekend.

    Note:
        If a holiday falls on a Saturday or Sunday, it is still a weekend (no double classification).
    """
```

**Implementation:**
- If `local_date in cfg.holidays_as_weekend`, return `DayKind.holiday` (or treat as weekend; see open question #3).
- Otherwise, if `local_date.weekday() >= 5` (Sat=5, Sun=6), return `DayKind.weekend`.
- Else return `DayKind.weekday`.

#### 3. `window_for(local_date: datetime.date, tz: ZoneInfo, cfg: WindowConfig) -> Window`

**Purpose:** Compute the window start and end times (in both UTC and local) for a local date.

**Signature:**
```python
@dataclasses.dataclass(frozen=True)
class Window:
    """A time window in both UTC and local time."""
    start_utc: datetime.datetime      # UTC-aware
    end_utc: datetime.datetime        # UTC-aware
    start_local: datetime.time        # HH:MM
    end_local: datetime.time          # HH:MM

def window_for(
    local_date: datetime.date,
    tz: ZoneInfo,
    cfg: WindowConfig,
) -> Window:
    """Compute the window start and end times (UTC and local) for a local date in a given timezone.

    The window boundaries are determined by the day kind (weekday/weekend/holiday).

    Args:
        local_date: The local calendar date.
        tz: IANA timezone.
        cfg: WindowConfig with start/end times per day kind.

    Returns:
        Window with start_utc, end_utc (both UTC-aware), start_local, end_local (local times).

    Raises:
        ValueError: If the window start time does not exist due to DST gap (spring-forward);
                    or if the timezone or config is invalid.

    Example:
        >>> local_date = datetime.date(2026, 10, 10)  # Saturday
        >>> tz = zoneinfo.ZoneInfo("America/New_York")
        >>> cfg = WindowConfig(weekday_start=time(6,0), weekday_end=time(11,0),
        ...                     weekend_start=time(8,0), weekend_end=time(14,0),
        ...                     day_boundary=time(3,0), holidays_as_weekend=set())
        >>> w = window_for(local_date, tz, cfg)
        >>> w.start_local
        datetime.time(8, 0)
        >>> w.start_utc
        datetime.datetime(2026, 10, 10, 12, 0, tzinfo=datetime.UTC)  # 8am EDT = 12pm UTC
    """
```

**Implementation notes:**
- Look up the window start/end times based on `day_kind(local_date, cfg)`.
- For each boundary time (start, end), construct a local datetime: `local_dt = datetime.datetime.combine(local_date, time)`.
- Attach the timezone: `local_dt = local_dt.replace(tzinfo=tz)`.
- **DST handling** (see open question #4):
  - If the time does not exist (spring-forward gap, e.g., 02:30 on 2026-03-08 in NY): **shift forward** to the next valid instant (03:00 in this case). Use `zoneinfo.fold` parameter if ambiguous (fall-back).
  - If the time is ambiguous (fall-back, e.g., 01:30 on 2026-11-01 in NY): use `fold=0` (first occurrence, earlier UTC time).
- Convert to UTC: `utc_dt = local_dt.astimezone(datetime.UTC)`.
- Return `Window(start_utc=..., end_utc=..., start_local=start_time, end_local=end_time)`.

#### 4. `is_in_window(instant: datetime.datetime, window: Window) -> bool`

**Purpose:** Test whether a UTC instant is within a window.

**Signature:**
```python
def is_in_window(instant: datetime.datetime, window: Window) -> bool:
    """Check if a UTC instant falls within the window.

    Window boundaries are [start_utc, end_utc) — start inclusive, end exclusive.

    Args:
        instant: A UTC-aware datetime.
        window: A Window object.

    Returns:
        True if start_utc <= instant < end_utc, else False.
    """
```

**Implementation:** `return window.start_utc <= instant < window.end_utc`.

#### 5. `next_window_start(after: datetime.datetime, tz: ZoneInfo, cfg: WindowConfig) -> datetime.datetime`

**Purpose:** Given a UTC instant, find the next window start time in that timezone.

**Signature:**
```python
def next_window_start(
    after: datetime.datetime,
    tz: ZoneInfo,
    cfg: WindowConfig,
) -> datetime.datetime:
    """Find the next window start time after a given UTC instant.

    Used by the scheduler to compute the next tick or state transition.

    Args:
        after: A UTC instant.
        tz: IANA timezone.
        cfg: WindowConfig.

    Returns:
        A UTC datetime representing the start of the next window (may be today or a future date).

    Example:
        >>> after = datetime.datetime(2026, 10, 6, 15, 0, tzinfo=datetime.UTC)  # 3 PM UTC
        >>> tz = zoneinfo.ZoneInfo("America/New_York")  # EDT = UTC-4
        >>> cfg = WindowConfig(...)
        >>> # 3 PM UTC ≈ 11 AM EDT; window 8am-2pm EDT is still open
        >>> next_start = next_window_start(after, tz, cfg)
        >>> # If after is 6 PM UTC (2 PM EDT), next window is tomorrow 8 AM EDT
    """
```

**Implementation:**
- Convert `after` to local time: `local_after = after.astimezone(tz)`.
- Compute today's local date using `local_date_for(after, tz, cfg.day_boundary)`.
- Get today's window start time based on `day_kind(local_date, cfg)`.
- If `local_after.time() < start_time`, return today's window start (converted to UTC).
- Else, try tomorrow: increment local date, check its day kind, repeat.
- **Special case**: if a start time does not exist (DST gap), use the next valid instant.

#### 6. `tick_instants(window: Window, interval_min: int) -> list[datetime.datetime]`

**Purpose:** Generate a list of UTC instants at regular intervals within a window (used by T1.7 scheduler).

**Signature:**
```python
def tick_instants(window: Window, interval_min: int) -> list[datetime.datetime]:
    """Generate tick timestamps at regular intervals within a window.

    Used by the scheduler to compute when to send silent pushes.

    Args:
        window: The time window.
        interval_min: Interval in minutes (e.g., 5).

    Returns:
        A list of UTC datetimes, starting at window.start_utc and ending before window.end_utc,
        spaced interval_min apart.

    Example:
        >>> window = Window(
        ...     start_utc=datetime.datetime(2026, 10, 6, 10, 0, tzinfo=datetime.UTC),
        ...     end_utc=datetime.datetime(2026, 10, 6, 15, 0, tzinfo=datetime.UTC),
        ...     start_local=time(6, 0), end_local=time(11, 0)
        ... )
        >>> ticks = tick_instants(window, 5)
        >>> ticks
        [datetime.datetime(2026, 10, 6, 10, 0, tzinfo=datetime.UTC),
         datetime.datetime(2026, 10, 6, 10, 5, tzinfo=datetime.UTC),
         datetime.datetime(2026, 10, 6, 10, 10, tzinfo=datetime.UTC),
         ...]  # Until < 15:00
    """
```

**Implementation:**
- Start at `window.start_utc`.
- Generate ticks by adding `timedelta(minutes=interval_min)` repeatedly.
- Stop when the next tick would be >= `window.end_utc`.

## Constraints

### Platform and memory

- **iOS 17+, single-user, no cloud**: (D01, D10) Pure functions must not make network calls, access the DB, or write files. All I/O is in T1.5 (scoring), T1.6 (state machine), T1.7 (scheduler).
- **16 GB MacBook Pro**: Pure computation means no memory overhead; time-zone loading via `zoneinfo` is negligible.

### Timezone rules (D25)

- **Phone sends IANA `tz`** on every telemetry event; server **never assumes the phone's locale or system timezone**.
- **Day boundary is 03:00 local** (not midnight). Rationale: avoids false positives from 3 a.m. bathroom checks.
- **Timezone is frozen per `days` row**: if the phone's timezone changes mid-morning, the `days` row keeps the original tz, and the next day (after the 03:00 boundary) uses the new tz. T1.3 functions read the tz from the input; they do not modify it. Enforcement is in T1.6 (state machine).

### DST handling (D25, open question #4)

- **Spring-forward (gap)**: when a configured local time does not exist (e.g., 02:30 on 2026-03-08 in America/New_York), **shift forward** to the next valid instant (03:00).
  - Example: if window start is configured as 06:00 but the day is 2026-03-08 (spring forward 02:00→03:00), use 06:00 EDT (no issue). But if window start were 02:30 (hypothetically), shift to 03:00 EDT.
- **Fall-back (ambiguous)**: when a local time occurs twice (e.g., 01:30 on 2026-11-01 in America/New_York), **use `fold=0`** (first occurrence, earlier UTC time). This is the default for `zoneinfo.ZoneInfo`.
  - Example: on 2026-11-01, 01:30 EDT (fold=0) is UTC 05:30; 01:30 EST (fold=1) is UTC 06:30. Use fold=0 for consistency.

### Security and validation

- **Input validation**: `instant` must be UTC-aware (tzinfo=datetime.UTC). `tz` must be a valid IANA name (constructing `ZoneInfo(tz)` must not raise). `cfg` must be valid (WindowConfig frozen, times in valid range).
- **No SSRF, no external data**: no HTTP calls, no file reads. Pure computation only.

## Proposed approach

**Module: `services/api/src/chronos/wake/window.py`**

1. **Define input type**: `WindowConfig` (frozen dataclass or Pydantic model) with `weekday_start`, `weekday_end`, `weekend_start`, `weekend_end`, `day_boundary`, `holidays_as_weekend: set[date]`.

2. **Define output types**:
   - `Window` (frozen dataclass): `start_utc`, `end_utc` (datetime.datetime), `start_local`, `end_local` (datetime.time).

3. **Implement core functions**:
   - `local_date_for(instant: datetime, tz: ZoneInfo, boundary: time) -> date`: compute local calendar date with custom boundary.
   - `day_kind(local_date: date, cfg: WindowConfig) -> DayKind`: classify date as weekday/weekend/holiday.
   - `window_for(local_date: date, tz: ZoneInfo, cfg: WindowConfig) -> Window`: compute window start/end in UTC and local time, with DST gap handling.
   - `is_in_window(instant: datetime, window: Window) -> bool`: test membership in [start, end).
   - `next_window_start(after: datetime, tz: ZoneInfo, cfg: WindowConfig) -> datetime`: find next window start.

4. **No module-level I/O**: no DB access, no file reads, no API calls. Import only stdlib (`datetime`, `zoneinfo`, `dataclasses`) and `enums.DayKind`.

   - **T1.5 (scoring)**: calls `window_for(days.local_date, days.tz, cfg)` to check if an evaluation's timestamp is in-window.
   - **T1.6 (telemetry + state machine)**: calls `local_date_for(device_ts, tz, boundary)` to compute `telemetry_events.local_date` column; calls `window_for()` to transition in/out of monitoring.

## Open questions

1. **Module API shape**: Are the six function names and signatures (`local_date_for`, `day_kind`, `window_for`, `is_in_window`, `next_window_start`, `tick_instants`) correct? Or should any be combined/split? Should `next_window_start` return the next window *start*, or the entire next window (Window object)? Should `tick_instants` be a pure function (as proposed) or deferred to T1.7?

2. **Weekend definition**: Are weekends always Sat (5) + Sun (6) (ISO weekday), or configurable per user? Design doc D07 says "weekdays 06:00–11:00, weekends 08:00–14:00" without naming the days. Assume Sat+Sun fixed.

3. **Holiday classification**: When `holidays_as_weekend` contains a date, should `day_kind()` return `DayKind.holiday` or `DayKind.weekend`? The schema has three kinds (weekday/weekend/holiday), but do they affect scoring/window differently? (Assume holiday means "treat as weekend".)

4. **DST gap handling**: When a configured local time does not exist (spring-forward gap), should the module **shift forward to the next valid instant** (proposed), or **fail loudly with an exception**? Shifting silently could hide config errors, but failing would require T1.4 (rules loader) to validate that all times are reachable in the timezone. (Propose: shift forward, log a warning, document in config YAML that times near DST boundaries may shift.)

5. **next_window_start contract**: Should this function return the **next window that has not yet started**, or the **next window (even if it is in progress)**? If `after` is 10:30 and the window is 10:00–15:00, should it return 10:00 (already in progress) or 15:00 (next day)? (Assume: next window that has not started, so 15:00 or tomorrow's start.)

6. **Window boundary semantics**: Should the window be [start_utc, end_utc) (start inclusive, end exclusive), [start_utc, end_utc] (both inclusive), or something else? Proposal: [start, end) to avoid overlaps across days and to make `tick_instants` deterministic. Confirm.

7. **Property tests with hypothesis**: Should T1.3 include hypothesis property tests (e.g., `local_date_for` is monotone non-decreasing in instant; every instant maps to exactly one local_date)? Or are parametrised tests sufficient? (Propose: include property tests for robustness; hypothesis can catch edge cases humans miss.)

8. **`tick_instants` in this module or T1.7?**: The function is pure (no I/O), so it fits in T1.3; but it is used only by the scheduler (T1.7). Should it live in `wake/window.py` or `jobs/scheduler.py`? (Propose: `wake/window.py` because it is pure and testable in isolation; T1.7 imports and calls it.)

## Summary

**T1.3 Brief Summary** (8 lines):

T1.3 implements pure timezone and window-computation functions for the wake engine: `local_date_for` (derive local calendar date from UTC + timezone + day boundary), `day_kind` (classify weekday/weekend/holiday), `window_for` (compute UTC window start/end), `is_in_window` (test membership), `next_window_start` (find next window), and `tick_instants` (generate tick times). Must handle America/New_York spring-forward (gap) and fall-back (ambiguous) DST transitions, Asia/Kolkata (no DST), day boundary at 03:00 local, and holidays-as-weekend list. Input: frozen `WindowConfig` from T1.4's YAML loader. Output: deterministic, timezone-aware `Window` and `date` values used by scoring (T1.5), state machine (T1.6), and scheduler (T1.7). Risks: DST gaps/ambiguity crashes, day-boundary off-by-one, incorrect holiday handling. Open questions: (1) module API shape, (2) weekend definition Sat/Sun fixed vs configurable, (3) holiday classification returns DayKind.holiday or DayKind.weekend, (4) DST gap handling policy (shift forward vs fail), (5) next_window_start returns next-not-started or next-even-in-progress, (6) window boundary [start, end) vs [start, end], (7) hypothesis property tests vs parametrised, (8) tick_instants in T1.3 or T1.7.
