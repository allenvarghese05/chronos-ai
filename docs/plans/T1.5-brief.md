# T1.5 Brief: Scoring engine `wake/scoring.py`

## Task

**ID:** T1.5
**Title:** Scoring engine `wake/scoring.py`: `evaluate(signals, rules, now, ctx) -> Evaluation` pure; derived facts (charger transition, consecutive unlocked, dedupe); penalties; reweighting; breakdown
**Size:** L (2–3 days)
**Depends:** T1.3 (window computation), T1.4 (rules loader)
**Acceptance criteria** (from the plan):
1. Golden fixture `tests/fixtures/wake/mornings/*.json` (≥ 6 scripted mornings incl. "3 a.m. phone check", "unplug and go back to sleep", "pedometer denied", "walk at 05:55 then 06:05") produce the expected decisions.
2. Hypothesis property: score ∈ [0,100], monotone in steps; outside window always 0.

---

## Why it matters

T1.5 is **the heart of the wake engine**. The pure scoring function decides whether the owner is awake; every state transition, every push, every report, and all tuning decisions depend on it being:

- **Correct**: the breakdown reproduces the worked example in docs/03-wake-engine.md §1 exactly (48 steps → 30, walking 95 s high → 20, unlocked +15 and consecutive bonus +10 = 25, charger 15, steps_window 112 → 5, foreground 0 → 85 ≥ strong 85 → CONFIRMED).
- **Explainable**: `wake_evaluations.breakdown_json` lists every rule, penalty, derived fact, input value, points awarded, cap applied, and any note explaining a 0 or modification.
- **Deterministic**: same inputs → equal output, always. Used for replay (T1.8), tuning, and post-mortem debugging.
- **Pure**: no I/O, no DB, no side effects. Takes signals, rules, context and returns a score and decision; the caller stores it.
- **Replayable**: stored evaluations reference a `rule_version_id`, so the owner can re-score history under different rules without re-sampling.

**If T1.5 is wrong:**
- A false negative (score too low) → owner misses their own wake signal → fallback delivery saves the day but morning is delayed and frustrating.
- A false positive (score too high, score too easily) → owner's phone in a drawer confirms the day early → no reel ready on actual wake → empty feed.
- Non-deterministic scoring → replay shows one thing, the actual history shows another → owner loses trust in the system and tuning becomes futile.
- Missing breakdown details → owner cannot debug why a tick scored high/low → tuning impossible.

## Governing decisions

| ID | Binding constraint |
|---|---|
| D06 | **Scoring is additive and rule-based** (not ML). Weights are per-signal in the YAML; every evaluation stored with full breakdown for replay and tuning. |
| D25 | **Timezone is frozen per day** (`days.tz`). Scoring uses the day's timezone, not the server's naive time. Window membership is computed from `device_ts` in `tz`. |
| D05 | **Signal set** (docs/03 §2): steps (10 min + since window start), walking seconds and confidence, unlocked state, charger disconnect transition, app foregrounded, battery state, pedometer auth. All readable in a 30 s background wake. |
| D04 | **Silent push ticks** every `tick_interval_min` (default 5). Scoring sees a snapshot of signals at tick time; history windows (e.g., steps last 10 m) come from CoreMotion, not deltas between ticks. |
| D09 | **Eager render**: pipeline ready before window; scoring at window open is deterministic. |
| D24 | **Privacy**: no location, no Wi-Fi IDs, no contacts. Telemetry stores only the 19 fields in docs/03 §3. |
| D16 | **LAN-only network**: phone ↔ laptop over home Wi-Fi; clock skew check in T1.6 guards against large device_ts errors. |

**Evaluation struct (not stored directly; this goes into JSON):**

- `gate: EvaluationGate` — open or closed (determined first).

- `decision: EvaluationDecision` — the final decision (outside_window / low / high / confirm / ignored_dedupe / already_confirmed).
- `consecutive_high: int` — count of consecutive ticks ≥ confirm and within max gap (used for the 2-tick rule).
- `breakdown: list[BreakdownItem]` — each rule's contribution (must match YAML rule order, then penalties, then derived facts).

**BreakdownItem struct** (to be persisted in `breakdown_json` as JSON array):

```python
class BreakdownItem(BaseModel):

    input: int | float | bool | str  # the signal value evaluated
    points: int            # points awarded (may be 0 or negative)
    cap: int               # the cap applied
    note: str | None       # optional explanation (e.g., "conf=high", "consecutive bonus +10", "pedometer unavailable")
```

## Constraints

### Scope: pure function only

- **No I/O**: no database, no API calls, no file reads, no random numbers, no clock reads except the `now` parameter.
- **No side effects**: no mutations of caller's objects, no logging.
- **Deterministic**: same inputs always produce equal output.
- **Testable**: no mocks needed; property tests can run millions of evaluations in seconds.

### Score range and bounds

- **Score ∈ [0, 100]**: always. Clamped after penalties applied.
- **Rule caps**: each rule enforces a per-signal cap (e.g., unlocked cap 25, steps_10m cap 30).
- **Global maximum**: sum of caps = 30 (steps_10m) + 20 (walking_10m) + 25 (unlocked) + 15 (charger_disconnect) + 5 (steps_window) + 40 (foreground) = 135. After reweighting (when pedometer unavailable), the adjusted caps sum to 100.
- **After penalties**: score clamped to [0, 100] after all penalties are applied. Never negative in the output.

### Thresholds (from rules.yaml)

- `confirm: 70` — two consecutive ticks ≥ 70 within ≤ 12 min → CONFIRMED.
- `strong: 85` — one tick ≥ 85 → CONFIRMED (single-tick rule; must be ≥ confirm per the schema validator).
- `dedupe_min: 2` (minutes) — second snapshot < 2 min after last is deduped (decision = ignored_dedupe, but still scored and stored).
- `confirm_max_gap_min: 12` (hardcoded in §4 of docs/03 and example; see open question 4).

### Window gate

- Evaluated **first, before any rules**.
- If outside the window: `gate = closed`, `score = 0`, `decision = outside_window`, no rules run, no breakdown (or minimal "gate closed" entry).
- If inside: `gate = open`, rules run normally.

### Day state machine interaction

- If `day_state = confirmed` or `day_state = delivered`: **always return `decision = already_confirmed`**, regardless of score (do not re-confirm). Score may be stored for analytics/tuning but decision is locked.
- If `day_state = fallback`: still score normally (useful for tuning); decision is the computed one, but delivery is blocked (T1.6's job).
- If `day_state = idle` or `monitoring`: normal scoring.

### Pedometer reweighting

- If `pedometer_auth ∈ {denied, restricted}`: apply `reweight_without_pedometer` from the rules.
  - Affected rules: any rule with a derived SignalSpec property `needs_pedometer = true`.
  - Specific rules to reweight: `steps_10m`, `walking_10m`, `steps_window` (these are skipped and give 0 with note "pedometer unavailable").
  - Bonus weights applied to: `unlocked`, `charger_disconnect`, `foreground` (from the YAML `reweight_without_pedometer` dict).
  - Other rules unaffected.
- If pedometer is authorized / not_determined: use normal weights.

### Memory and performance

- Target: evaluate a tick in < 10 ms on a 2026 M1 MacBook Pro.
- No streaming; whole snapshot in memory (all signals ≤ 100 KB).
- No caches inside evaluate(); the caller manages rule caching (T1.4 has `RulesCache`).

## Inputs and outputs (detailed)

### Function signature

```python
def evaluate(
    signals: Signals,
    rules: WakeRules,
    now: datetime,              # server's current UTC time (used for comparisons, not the score's timestamp)
    ctx: EvalContext,           # previous tick, window, day state, rule version
) -> Evaluation:
    """Score the signals and return a decision.

    Args:
        signals: Telemetry from the phone (19 fields).
        rules: The active rule set.
        now: Server's current UTC time for reference (e.g., checking if a time is in the window).
        ctx: Context from previous ticks and day state.

    Returns:
        Evaluation with score, decision, breakdown, and consecutive_high count.

    Raises:
        ValueError: If inputs are invalid (e.g., unknown signal name in rules; should not happen if T1.4 validates).
    """
```

### Inputs to `evaluate()`

1. **Signals** (from the phone, validated in T1.6's endpoint):
   - All 19 fields required (no optionals).
   - Types validated by Pydantic `extra="forbid"`.

2. **Rules** (from T1.4's `get_effective_rules()`):
   - Already schema-validated.
   - `window`, `thresholds`, rules list, penalties list, `reweight_without_pedometer` dict all present.

3. **now** (server UTC):
   - Used to check if signals' `device_ts` is within the window.
   - Should be close to the evaluation time but is deterministic for replay (T1.8 supplies a fixed clock).

4. **Context** (from T1.6 and T1.7's state machine):
   - Previous tick's state (if any).
   - Resolved Window for the local date.
   - Day state.
   - Rule version ID (for storage).

### Outputs from `evaluate()`

**Evaluation struct** (to be defined in this module):

```python
class Evaluation(BaseModel):
    gate: EvaluationGate           # "open" or "closed"
    score: int                      # 0–100
    decision: EvaluationDecision    # one of the 6 decision types
    consecutive_high: int           # count of consecutive ticks ≥ confirm
    breakdown_json: str             # JSON array of BreakdownItem dicts (serialized for storage)
```

The breakdown array is built incrementally (see algorithm below) and serialized to JSON for storage in `wake_evaluations.breakdown_json`. At the API response layer (T1.6), this JSON is deserialized and sent as the `breakdown` array in the HTTP 200 response.

## Edge cases (exhaustive)

1. **Tick at 05:59:50 UTC with device_ts 06:00:10 local** (docs/03 §8.1):
   - Parse `device_ts` and `tz` from signals.
   - Compute `local_date` using `local_date_for(device_ts, tz)`.
   - Compute window using `window_for(local_date, ..., config)`.
   - If `device_ts` is in [start_utc, end_utc), gate is open; otherwise closed.
   - Expected: gate open, rules run.

2. **Phone timezone changes mid-day** (docs/03 §8.2):
   - This evaluation uses the `tz` from the signals (the phone's current timezone).
   - The `days` row was created with a different tz; that row's tz is frozen.
   - This evaluation's window is computed using the phone's current tz.
   - **Result**: the window may differ from the day's frozen window. This is expected and handled by T1.6 (state machine creates a new day row at the boundary if needed).
   - **For scoring**: use the signals' `tz` for the window lookup; the decision is computed correctly for this snapshot.

3. **Two snapshots 20 s apart** (docs/03 §8.3):
   - First snapshot (silent push) and second (foreground user tap) within 2 min dedupe window.
   - First: evaluate normally, e.g., score 50.
   - Second: `device_ts` − previous.device_ts = 20 s < dedupe_min (2 min).
   - **Decision**: `ignored_dedupe`.
   - **Score**: still computed (0–100) and stored (for analytics).
   - **Consecutive-high count**: does NOT advance; the deduped tick is skipped for the 2-tick rule.
   - Expected: both stored, but second's decision is ignored_dedupe.

4. **Pedometer permission denied** (docs/03 §8.4):
   - `pedometer_auth = denied`.
   - Rules `steps_10m`, `walking_10m`, `steps_window` are skipped (give 0 with note "pedometer unavailable").
   - Rules `unlocked`, `charger_disconnect`, `foreground` get reweighted caps from `reweight_without_pedometer`.
   - Expected: day can still confirm via unlocked+charger+foreground if those score high.

5. **Weekend / holiday window** (docs/03 §8.5):
   - `local_date` is classified as weekend or holiday.
   - Window times are from `config.weekend_start` / `config.weekend_end` instead of weekday.
   - Example: weekend window 08:00–14:00 instead of weekday 06:00–11:00.
   - Expected: gate open if within the wider window; same rules apply.

6. **Daylight-saving transition (spring forward)** (docs/03 §8.8):
   - On the 2026 spring-forward day in America/New_York (e.g., 03:00 → 04:00), the configured window start "06:00" may not exist (the hour skips from 02:59 to 04:00).
   - Use `zoneinfo.ZoneInfo` to resolve the time; it picks the earliest valid time (06:00 becomes 07:00 in EDT).
   - Window computation (T1.3) handles this; scoring just uses the result.
   - Expected: window is correct, gate logic works.

7. **Fall-back DST transition** (docs/03 §8.8):
   - On the 2026 fall-back day (e.g., 02:00 → 01:00), times 01:00–02:00 are ambiguous.
   - Use the `fold` parameter in `zoneinfo` to pick the correct side.
   - Window computation uses a fixed fold value; scoring uses the result.
   - Expected: window is correct and unambiguous for all snapshots.

8. **Missed ticks** (docs/03 §8.9, fixture missed_ticks):
   - Ticks at 07:00 and 07:12 (5-min interval default; one tick missed).
   - Both ticks score high (≥ 70).
   - First tick: consecutive_high = 1 (first tick of the day).
   - Second tick: time gap = 12 min ≤ dedupe_min's confirm_max_gap_min (12 min). consecutive_high = 2.
   - **Decision at second tick**: confirm (2 consecutive ticks ≥ 70).
   - Expected: confirm even with missed tick in between.

9. **Out-of-order delivery** (from AGENTS.md correctness rules):
   - Device_ts from a previous local_date (e.g., tick from yesterday arriving today).
   - T1.6's endpoint should reject this based on `local_date` mismatch or age (> 1 day old), not the scoring engine.
   - If it reaches scoring: compute the window for the historical date; gate would be closed (if evaluating tomorrow); score 0.
   - **For consecutive_high**: if `previous` is from a different local_date, treat as not consecutive (reset count).
   - Expected: no false confirms across day boundaries.

10. **First tick of the day** (no previous tick):
    - `ctx.previous = None`.
    - `consecutive_high` initialized to 0, can only become 1 or 2+ if this tick is ≥ threshold.
    - Derived facts that depend on previous (charger_disconnected): assume false (charger transition requires previous state).
    - Expected: day starts fresh; no artificial carry-over.

11. **Device clock severely skewed** (docs/03 §8.7):
    - Device_ts is > 5 min off from now.
    - T1.6's endpoint rejects with 422 `clock_skew` before reaching scoring.
    - Scoring never sees this case.
    - Expected: not an issue for the scoring engine.

12. **Battery state unknown** (edge case from signals enum):
    - `battery_state = unknown`.
    - Charger-related rules (e.g., charger_disconnect penalty) do not fire (no condition matches).
    - Score may be lower but is valid.
    - Expected: handled gracefully (no crash).

13. **Walking confidence low with 95 s** (derived from fixture early_walk):
    - `walking_sec_10m = 95`, `walking_conf = low`.
    - Rule walking_10m has `requires: { walking_conf: [medium, high] }`.
    - Requirement not satisfied → rule gives 0 with note "requires walking_conf in [medium, high], got low".
    - Expected: walking rule contributes 0.

14. **Steps > 5000 in a 10-min window** (sanity check):
    - Pydantic Signals model should bound steps_10m to a reasonable max (e.g., 300 steps/min → 3000 max in 10 min).
    - If an invalid value reaches scoring: evaluate normally (no runtime check; trust T1.6's validation).
    - Expected: rejection at the endpoint (T1.6), not the scoring engine.

15. **Bonus consecutive only when both ticks are unlocked and within gap**:
    - Rule `unlocked` has `bonus_consecutive: { ticks: 2, points: 10 }`.
    - First tick: `is_unlocked = true`, score is 15 + bonus check: only 1 tick so far, no bonus yet. Contribution: 15.
    - Second tick: `is_unlocked = true`, time gap 5 min ≤ 12 min, and `previous.is_unlocked = true`.
    - Bonus applies: contribution is 25 (15 + 10).
    - If second tick `is_unlocked = false`: no bonus, contribution is 0 (or may trigger another rule, but not this one).
    - Expected: bonus only applies when condition and history align.

16. **Previous tick from an earlier local_date (day boundary crossed)**:
    - Previous tick at 02:50 local (2026-10-06 in tz), current tick at 03:10 local (2026-10-07 in tz, after 03:00 boundary).
    - These are different local dates.
    - **Consecutive count**: reset to 0 (they are not consecutive across day boundaries).
    - **Derived facts**: treat as if no previous (charger_disconnected = false, bonus_consecutive = false).
    - Expected: day starts fresh the next morning; no carryover.

17. **Pedometer auth = not_determined** (edge case):
    - Similar to `denied` / `restricted`: treat as unavailable.
    - Apply reweighting; pedometer-based rules skipped.
    - Expected: consistent with denied/restricted (conservative approach).

18. **Fixture: "3 a.m. phone check"** (from plan acceptance criteria):
    - Tick at 03:10 local, outside the 06:00–11:00 window.
    - Expected: gate closed, score 0, decision outside_window.

19. **Fixture: "unplug and go back to sleep"** (from plan acceptance criteria):
    - Tick 1: unplug at 06:05, steps 50, unlocked true → score high.
    - Tick 2 (at 06:10): 0 steps, 540 s stationary, unlocked false → penalty stationary_dominant applies → score drops to 0 → decision low or high depending on first tick → no early confirm.
    - Expected: the 2-tick rule prevents a false confirm from a single wake gesture followed by sleeping again.

20. **Fixture: "walk at 05:55 then 06:05"** (from plan acceptance criteria):
    - Tick 1 (05:55): outside window, 100 steps in last 10 min. Decision outside_window, score 0.
    - Tick 2 (06:05): inside window, steps_10m = 100 (still high from the 05:55–06:05 window, or reset to lower). If the window is [06:00, 11:00) and steps are cumulative since window start (steps_since_window), the 100 from 05:55 is before the window, so steps_since_window may be lower. Assuming the window-relative counter starts at 0 at 06:00:
      - Tick 2 at 06:05: steps_10m (last 10 min, including the 05:55–06:05 period) = 100. steps_since_window (from 06:00) may be 50 (steps from 06:00–06:05, assuming some steps early in the window). Score depends on the exact signals; expected is high or low (not confirm on first tick alone unless score ≥ 85).
    - Expected: first window tick (05:55) is outside and scored 0; second tick inside is scored according to the current signals; no false early confirm.

## Proposed approach

(Narrative proposal for the implementer to veto early)

**Module structure**: `services/api/src/chronos/wake/scoring.py` with these components:

1. **Input models** (Pydantic):
   - `Signals`: 19 fields from telemetry + validation (`extra="forbid"`, bounded types).
   - `PreviousTick`: frozen dataclass with device_ts, battery_state, is_unlocked, score, decision, consecutive_high.
   - `EvalContext`: frozen dataclass with previous, window, day_state, rule_version, ticks_received_today.
   - `BreakdownItem`: rule_id, input, points, cap, note (stored as JSON).

2. **Derived facts computation** (pure helpers):
   - `compute_charger_disconnected(prev: PreviousTick | None, current_battery_state) -> bool`: true iff prev ∈ {charging, full} and current is unplugged.
   - `compute_consecutive_unlocked_ticks(prev: PreviousTick | None, current_is_unlocked: bool) -> int`: return count (0, 1, or 2+).
   - `minutes_since_window_start(window: Window, device_ts_dt: datetime) -> int`: used for rule inputs.
   - `is_in_window_gate(device_ts_dt: datetime, window: Window) -> bool`: wrapper of T1.3's `is_in_window`.
   - `should_dedupe(prev: PreviousTick | None, device_ts_dt: datetime, dedupe_min_sec: int) -> bool`: true iff seconds apart < dedupe_min_sec.

3. **Rule evaluation engine**:
   - `evaluate_rule(rule: Rule, signals: Signals, derived: dict[str, int | bool | str], rules: WakeRules) -> tuple[int, str | None]`: apply the rule to compute points and optional note. Returns (points, note). Handles:
     - Signal lookup (phone or derived).
     - Points threshold matching (first matching row wins).
     - Cap application.
     - `requires` condition checks.
     - Bonus consecutive logic (for rules with bonus_consecutive).
   - `evaluate_penalty(penalty: Penalty, signals: Signals, derived: dict) -> int`: compute penalty points (usually negative). Returns 0 if conditions not met, negative value if met.

4. **Reweighting logic**:
   - `should_reweight(pedometer_auth: PedometerAuth) -> bool`: true iff pedometer unavailable.
   - `get_effective_rule_weights(rules: WakeRules, pedometer_auth) -> dict[str, int]`: return caps/points per rule after reweighting.
   - `mark_pedometer_unavailable_rules(breakdown: list[BreakdownItem], reweight: bool)`: add note "pedometer unavailable" to affected rules that are zeroed out.

5. **Decision logic**:
   - `compute_decision(gate: EvaluationGate, score: int, thresholds: Thresholds, ctx: EvalContext, prev: PreviousTick | None) -> EvaluationDecision`:
     - If gate closed: return outside_window.
     - If day_state ∈ {confirmed, delivered}: return already_confirmed.
     - If dedupe: return ignored_dedupe.
     - If score ≥ strong: return confirm.
     - If score ≥ confirm and consecutive_high >= 2: return confirm.
     - If score ≥ confirm: return high.
     - Else: return low.

6. **Main evaluation function**:
   ```python
   def evaluate(signals: Signals, rules: WakeRules, now: datetime, ctx: EvalContext) -> Evaluation:
   ```
   - Parse device_ts and tz from signals.
   - Derive local_date using `local_date_for(device_ts, tz)`.
   - Check gate: is device_ts in window? (from `ctx.window` or compute fresh).
   - Compute derived facts (charger_disconnected, consecutive_unlocked, minutes since window start, etc.).
   - Apply dedupe check.
   - If dedupe: return with decision ignored_dedupe, score still computed.
   - Apply reweighting if pedometer unavailable.
   - Iterate rules in order, accumulate breakdown.
   - Apply penalties (order from YAML).
   - Clamp score to [0, 100].
   - Compute decision.
   - Compute consecutive_high (from history and current score + thresholds).
   - Return Evaluation with breakdown JSON serialized.

7. **Test structure** (`services/api/tests/wake/test_scoring.py`):
   - Unit tests for each helper function (charger transition, dedupe, reweighting).
   - Rule evaluation tests (each rule type, thresholds, caps, requires, bonuses).
   - Golden fixture tests (load JSON fixture mornings, replay each tick, compare expected decisions).
   - Hypothesis property tests:
     - `test_score_in_range`: score always ∈ [0, 100].
     - `test_monotone_in_steps`: if steps_10m increases and all else is constant, score is non-decreasing (or explain why not, e.g., penalties).
     - `test_outside_window_always_zero`: if device_ts outside window, score is 0 and decision is outside_window.
     - `test_deterministic`: same inputs produce equal output.
   - Edge case tests for each of the 20 scenarios above.

8. **Fixture mornings** (`services/api/tests/fixtures/wake/mornings/*.json`):
   - Hand-authored JSON files, one per morning scenario (9 required from T1.2 + 3 extra from acceptance criteria = 12 total minimum).
   - Format (see open question 11): `{ name, tz, rules_version|rules_file, day_kind, events: [{device_ts, signals..., expect: {gate, score, decision, consecutive_high}}], expect_day: {confirmed_at|null} }`.
   - Runner iterates events, feeds each into evaluate() with accumulated context, asserts expected outcomes.
   - Hand-checked against the worked example in docs/03 §1.

## Open questions

1. **`Signals` input model namespace**: Should the `Signals` Pydantic model be defined in `wake/signals.py` (same file as `SignalSpec` registry) or a new `wake/types.py`? T1.6's telemetry endpoint will also need to validate the input payload; should that reuse the same model?
   - **Proposal**: Define `Signals` in `wake/types.py` (new file, separates types from registry); T1.6's endpoint imports it and uses it for request validation. Registry (`signals.py`) stays independent for rule validation.

2. **`EvalContext` structure**: The exact shape of the server-side context passed into evaluate(). Must it include rule_version for determinism (for replay)? Should it carry a timestamp of when the previous tick was evaluated (for history computation)?
   - **Proposal**: Frozen dataclass `EvalContext` with:
     - `previous: PreviousTick | None` (includes device_ts, battery_state, is_unlocked, score, decision, consecutive_high, local_date).
     - `window: Window` (resolved, from T1.3).
     - `day_state: DayState` (for the already_confirmed check).
     - `rule_version_id: int` (for storage provenance).
     - `ticks_received_today: int` (for statistics).
     - Add `previous.local_date: str` to detect day boundary crossing.

3. **Derived facts structure**: Which derived facts are computed inside evaluate() vs. passed in via signals or ctx? Currently, docs/03 §3 lists charger_disconnected and consecutive_unlocked_ticks as "server-derived facts". Should they be part of the breakdown, and if so, how?
   - **Proposal**: Compute them inside evaluate() from signals and ctx.previous. Add them to the breakdown as special entries with `rule_id = "derived:charger_disconnected"`, etc., so they appear in the JSON and the owner can see the full derivation.

4. **`confirm_max_gap_min` constant**: The rule says "2 consecutive ticks ≤ 12 min apart". Is 12 min hardcoded in the logic, or should it be configurable in the schema as `thresholds.confirm_max_gap_min`? This affects T1.4's schema.
   - **Proposal**: Add `confirm_max_gap_min: int = 12` to the `Thresholds` Pydantic model in T1.4. Default 12, min 5, max 30. This requires a T1.4 plan update (schema addition).

5. **Decision precedence**: docs/03 §4 says "window gate first → decision outside_window score 0". What if the day_state is already confirmed? Does outside_window trump it, or does already_confirmed?
   - **Proposal**: Precedence is: (1) outside_window (gate closed), (2) already_confirmed (day_state ∈ confirmed/fallback/delivered), (3) ignored_dedupe (timestamp too close), (4) confirm (score thresholds), (5) high/low. Gate is evaluated first; if outside, return immediately with decision outside_window regardless of day_state.

6. **`foreground` rule**: docs/03-wake-engine.md §4 YAML has `- id: foreground` with `signal: wake_source` and `points: [["foreground", 40]]`. Does this mean only foreground wake_sources give points (40), and all other wake_sources give 0? Or is there a penalty for non-foreground?
   - **Proposal**: Rule as stated: if wake_source == "foreground", award 40 points (capped at 40). If wake_source ≠ "foreground", rule contributes 0 (the first row is not satisfied; no other rows).

7. **`requires` condition on walking_10m**: Rule walking_10m has `requires: { walking_conf: [medium, high] }`. If walking_conf is low, does the rule award 0 points with a note, or is the entire rule skipped?
   - **Proposal**: The rule is evaluated. If requires condition not met, the rule contributes 0 points with a note like `"requires walking_conf in [medium, high], got low"`. This is clearer for the breakdown than silently skipping the rule.

8. **Pedometer-based rules**: Docs/03-wake-engine.md lists the rules. Which ones depend on pedometer authorization? The YAML shows rules for steps_10m, walking_10m, steps_window. Are those the only ones?
   - **Proposal**: Mark on each `SignalSpec` in the registry whether it needs pedometer (add property `needs_pedometer: bool`). Rules that reference such signals are skipped when pedometer unavailable. Explicitly: `steps_10m` and `steps_since_window` and `walking_sec_10m` and `walking_conf` need pedometer. Rules: `steps_10m`, `walking_10m`, `steps_window`.

9. **Penalties AND-logic**: The example penalty `stationary_dominant` has `when: { stationary_sec_10m: ">= 540", steps_10m: "< 10" }`. Are all conditions AND-ed, or is there OR logic?
   - **Proposal**: All conditions in a penalty's `when` dict are AND-ed (all must be true for the penalty to apply). This is the safest and most intuitive.

10. **Breakdown ordering and structure**: docs/04-data-model.md §2.2 says `breakdown_json` contains `[{rule_id, input, points, cap, note}] + penalties + derived facts`. Is the order: rules first (in YAML order), then penalties (in YAML order), then derived facts? And does each entry include the signal input value?
    - **Proposal**: Order is (1) rules in YAML order, (2) penalties in YAML order, (3) derived facts (charger_disconnected, consecutive_unlocked if they affect scoring, etc.). Each BreakdownItem includes the input value (the signal value or derived value evaluated) so the owner can see what the rule saw.

11. **Fixture morning JSON format**: The acceptance criteria mention "golden fixture `tests/fixtures/wake/mornings/*.json`". What is the exact JSON structure? Should it include rule_version, the exact rules YAML inline, or a reference?
    - **Proposal**: Fixture format is:
       ```json
       {
         "name": "typical_weekday",
         "tz": "America/Los_Angeles",
         "rules_version": 1,
         "day_kind": "weekday",
         "events": [
           {
             "device_ts": "2026-10-06T06:48:00-07:00",
             "wake_source": "silent_push",
             "steps_10m": 0,
             "steps_since_window": 0,
             ...all 19 signal fields...,
             "expect": { "gate": "open", "score": 12, "decision": "low", "consecutive_high": 0 }
           },
           { "device_ts": "2026-10-06T06:53:00-07:00", ..., "expect": { "gate": "open", "score": 85, "decision": "confirm", "consecutive_high": 2 } }
         ],
         "expect_day": { "confirmed_at": "2026-10-06T06:53:00Z" }
       }
       ```
    - The runner iterates events, feeds each into evaluate() with accumulated context, and asserts expected outcomes.

12. **Hypothesis property strategies**: How should Hypothesis generate Signals, EvalContext, and rules for property tests? Steps can be 0–300, walking_conf is an enum, etc.
    - **Proposal**: Define Hypothesis strategies:
       - `signals_strategy`: generate random Signals with valid enums, bounded numeric fields, consistent tz values.
       - `window_strategy`: generate valid Windows (start < end, UTC times).
       - Property `test_score_in_range(signals, rules, now, ctx)`: assert 0 ≤ score ≤ 100 always.

13. **Monotonicity property statement**: docs/03 says "score ∈ [0,100], monotone in steps". But penalties can decrease the score if more steps trigger a penalty's inverse condition (e.g., if steps_10m < 10 AND stationary_sec_10m >= 540 then penalty). How is monotonicity stated precisely?
    - **Proposal**: "Score is monotone non-decreasing in steps_10m holding all other signals constant, except when a penalty's when-condition changes from false to true due to other signals. More precisely: if you increase only steps_10m, score ≤ new_score (may stay same, may increase, never decrease)." Test this hypothesis property.

14. **Performance target**: Is "< 10 ms per evaluation" a hard constraint or a goal? Should the implementer optimize (e.g., inline rule lookups), or focus on correctness?
    - **Proposal**: Correctness first. 10 ms is a goal for benchmarking later. If performance is a problem post-release, profile and optimize (probably in T6.1 or similar).

15. **Should evaluate() also return `next_tick_in_sec`?** (from the API response in docs/05 §2). The response includes this field for the app to know when to expect the next tick.
    - **Proposal**: No. The scheduler (T1.7) decides next_tick_in_sec based on day_state, window times, and whether the day is confirmed. The scoring engine does not know about scheduling.

## Summary

T1.5's scoring engine is the computational heart of the wake system. It must:

1. **Be pure**: no I/O, no side effects, deterministic.
2. **Reproduce the worked example exactly**: the breakdown shows 48 steps → 30, walking → 20, unlocked → 25, charger → 15, steps_window → 5, foreground → 0 = 85 ≥ strong 85 → CONFIRMED.
3. **Handle all edge cases**: window gate, DST, timezone changes, deduping, pedometer reweighting, penalties, bonus consecutives, day boundaries, missed ticks.
4. **Store the full breakdown**: every rule, penalty, derived fact, input, points, cap, and note goes into `breakdown_json` so the owner can tune and replay.
5. **Support replay**: evaluations are keyed by rule_version_id; the owner can re-score history under new rules (T1.8).
6. **Be testable**: property tests for score range and monotonicity; golden fixtures for known mornings; hypothesis for property-based fuzzing.

The 9 required fixture mornings (typical_weekday, night_check, snooze, pedometer_denied, early_walk, weekend, dst_fall_back, missed_ticks, foreground_only) plus 3 extras from acceptance criteria (3 a.m. phone check, unplug and go back to sleep, walk at 05:55 then 06:05) = 12 total minimum should all pass with the implemented rules.
