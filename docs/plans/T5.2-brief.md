# T5.2 — Delivery job (brief)

Branch `t5-2-delivery`, stacked on `t5-1-media-serving` (#52).

| ID | Task | Size | Depends | Acceptance criteria |
|---|---|---|---|---|
| T5.2 | Delivery job: visible push on confirm/fallback with reel id, text fallback when render failed, receipts, `POST /v1/admin/deliver`, `push-test` | M | T5.1, T1.7 | Fake Expo client: confirm → exactly one `reel_ready` push even if confirm and window-end race; failed render → `text_fallback` push with headlines |

Decisions made overnight under the owner's go-ahead:

1. **Delivery runs in the scheduler loop** (`run_deliveries` after each device pass), the same place silent ticks are sent. It is not a queued job: the telemetry request that confirms the day would otherwise have to enqueue while holding SQLite's write lock. Latency is at most 60 s after confirmation (G2 allows 90 s).
2. **Exactly once.** An atomic `UPDATE days SET delivered_at … WHERE delivered_at IS NULL` claim happens before sending. A failed send releases the claim for the next loop. The day then moves to `delivered` (audited `deliver_ok`), with `fallback_used=1` when it came from fallback.
3. **What is sent.**
   - Ready reel: `reel_ready` (payload per docs/05).
   - Failed reel, no brief, or render stalled > 30 min: `text_fallback` with up to 3 headlines.
   - Render still running: wait.
   - Visible pushes have `_contentAvailable: false` and `sound: default`; the token is never stored.
4. **Receipts** reuse T1.7's receipts job; delivery rows are ordinary `push_notifications`. **`push-test`** already exists from T2.6.
5. **`POST /v1/admin/deliver`** (bearer, 3/min): delivers the caller's day now. `force` moves an idle or monitoring day to `fallback` (audited `manual`) first.
6. **T1.7 scheduler simulations updated.** Days now end `delivered` after fallback/confirm, and the simulations see exactly one extra visible push.
