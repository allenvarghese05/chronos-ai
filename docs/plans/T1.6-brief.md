# T1.6 Brief: Telemetry endpoint + day state machine

## Task

**ID:** T1.6
**Title:** Telemetry endpoint + day state machine: `POST /v1/telemetry` (validation, clock skew, idempotent seq), `wake/state.py` transitions with audit rows, `GET /v1/day/*`, `PUT actual-wake`
**Size:** M (≈ 1 day)
**Depends:** T1.2 (bearer auth via `require_device`), T1.5 (scoring engine; `evaluate()`, `Signals`, `Evaluation` output types)
**Acceptance criteria** (from the plan):
1. Integration test drives a day from `monitoring` to `confirmed` with two high ticks.
2. Duplicate `seq` returns the same evaluation (idempotency).
3. Clock skew > 300 s → 422 with server_time in detail.
4. Transition audit rows match the state machine.

---

## Why it matters

T1.6 connects the wake-scoring engine (T1.5) to the state machine and persistence. Without it:

- **Telemetry vanishes**: the phone sends signals but they are not stored or scored.
- **No confirmation path**: even with high scores, the day never transitions from `idle` → `monitoring` → `confirmed`.
- **No audit trail**: state changes are invisible; the owner cannot debug why a day failed.
- **Idempotency breaks**: network retries cause duplicate evaluations; the score timeline becomes noisy.
- **Clock attacks**: a malicious phone (or one with a compromised system clock) sends device_ts far in the future, confusing window membership and timestamps.

T1.6 must be **correct**:
- The day-state machine transitions must match the diagram in docs/03 §5 exactly: `idle → monitoring` at window start, `monitoring → confirmed` on two consecutive high ticks (or one strong), `monitoring → fallback` at window end, `fallback → delivered` on push receipt.
- Every transition must be audited to `day_transitions` with its cause (evaluation / scheduler_window_start / scheduler_window_end / deliver_ok / manual), the evaluation_id that triggered it (or null for scheduler), and a precise UTC timestamp.
- Clock skew validation must reject anything > 300 s before 422 is returned and before the telemetry is stored (prevent corrupting the timeline).
- Idempotency must be strict: the same `(device_id, seq)` always returns the *stored* evaluation with 200, never re-evaluates (so retry=true in the app does not double-score).

---

## Governing decisions

| ID | Binding constraint |
|---|---|
| D04 | **Background wake mechanism**: silent pushes every `tick_interval_min` (5 min default) wake the app to sample signals. |
| D05 | **Signal set**: 19 fields readable in ≤ 30 s (steps, walking, unlocked, charger, app state, battery, auth status, versions). |
| D06 | **Scoring**: pure additive per-signal weights; every evaluation stored with full breakdown for replay. |
| D08 | **One reel per day**: a day may only transition to `confirmed` or `fallback` once; later triggers are no-ops. |
| D09 | **Eager render**: reel is ready before window opens; telemetry at window open triggers immediate scoring and (if high) delivery. |
| D16 | **LAN-only HTTPS**: bearer token + mkcert CA. Clock skew ≤ 300 s accepted; outside that → 422 with server time echoed. |
| D25 | **Timezone**: phone sends IANA tz on every event; server derives local date and window in that tz. Day boundary at 03:00 local. |

## Constraints

### Timing and budgets

- **Window membership**: computed from `device_ts` (with offset) in the device's `tz`, not server time. If device_ts is 05:59:50 UTC but local is 06:00:10 in tz=+05:30, gate is open.
- **Clock skew tolerance**: |device_ts (UTC) − server now (UTC)| ≤ 300 s (5 min), per docs/05 §0. Outside this, 422 clock_skew before any storage.
- **Idempotency window**: `(device_id, seq)` UNIQUE constraint persists indefinitely (no TTL); the same seq always returns the stored evaluation (200) even if called days later.
- **Deduplication threshold**: two snapshots < `dedupe_min` (default 2 min) apart are tagged ignored_dedupe (stored but not advanced in consecutive-high counter).

### Security

- **Bearer token**: required on all `/v1/telemetry`, `/v1/day/*` endpoints; validated via `require_device` dependency (T1.2 complete). 401 if missing, 403 if revoked.
- **Rate limiting**: 30 req/min per IP on telemetry (docs/05 §0); raises 429 with Retry-After header on exhaustion.
- **Clock skew defense**: reject device_ts > 300 s in the future or past before storing, returning 422 with server_time in the detail. Prevents a malicious phone from poisoning the timeline or manipulating window membership.
- **Input validation**: Pydantic `Signals` model with `extra="forbid"` rejects unknown fields; 422 validation error on schema mismatch.
- **SQL injection**: parameterized queries via SQLModel/SQLAlchemy; no string concatenation.

### Mobile-specific constraints

- **iOS background wake limits**: silent push delivery may be throttled by iOS; backoff is handled by T1.7 scheduler. T1.6 stores every event received.
- **Low Power Mode**: `low_power_mode=true` signals the app may not have background capabilities; the nightly report flags days with zero silent_push events (post-T1.6, in T1.8).
- **Device timezone changes**: when the owner travels and changes device.tz, the `days.tz` for that day stays frozen; the new tz applies from the next day boundary (03:00 local).

## Edge cases

### 1. Clock skew boundary

**Input:**
- device_ts: "2026-10-06T07:12:04Z" (UTC)
- server now: "2026-10-06T07:17:04Z" (UTC, +300 s skew exactly)

**Expected outcome:**
- 200 OK; event stored; clock skew not triggered (≤ 300 is accepted).

**Opposite:**
- device_ts: "2026-10-06T07:12:04Z"
- server now: "2026-10-06T07:17:05Z" (UTC, +301 s skew)
- Response: 422 clock_skew with detail including server_time.

### 2. Timezone change mid-day

**Scenario:** owner travels from Asia/Kolkata to America/New_York at 09:00 local.
- First tick at 09:00+05:30 → day created with tz=Asia/Kolkata.
- Device time zone changes to America/New_York.
- Second tick at local 22:00 (same UTC instant ≈ 09:30 old tz) sent as "2026-10-06T02:30:00-05:00" in new tz.
- Parsed to UTC: "2026-10-06T07:30:00Z".
- local_date_for(..., "America/New_York") → "2026-10-05" (previous calendar date in NY tz).

**Expected outcome:**
- telemetry_events.tz updated to "America/New_York" (from Signals payload).
- telemetry_events.local_date → "2026-10-05".
- Day row for "2026-10-06" (Asia/Kolkata) remains unchanged (tz frozen).
- New day row created for "2026-10-05" (America/New_York, if this is the first event of that date).
- EvalContext.ticks_received_today counts ticks for the day they belong to (day_transitions not triggered across dates).

### 3. Duplicate seq, same payload

**Input:** first POST /v1/telemetry with `seq=412`, steps_10m=48 → 200 with evaluation_id=9912, score=85, decision=confirm.

**Second identical request:** same payload, seq=412.

**Expected outcome:**
- UNIQUE(device_id, seq) constraint catches it.
- No new evaluation created; stored evaluation with id=9912 returned with 200 (not a 409 conflict).
- `raw_json` already stored matches the request.

### 4. Duplicate seq, different payload

**Input:** first POST with seq=412, steps_10m=48 → evaluation_id=9912, score=85, decision=confirm.

**Second request:** seq=412 but steps_10m=60 (different snapshot).

**Expected outcome:**
- UNIQUE(device_id, seq) constraint blocks insert at the telemetry_events level.
- Gracefully return the first evaluation (id=9912, score=85) with 200.
- Log a warning: "seq 412 resubmitted with different payload".

### 5. Out-of-window event (before window opens)

**Input:** 05:59 local, 30 min before window start (06:30). device_ts earlier than window_start_utc.

**Expected outcome:**
- `gate: closed`.
- `decision: outside_window`.
- `score: 0`.
- Day row created with state=idle (not monitoring, until next in-window event).
- Event stored; no state transition; no audit row.

### 6. Consecutive high ticks leading to confirm

**Scenario:**
- Tick 1 at 07:00: score=72 (≥ confirm 70). decision=high, consecutive_high=1.
- Tick 2 at 07:05: score=75 (≥ confirm 70). decision=confirm, consecutive_high=2.
- ≤ 12 min gap (confirm_max_gap_min).

**Expected outcome:**
- Day state transitions: monitoring → confirmed.
- DayTransition row: from_state=monitoring, to_state=confirmed, cause=evaluation, caused_by_evaluation_id=<id of tick 2>, at=<server time>.
- days.confirm_evaluation_id = id of tick 2.
- days.confirmed_at = UTC timestamp of this transition.
- Response to tick 2: day_state=confirmed, decision=confirm, confirm_reason="consecutive".

### 7. Strong single tick (score ≥ strong)

**Scenario:**
- Tick 1 at 07:00: score=90 (≥ strong 85, and ≥ confirm 70).

**Expected outcome:**
- Day state transitions: monitoring → confirmed (on a single high score if strong threshold met).
- decision=confirm, confirm_reason=strong.
- No prior tick was checked (first tick of the day or after the deduplication window).

### 8. Late outbox event for past date

**Scenario:** phone's outbox retries an old event; device was offline, date boundary passed.
- Original event: local_date="2026-10-05" at 05:00 UTC (before 03:00 local boundary in +05:30 tz).
- Outbox retries at "2026-10-06" 08:00 UTC, but device_ts in payload is still "2026-10-05T01:30:00+05:30" (same original value).
- seq=410, device_id=5.

**Expected outcome:**
- telemetry_events.device_ts = "2026-10-05T01:30:00+05:30".
- telemetry_events.local_date = "2026-10-05" (derived from payload, not current day).
- telemetry_events.received_at = "2026-10-06T08:00:00Z" (server now).
- Evaluated against the previous tick of "2026-10-05" (EvalContext.previous fetched from (device_id=5, local_date="2026-10-05")).
- Stored successfully; state transitions for "2026-10-05" day (if any), not "2026-10-06".

### 9. Already confirmed (no double transitions)

**Scenario:**
- Day state: confirmed (from an earlier evaluation).
- New tick arrives at 07:30, score=88 (high).

**Expected outcome:**
- decision=already_confirmed (enum value defined).
- No state transition.
- Event and evaluation stored (useful for tuning).
- DayTransition row NOT created.
- Response includes day_state=confirmed (unchanged).

### 10. Revoked device

**Input:** bearer token valid but device.status = "revoked".

**Expected outcome:**
- `require_device` dependency raises ProblemException(403, "revoked").
- No telemetry stored; no evaluation; no DB changes.

## Proposed approach

**Three modules:**

1. **`chronos/api/telemetry.py`**: Fast API router with:
   - `POST /v1/telemetry(device: Device, body: Signals, rate_limit_dep, session)`:
     - Validate clock skew (|device_ts − now| ≤ 300); if exceeded, raise 422 with server_time.
     - Check UNIQUE(device_id, seq) idempotency key; if exists, return stored evaluation with 200.
     - Derive local_date from device_ts + tz via `local_date_for()`.
     - Ensure day row exists; create if missing (state=idle by default, auto-transition to monitoring if in-window).
     - Get EvalContext.previous (latest evaluation of the same (device_id, local_date)).
     - Call `evaluate(signals, rules, now, ctx)`.
     - Store telemetry_events + wake_evaluations in one transaction.
     - Apply state machine (T1.6 will define; see question 6 for confirm decision handling).
     - Return 200 with evaluation + day_state.

2. **`chronos/wake/state.py`**: Pure state-machine module with:
   - `apply_transition(day: Day, evaluation: Evaluation, cause: TransitionCause, session) -> DayTransition | None`:
     - Take the day row and evaluation result.
     - Determine if a state transition should occur (idle → monitoring at window start, monitoring → confirmed on confirm decision, etc.).
     - Insert a DayTransition row if transition occurs.
     - Update day.state, day.confirmed_at, day.confirm_evaluation_id atomically.
     - Return the transition record (or None if no transition).

3. **`chronos/api/day.py`**: Router with:
   - `GET /v1/day/today`: derive local_date from device.tz + now, fetch day row, return day state + score_timeline or 404.
   - `GET /v1/day/{local_date}`: fetch day row, return 200 or 404.
   - `PUT /v1/day/{local_date}/actual-wake`: update days.actual_wake_local, return updated day.

**Integration points:**
- `POST /v1/telemetry` calls `apply_transition()` after storing evaluation.
- `apply_transition()` is pure enough for unit testing with a fake now.
- All three modules are wired into `create_app()` router list.

## Risks

### Most likely to go wrong

1. **Idempotency not truly idempotent**:
   - Risk: second POST with same seq is processed as a new evaluation, returning a different score or decision.
   - Test: mock DB to simulate UNIQUE constraint violation on the second insert; verify 200 and same evaluation_id returned.

2. **Clock skew validation order**:
   - Risk: clock skew is not checked before INSERT, so a malicious device poisons the DB with far-future device_ts.
   - Test: POST with device_ts +400 s in the future; assert 422 is returned *before* querying DB; no telemetry_events row created.

3. **State transition not atomic**:
   - Risk: evaluation stored, but day.state update fails; day remains in old state; next tick re-confirms or double-transitions.
   - Test: wrap INSERT evaluation + UPDATE day in a transaction; mock SQLModel session.rollback on conflict.

4. **Previous tick lookup for EvalContext crosses date boundary**:
   - Risk: a late outbox event from yesterday gets compared against today's previous tick; consecutive_high counter is wrong.
   - Test: fixture with two days; late event from day 1 after day 2 starts; verify previous is None (or from day 1).

5. **Window membership computed in server time, not device tz**:
   - Risk: 05:59 UTC in +05:30 tz is 06:29 local, but code uses window.start_utc without tz conversion.
   - Test: freeze time, set device.tz, POST with device_ts in tz, verify gate based on *local* time.

### How tests will catch these

- **Idempotency**: integration test with two identical POST requests; assert same evaluation_id and score.
- **Clock skew**: parametrized test (device_ts in -301..+301 s range); assert 422 only outside [−300, +300].
- **Atomicity**: mock SQLModel session with commit/rollback spies; verify both INSERT and UPDATE happen in one transaction.
- **Previous tick isolation**: fixture with two local_dates; late event with previous day's seq; verify consecutive_high stays per-day.
- **Window membership**: parametrized test with tz + device_ts; verify gate against local time in the tz, not server time.

## Open questions

1. **Reuse `Signals` as the telemetry request body?** The task description says reuse the Signals model (T1.5). Are there any extra fields the response adds (e.g., raw_json, received_at) that should not be in the request, or is the request body exactly the Signals model?

2. **Clock skew 422 detail format:** Should the 422 clock_skew response detail be `"detail": "Device clock is 301 seconds in the future. Server time: 2026-10-06T07:17:05Z"`, or a separate `server_time` field in the problem object (breaking RFC 9457 strictly, but may be easier to parse on the app)?

3. **Persist `Evaluation.breakdown_json` losslessly:** The Evaluation model includes breakdown as a list of RuleBreakdown objects (with rule_id, input, points, cap, note). Should this be serialized as `model_dump_json()` and stored in wake_evaluations.breakdown_json, or parsed back out in the POST response? Do we keep scalar columns (score, decision, consecutive_high, gate) separate for querying/sorting?

4. **Days row creation on first event:** When the phone's first event arrives for a (device, local_date), the days row should be created with:
   - tz: from the Signals payload (frozen at creation).
   - kind: computed via `day_kind(local_date, rules_config)`.
   - window_start_utc, window_end_utc: computed via `window_for()`.
   - state: should it be `idle` or `monitoring`? If now ≥ window_start_utc, should it auto-transition to monitoring? Or should T1.7's scheduler be responsible for the idle→monitoring transition? (Affects whether the first tick auto-evaluates or waits.)
   - ticks_received: increment from 0 to 1.

5. **EvalContext.previous lookup:** EvalContext.previous should be built from the latest wake_evaluation of (device_id, local_date) ordered by device_ts desc, limit 1. But if that evaluation's decision is `ignored_dedupe`, should it be skipped and the one before it used? Or is `ignored_dedupe` treated as a valid previous tick for consecutive counting?

6. **Confirm decision → state transition:** When evaluation.decision = `confirm`, the endpoint should:
   - Check if day.state is already `confirmed` or `delivered` → store evaluation with decision=`already_confirmed`, no transition, no audit row.

Approved with the orchestrator's recommendations:

1. Request body is `Signals` exactly.
2. 422 `clock_skew` carries a structured `server_time` field plus detail text.
