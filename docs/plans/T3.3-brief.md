# T3.3 — Normalise + dedupe + rank + select (brief)

Branch: `t3-3-normalise-rank-select`, stacked on `t3-2-feed-fetchers` (PR #43, not yet merged).
Rebase onto `main` after #43 merges.

## 1. Task

| ID | Task | Size | Depends | Acceptance criteria |
|---|---|---|---|---|
| T3.3 | Normalise + dedupe + rank + select: canonical URLs, simhash, scoring formula, quotas, category minimums | M | T3.2 | Property test: dedupe idempotent/order-independent; selection returns exactly `total_stories` with category minimums when possible; golden selection for a fixture day |

M3 "Done when": `chronos run --date today --stages ingest,script` produces a validated
`ReelScript` from live sources with Ollama, and a template script when Ollama is unavailable.
T3.3 supplies the ordered story list that T3.4's script step consumes.

## 2. Why it matters

T3.4's prompt and validator only accept stories from the candidate list T3.3 returns. The
validator rejects any `item_id` not in the list and any `source_url` that differs from the item's
canonical URL (docs/06 §4). So T3.3 decides what the owner hears every morning, and its
canonical URL is the contract T3.4 validates against. If it is wrong:
- duplicates waste one of the 6 slots;
- stale items appear;
- a category is missing;
- quotas are ignored and one feed floods the reel;
- non-deterministic ordering makes the golden tests and replays flaky.

## 4. Current state (after T3.2)

- `chronos.content.fetchers.ParsedItem` (frozen dataclass): `external_id, url, title, summary,
  author, published_at, image_url, extra_json`. HN items carry `extra_json = {"points": int|null}`.
  HF items carry `{"upvotes": int}` (when present). arXiv carries `{"categories": [...]}`.
- `chronos.content.ingest.fetch_all(client, session, config, now) -> IngestReport` gives

- `chronos.content.sources.SourcesConfig.selection: SelectionConfig` with fields
  `total_stories=6`, `category_min={"ai":2,"world":1,"india":1}`, `freshness_hours=20`,

  validated against `ContentCategory`.
- `chronos.models.content.Item` (table `items`, migration 0003):
  `UNIQUE(source_id, external_id)`, `INDEX(url_hash)`, `INDEX(published_at)`,

- `chronos.models.content.Source`: `id, key, kind, url, category, enabled, quota, weight,
  min_points, …`.
- `BriefItem(role ∈ {primary, mention})` requires a `briefs` row, which T3.4 creates.
- HF fetcher (`hf_daily_papers.parse`) does **not** extract a published date today, so every HF
  item has `published_at = None`.
- `hypothesis==6.168.5` is already a dev dependency. `python-dateutil` is **not** installed
  (deferred to T3.3 by the T3.2 owner gate).
- Coverage gate: `chronos.content` ≥ 85 % (justfile, T3.2).

## 5. Inputs and outputs

**In**
- `list[SourceFetchOutcome]` from `fetch_all`, plus their `Source` rows.
- `SelectionConfig`.
- `now: str` (UTC ISO).

**Out**
1. **Persisted items.** Rows upserted into `items` by `(source_id, external_id)`, with:
   - canonical `url`;
   - `url_hash` = sha256 hex of the canonical URL;
   - `title_simhash` (64-bit, stored encoded);
   - `summary` capped at 1 000 chars;
   - `published_at` falling back to `fetched_at`.
2. **Selection.** An ordered `list[SelectedStory]` in narrative order (AI, then tech, world,
   India). Each entry carries `item_id`, `category`, `score`, `source_key`, and the
   `mention_item_ids` of its duplicates in other sources (for T3.4 to write as
   `brief_items.role = mention`).

No endpoint, job handler or CLI command in this task: job wiring is T3.5. The output contract is
a Python API.

## 6. Constraints

- **Ingest budget.** < 20 s total (docs/07 §5). Dedupe over ~150 items is O(n²) simhash
  comparisons, which is trivial.
- **Determinism.** Same inputs give the same selection. Ties break on `(score desc,
  published_at desc, item_id asc)`. Clustering must be order-independent (acceptance criterion).
- **Untrusted feed text.** Never evaluate it. Canonicalisation must not fetch anything (no
  redirect following to resolve AMP or short links).
- **SQLite constraints.** The signed simhash goes through `encode_simhash`. `published_at` must
  be ISO text so `INDEX(published_at)` orders correctly.

## 7. Edge cases

| # | Case | Example input | Expected |
|---|---|---|---|
| 1 | Tracking params | `https://BBC.co.uk/news/x/?utm_source=rss&fbclid=1&ref=hp#top` | `https://bbc.co.uk/news/x` |
| 2 | Meaningful query kept and sorted | `https://a.com/p?id=3&utm_medium=x&b=2` | `https://a.com/p?b=2&id=3` |
| 3 | AMP variants | `https://www.ndtv.com/india-news/story-123/amp/1`, `…?amp=1`, `https://amp.example.com/x` | Map to the non-AMP URL when the pattern is known (Q4), else unchanged |
| 4 | Default port, `www.` | `https://www.a.com:443/x` | `https://a.com/x` (strip `www.`? see Q4) |
| 5 | Same story, two sources, same URL | BBC and CBS both link `a.com/x` | One cluster. The primary is the higher `source.weight` (BBC 1.0 > CBS 0.8); the other is a mention; `n_sources = 2` |
| 6 | Near-duplicate titles | "India launches lunar probe Chandrayaan-4" vs "Chandrayaan-4: India launches lunar probe" | Same cluster if Hamming distance ≤ 6 and both within 36 h |
| 7 | Same title, > 36 h apart | Two "Markets update" items 2 days apart | Not merged |
| 8 | Same source, near-duplicate | A feed republishes with a new guid | Clustered too (dedupe is not limited to cross-source); `n_sources` counts distinct sources only |
| 9 | Missing `published_at` | HF items (no date today) | `published_at := fetched_at`, so recency is 1.0 |
| 10 | Future-dated item | `published_at` 3 h after `now` | Clamp age to 0 (recency 1.0); do not drop |
| 11 | Older than `freshness_hours` | BBC item 30 h old | Ignored, unless its category would otherwise be empty (docs/06 §1) |
| 12 | Category short | Only 1 AI item survives, but `category_min.ai = 2` | Take 1 AI; fill the remaining slots by score ("when possible") |
| 13 | Quota binds | HF quota 2, three top-scoring HF items | At most 2 HF selected |
| 14 | Too few items overall | Only 3 items in total | Return 3, not exactly 6 ("when possible"). docs/02 §7: < 4 items means template script from cached items (T3.4/T3.5 decide) |
| 15 | Empty or whitespace title | `title = "   "` | Skip the item (never persisted; T3.4 needs a headline) |
| 16 | Empty URL | HF item with no id gives `url = ""` | Skip (T3.4 validates `source_url`) |
| 17 | Re-ingest same item | Same `(source_id, external_id)` next morning | Upsert in place; `id` stable; `fetched_at` keeps the first value (Q5) |
| 18 | Popularity missing | HN `points: null` (Algolia failed), arXiv | popularity = 1.0 |
| 19 | Huge popularity | HN item with 4 000 points | Capped at 1.6 |
| 20 | Unicode titles | Hindi or accented words, curly quotes | Simhash tokeniser: NFKC, casefold, `\w+` tokens, so it must not crash |
| 21 | `category_min` sum > `total_stories` | `{ai:4, world:3}` with total 6 | Fill mins in narrative order until `total` is reached; never exceed `total` |
| 22 | Disabled source's old items | Source disabled yesterday | Selection uses only items fetched in **this** run (Q3) |

## 8. Proposed approach (proposal; the owner may veto)

1. **`content/normalise.py`** (pure):
   - `canonical_url(url) -> str`;
   - `url_hash(url) -> str`;
   - `title_tokens(title)`;
   - `simhash64(title) -> int` (blake2b-64 per token, standard 64-bit simhash, no new
     dependency);
   - `hamming(a, b)`;
   - `normalise(parsed: ParsedItem, now) -> NormalisedItem | None` (skips edge cases 15/16, caps
     the summary, applies the date fallback).
2. **`content/store.py`**: `upsert_items(session, source, items, now) -> list[Item]` with
   SQLite `INSERT … ON CONFLICT(source_id, external_id) DO UPDATE`, in one short transaction per
   source.
3. **`content/dedupe.py`** (pure): `cluster(candidates) -> list[Cluster]`.
   - Union-find over pairs that share a `url_hash`, or have simhash distance ≤ 6 within 36 h.
   - The result is a set partition, so it is order-independent by construction.
   - Primary = max `(source.weight, popularity, published_at, -item_id)`.
4. **`content/rank.py`** (pure):
   - `score(cluster, weight, now, cfg)` implements the docs/06 §3 formula: recency is linear
     from 1.0 at 0 h to 0.3 at `freshness_hours`; popularity uses the log scale in Q2; the boost
     is `1 + 0.25 × (n_sources − 1)`.
   - `select(clusters, sources, cfg, now) -> list[SelectedStory]`:
     - drop stale clusters except to rescue an empty category;
     - fill `category_min` in narrative order (best per category);
     - fill the rest by score, honouring each source's `quota`;
     - sort into narrative order.
5. **`content/selection.py`** (thin orchestrator):
   `build_candidates(session, outcomes, cfg, now) -> list[SelectedStory]`. It calls
   normalise → upsert → cluster → select. T3.5 will call it from the `ingest` job.
6. **Tests:**
   - unit tables for the canonical URL cases;
   - simhash known pairs;
   - hypothesis properties: clustering is idempotent and order-independent; selection length is
     `min(total, available)`; quotas are never exceeded; minimums are met when there is supply;
   - an upsert integration test;
   - golden selection: a new `tests/fixtures/content/day_2026-10-06.json` (~30 ParsedItems
     across the 8 sources with planted duplicates, stale items and a quota squeeze) maps to
     `day_2026-10-06.expected.json` (ordered `(source_key, external_id, category)`).

## 9. Risks

| Risk | How a test catches it |
|---|---|
| Over-aggressive dedupe merges different stories with similar short titles ("Live updates") | Golden day includes two distinct "Live:" headlines; also a minimum-token rule (titles with < 4 tokens only merge on `url_hash`; see Q6) |
| Order-dependent clustering (greedy first-match) | Hypothesis: shuffle the input, compare partitions as sets of frozensets |
| Canonicalisation breaks URLs (drops a meaningful query param) | Table test keeps `id=` / `p=` style params; only the deny-listed tracking params are stripped |
| Signed/unsigned simhash mix-up | Round-trip a value ≥ 2⁶³ through upsert and read-back |
| Non-deterministic ties | Golden test run twice with shuffled input gives an identical ordered list |
| T3.4 contract drift on canonical URL | `SelectedStory` exposes the stored `items.url`; T3.4 compares against exactly that field |

## 10. Open questions

1. **`python-dateutil`.** The T3.2 gate deferred it to T3.3. feedparser already normalises RSS
   and Atom dates, and the only other source of dates is HF JSON (ISO-8601, which
   `datetime.fromisoformat` handles in 3.12). **Proposal: do not add dateutil**; use the stdlib.
   Approve?
2. **Popularity scale.** docs/06 only says "log-scaled to [1, 1.6]". **Proposal:**
   `1 + 0.6 × min(1, log10(1+x) / log10(1+cap))` with `cap = 300` HF upvotes and `cap = 1000`
   HN points; arXiv and RSS = 1.0. Hard-coded constants or new `selection:` keys in
   `sources.yaml`? **Proposal: constants** in `rank.py` (no schema change).
3. **Candidate pool.** Select only from items fetched in **this** run (the `fetch_all` outcomes),
   or from all `items` rows fetched within `freshness_hours`? The latter keeps a source that
   returned 304 (not modified) in play, because a 304 yields no items. **Proposal: the DB window**
   (`fetched_at` or `published_at` within the last 36 h, enabled sources only). It handles 304s
   and partial outages correctly.
4. **Canonical URL policy.**
   - (a) Strip a leading `www.`?
   - (b) Which AMP patterns are "known"?

   **Proposal:** (a) yes, but for hashing only; store the URL with its original host minus
   tracking params, so the link in the app still works. (b) A trailing `/amp` or `/amp/<n>`
   path segment, an `amp=1` / `outputType=amp` query, and an `amp.` host prefix. Approve, or
   keep the stored URL and hash identical?
5. **Upsert semantics.** On re-fetch of an existing `(source_id, external_id)`, refresh `title`,
   `summary`, `image_url` and `extra_json` (points change through the morning), but keep
   `fetched_at` as first seen? **Proposal: yes.**
6. **Short-title guard.** Allow simhash merging only when both titles have ≥ 4 tokens, to avoid
   merging generic headlines. It is not in docs/06. **Proposal: add it**, documented in the plan.
7. **HF published date.** The HF fetcher (T3.2) drops `publishedAt`, so every HF paper looks
   brand new. May T3.3 make the small fix in `hf_daily_papers.parse` (and its golden file) to
   read `publishedAt`? **Proposal: yes.**
8. **Brief mentions.** Mentions are returned in `SelectedStory.mention_item_ids` for T3.4 to
   write as `brief_items.role = mention`, because a `briefs` row does not exist until T3.4.
   **Proposal: confirm T3.3 writes no `brief_items`.**

## 11. Owner gate decision (Phase 1 → Phase 2)

Owner answered **"Approve all"** (2026-11-08) to every proposal in §10:

1. No `python-dateutil`; stdlib `datetime.fromisoformat` plus feedparser's parsed dates.
2. Popularity = `1 + 0.6 × min(1, log10(1+x)/log10(1+cap))`, cap 300 (HF upvotes) / 1000
   (HN points), constants in `rank.py`.
3. Candidate pool = DB window: enabled sources' items with `fetched_at` or `published_at`
   within the last 36 h.
4. `www.` and the known AMP patterns are removed for the **dedupe hash only**; the stored `url`
   keeps its host (tracking params stripped, query sorted, fragment and trailing `/` dropped).
5. Upsert refreshes title/summary/image/extra/author/url; `fetched_at` stays first-seen.
6. Simhash merge only when both titles have ≥ 4 tokens.
7. T3.3 fixes `hf_daily_papers.parse` to read `publishedAt`.
8. T3.3 writes no `brief_items`; mentions travel in `SelectedStory.mention_item_ids`.

**Implementation-time owner decision (2026-11-08):** near-duplicate titles use stopword-filtered
word-set Jaccard ≥ 0.6 instead of simhash Hamming ≤ 6 (calibration test showed simhash cannot
separate reworded duplicates from distinct stories). Recorded as ADR D35; docs/06 §2.3 updated.

**Second implementation-time owner decision (2026-11-08):** after a live Sunday run selected only one
AI story, stale stories now top a category up to its `category_min` (ADR D36); a category without a
minimum still gets at most one stale story when empty.
