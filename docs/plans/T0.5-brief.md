## Why it matters

T0.5 establishes the visual rendering pipeline. It creates:
- A fully configured Remotion project that generates the final 1080×1920 MP4 "Morning Reel" video through `npx remotion render` invoked by the Python API worker (T4.5)
- The `MorningReel` composition (1080×1920, 30 fps) and the `CoverScene` (now) plus stubs for `StoryScene`, `OutroScene`, and `WordCaptions` (later in T4.4)
- A hand-written zod schema for `ReelProps` that mirrors the API's Pydantic model; in T3.4 `just gen-types` will generate the authoritative zod from JSON schema to replace it, ensuring type safety between Python and React
- Fixtures and vitest unit tests for timing maths (frame calculations) and caption line-breaking (both needed in T4.4)
- CI integration: the `renderer` job in `ci.yml` runs `biome ci`, `tsc --noEmit`, `vitest run`, and a still smoke render at frame 60, with the `smoke.png` artefact proving the Remotion → PNG pipeline works on ubuntu-latest without Xcode or a display

Without T0.5, the media pipeline has no output stage; the API cannot invoke Remotion; the CI cannot validate TypeScript/lint/test in the renderer; and the owner cannot see a visual proof of concept (the smoke still).

The design direction (docs/07-media-pipeline.md §6) is locked in now: vertical, generous margins, 3–5 word captions, slow motion, strong type/contrast rules. Every scene component built in T4.4 must respect these rules via code invariants (minimum font sizes, contrast checks, safe area offsets), not manual review.

## Inputs and outputs

### Inputs (at runtime, from the API worker via `npx remotion render`)

**Props JSON file** (`reel.json`):
```typescript
ReelProps = {
  localDate: string;           // "2026-10-06"
  greeting: string;            // "Good morning"
  tone: "friendly" | "formal"; // style hint for motion
  audio: {
    src: string;               // "public/renders/<reel_id>/voice.mp3"
    durationSec: number;       // 61.4
  };
  scenes: Array<{
    index: number;
    type: "cover" | "story" | "outro";
    title?: string;            // headline
    body?: string[];           // bullet points
    media?: { type: "image" | "video" | "gradient"; url?: string };
    source?: { name: string; url: string };
    startSec: number;
    endSec: number;
  }>;
  captions: Array<Array<{     // [scene][word]
    w: string;                 // text
    s: number;                 // start sec
    e: number;                 // end sec
  }>>;
  theme: "dawn" | "mono" | "ink";
  attribution: string[];       // Pexels, edge-tts, etc.
}
```

**Audio file:** `public/renders/<reel_id>/voice.mp3` (or .wav for fallback)

**Media files** (if used): `public/renders/<reel_id>/assets/scene-NN.jpg` (images) or `scene-NN.mp4` (b-roll)

### Outputs (from `remotion render` CLI)

**Primary:** `out/reel.mp4` (1080×1920, 30 fps, H.264 video + AAC audio, duration ≈ 61 s, ~15–25 MB)

**Thumbnail (by render.py):** `out/thumb.jpg` (still at frame 45, downscaled for app feed)

**CI smoke still (by `just check-renderer`):** `out/smoke.png` (single frame at frame 60, PNG for artefact storage)

**Metadata (recorded by render.py):** sha256, duration, codec, fps, bitrate

## Constraints

### iOS / Media player constraints (from docs/07-media-pipeline.md §6)
- **Safe area:** 220 px top (status bar + safe area) and 220 px bottom (gesture zone + home indicator); content must fit within 1080×1480 (or leave margins on purpose)
- **Vertical delivery:** 1080×1920 portrait only; no rotation
- **Legibility rules (code-enforced, not manual):** headline ≥ 64 px, bullets ≥ 40 px, captions ≥ 52 px, contrast ≥ 4.5:1 against any background (via a scrim over media)
- **Duration:** ≤ 2 minutes total (target ≈ 60 s); no hard stop, but exceeding 2 min risks Apple's video frame-rate limits on some iPhones

### Rendering budget (16 GB M1 Pro, from docs/07-media-pipeline.md §5)
- **Render time target:** 90–180 s for a full 1850-frame reel with video layers
- **Concurrency:** Remotion concurrency=2 (two parallel ffmpeg instances); serial worker ensures only one render at a time per laptop
- **Memory:** Chrome headless shell + Remotion + ffmpeg together must fit in ~14 GB (leaving 2 GB for OS); model unloaded before render

### Build and CI constraints
- **Browser cache:** Remotion downloads Chrome headless shell to `packages/renderer/node_modules/.remotion` on first `npx remotion render` or `npx remotion browser ensure`; GitHub Actions cache at CI to avoid re-downloading on every PR
- **No display needed:** Headless shell runs without X11/Wayland on ubuntu-latest
- **Isolated React version:** This project's React (≥16.8.0, pinned) is separate from the mobile app's React; no shared react/react-dom across the monorepo projects (each has its own node_modules via pnpm)

### Security constraints (D16 + D23)
- No hardcoded API URLs, tokens, or media paths in the code; all injected via props JSON at render time
- No external network calls inside compositions (purely functional React)
- No file I/O from the renderer itself (the Python runner orchestrates file moves)

## Edge cases

### 1. Cover scene only (T0.5 scope)
- **Input:** Minimal fixture with only a cover scene (no story/outro yet)
- **Expected:** MorningReel composition renders, frame 60 is a still of the cover with date and greeting, no videos/images in the cover (gradient only)

### 2. Missing or malformed props
- **Input:** `sample-reel.json` has a scene with no `startSec`/`endSec`, or `audio.durationSec` is null
- **Expected:** zod schema validation fails during `npx remotion still --props=...`; Remotion exits with a clear error message; CI fails

### 3. Audio duration mismatch
- **Input:** `audio.durationSec = 65` but `captions` end at 60 sec
- **Expected:** Rendering does not error (Remotion will pad with silence or cut); test assertion checks that the render completes and has valid duration; a warning may be logged by the Python runner in T4.5, but T0.5 vitest tests do not validate audio length (that is T4.3–T4.5 smoke tests with real audio)

### 4. Empty captions array
- **Input:** `captions = []`
- **Expected:** Composition renders without the `WordCaptions` layer; cover and stories render (if present) without karaoke text; no error

### 5. Gradient scene (no media URL)
- **Input:** Scene with `media = { type: "gradient", query: "blue-sunrise" }`
- **Expected:** Renderer draws an animated gradient background; no image fetch; completes in under 5 s per scene

### 6. Very long headline
- **Input:** Story scene with 20-word headline and `fitHeadline()` must fit it in 3 lines
- **Expected:** `fitHeadline()` vitest test checks that the line count does not exceed 3 and the font size does not drop below 32 px (absolute minimum); a warning is logged; the renderer places the text left-aligned in a 60-char limit (TBD in T4.4); acceptance test: the headline is visible and not truncated

### 7. High scene count
- **Input:** 8 story scenes + cover + outro (9 total) with 30 fps × 7 sec per scene ≈ 1890 frames
- **Expected:** Render time ~120–150 s; no memory overflow (vitest does not test this; it is a load test for T4.5)

### 8. Chrome headless shell download blocked (no internet)
- **Input:** First CI run after a cache miss; no network access to GitHub (cannot happen in practice on ubuntu-latest)
- **Expected:** Remotion CLI fails with a clear "cannot download browser" message; CI job fails; nothing is uploaded as artefact; developer must retry or `npx remotion browser ensure` locally with internet

### 9. Malformed caption timings (out of order)
- **Input:** Captions JSON has `{ w: "a", s: 10, e: 15 }` followed by `{ w: "b", s: 8, e: 12 }` (overlapping, end before start of previous)
- **Expected:** zod schema validates `s <= e`, but does NOT validate order across words (that is a vitest test in the caption line-breaking suite in T4.4); Remotion renders captions at their specified times; earlier test in T4.3 ensures whisper output is sorted

### 10. Theme enum mismatch
- **Input:** `theme: "sunset"` (not one of "dawn", "mono", "ink")
- **Expected:** zod schema validation fails; Remotion exits with a clear error; CI fails; developer must run `just gen-types` if coming from an API change, or fix the fixture

## Proposed approach

1. **Project scaffold** (`src/`, build config, package.json): Create `packages/renderer/` with a standard Remotion project tree. Use pnpm 12.10.1 pinned in `packageManager`. Add `pnpm-workspace.yaml` for consistency (nodeLinker: hoisted). `remotion.config.ts` sets fps=30, width=1080, height=1920. `vitest.config.ts` sets up a basic test environment (no Canvas/DOM unless using a library). `biome.json` enforces the same style as `apps/mobile` (trailing commas, print width 100). TypeScript strict mode on. Gitignore Remotion and pnpm specific paths.

2. **Composition structure** (`src/compositions/MorningReel.tsx`, scenes stubs): Define `MorningReel` as a Remotion composition accepting `ReelProps`. Loop through `props.scenes`, render each as a `<Sequence>` with `startFrame`/`endFrame` calculated from seconds. CoverScene is the only working scene now (date, greeting, animated gradient background, no media). StoryScene and OutroScene are stubs returning null (built in T4.4).

3. **Design tokens** (`src/design/tokens.ts`): Centralize type scale (1.25), color palette per theme, spacing grid (24 px), spring animation configs, safe area offsets. Reference in every component to ensure consistency and make it easy to tweak in one place.

4. **Fonts** (`src/design/fonts.ts`): Import from `@remotion/fonts` (self-hosted Inter Tight and JetBrains Mono via the library); set up `loadFont` calls. Decision on network vs. self-host pending (open question #2).

5. **Hand-written zod schema** (`src/schema.ts`): Mirror the API's Python `ReelProps` in zod; validate `localDate` format, `audio.durationSec > 0`, `scenes[].startSec <= endSec`, `theme` enum, etc. Will be replaced by generated schema in T3.4 after `just gen-types` exists. Add a small TypeScript test to parse `sample-reel.json`.

6. **Fixture** (`src/fixtures/sample-reel.json`): A minimal valid JSON fixture with one cover scene (index 0, "Monday, 6 Oct", no media), 30 fps, 30 frames duration (1 sec), a silent audio file or zero-length audio. Used by vitest and CI smoke render. Stored in the repo; used only in tests, not at runtime.

7. **Vitest suite** (`__tests__/timing.test.ts`, `__tests__/captions.test.ts`):
   - **timing.test.ts:** Test `sceneFrames(startSec, endSec, fps)` helper (calculate frame ranges). Edge cases: zero duration, fractional seconds, rounding behavior.
   - **captions.test.ts:** Test `layoutCaptions(words, maxWidth)` helper (group 3–5 words per line, no orphans, line-break rules). Golden fixtures with known-good layouts.
   - Both use snapshot tests (vitest `expect().toMatchSnapshot()`) for easy updates when intentional changes are made.

8. **CI smoke render** (in justfile's `check-renderer`, executed in `ci.yml`): `remotion still src/index.ts MorningReel out/smoke.png --props=src/fixtures/sample-reel.json --frame=60`. Frame 60 is the default in docs/07; for a 1-sec cover-only fixture, frame 60 is well past the end, so Remotion will render the last frame (cover). The smoke.png proves the full pipeline (props → composition → PNG) works on ubuntu-latest.

9. **Upload artefact** (in `ci.yml`): After smoke render, upload `out/smoke.png` if it exists, with 7-day retention. Visible on the PR for manual inspection.

## Risks

### 1. React version conflict between renderer and mobile
**Risk:** Remotion requires React ≥16.8.0 (broad peer range); this project could be pinned to React 19.3.0, while mobile uses 19.2.3. If major breaking changes occur in React, one or both projects may fail to type-check.
**Mitigation:** Keep each project's React version independent (separate pnpm lockfiles, `nodeLinker: hoisted` for mobile Metro). Pin Remotion to a stable version (4.0.534). Test indicates both projects pass `tsc --noEmit` with their respective versions. Revisit in T3.4 if issues arise.

### 2. Chrome headless shell download fails or is corrupted
**Risk:** Remotion auto-downloads the shell on first use; if the CDN is unreachable, the download is truncated, or the SHA does not match, `npx remotion still` fails silently or with an unclear error.
**Mitigation:** CI caches the shell at `packages/renderer/node_modules/.remotion` across runs. `just models` includes `npx remotion browser ensure` to pre-download on the laptop (T0.6). Smoke render step will fail the CI job if the shell is missing, providing clear feedback. Document the cache strategy in the README.

### 3. Fixture props become stale during development
**Risk:** As ReelScript schema evolves (T3.4), the hand-written `sample-reel.json` may have keys that are removed or required fields that are missing, causing the smoke render to fail.
**Mitigation:** The zod schema validates every smoke render; any mismatch is caught immediately. Update the fixture in the PR that changes the schema. Snapshot tests for captions and timing are not tied to fixture structure, so they are less brittle.

### 4. Vitest snapshot tests require manual approval after intentional changes
**Risk:** If caption layout or timing logic changes intentionally, all snapshots must be updated; a careless reviewer might approve without checking the visuals.
**Mitigation:** Document snapshot-update workflow in the PR template. Require the reviewer to run `vitest --ui` or check the diff. The schema zod test (not snapshot-based) catches logic errors; snapshots are for regression detection and golden layouts.

### 5. Design token values are hard to preview without rendering
**Risk:** The implementer may choose a color, spacing, or motion curve in `tokens.ts` that looks wrong on the owner's phone because the rendering context (safe area, font rendering, screen brightness) is not captured in a Remotion still.
**Mitigation:** In T0.4b/T4.5, the owner inspects the smoke still and the full render on their phone against the visual checklist in `docs/12-testing-and-quality.md` §4. Minor tweaks to tokens go into T4.4 or a post-T5.5 polish task. Document the design workflow so the implementer knows to expect feedback.

### 6. Composition structure is complex (Sequence nesting, frame math)
**Risk:** Off-by-one errors in `startFrame`/`endFrame` can cause scenes to overlap, cut short, or have dead time. A typo in timing logic is easy to miss in code review.
**Mitigation:** Vitest tests for `sceneFrames()` with known inputs/outputs (golden fixtures); property tests for monotonicity and non-overlap. The smoke render output includes timing metadata that can be spot-checked (ffprobe in T4.5). Acceptance test in T5.5 watches the reel and confirms scenes play in order and are complete.

### 7. Linting or formatting failures block CI without clear error messages
**Risk:** A Biome rule in `biome.json` may be too strict, or a file may have trailing whitespace, and the CI job fails with a confusing diff.
**Mitigation:** `just check-renderer` can be run locally before push; developers see the error immediately. Biome formatting is idempotent; `pnpm exec biome format .` fixes most issues automatically. Pre-commit hook runs biome-renderer on staged files, catching errors before commit.

## Open questions

1. **React version to use:** Should the renderer pin React 19.2.3 (same as mobile) or use the latest stable (19.3.0)? Remotion's peerDependencies accept >=16.8.0. Since the renderer and mobile are separate pnpm projects, they can differ, but pinning the same version reduces cognitive load.

2. **Fonts approach:** Should the renderer self-host Inter Tight and JetBrains Mono font files (OFL licensed, ~100 KB combined) in the repo, or fetch them at render time via `@remotion/google-fonts`? Self-hosting ensures offline renders and faster render time; fetching keeps the repo smaller but adds a network dependency at 05:30 AM.

3. **Smoke still frame:** Should the CI smoke render capture frame 60 only (current plan) or both frame 0 (cover only) and frame 60 (confirm cover is fully rendered)? Frame 60 is sufficient for a 1-sec cover-only fixture; frame 0 and 60 would catch both the start and end of the composition.

4. **Composition defaults for the fixture:** What should `fps`, `width`, `height`, and `durationInFrames` be for `sample-reel.json`? Proposal: 30 fps, 1080×1920, 2-3 seconds total (60–90 frames, covering cover + padding). This is enough to test timing math and scene sequencing without a full 8-scene reel.

5. **ReelProps zod schema:** Should the hand-written schema now match the full `docs/07-media-pipeline.md` §4 ReelProps (including `SceneProps`, `CaptionWord`) or a minimal cover-only subset? Full schema ensures T0.5 smoke render and T4.4 vitest tests use the final structure; minimal subset is quicker to scaffold and will be replaced in T3.4. Proposal: full schema, mirroring `docs/07` §4 exactly, so the implementer can validate the fixture immediately.

6. **Remotion version pin and Chrome Headless Shell:** Should the Remotion version (currently 4.0.534) be pinned to a major.minor (4.0.x) or exact (4.0.534)? Chrome Headless Shell version is auto-detected by Remotion; should a pin be added to `remotion.config.ts` to avoid surprises? Proposal: pin exact version (4.0.534) in `pnpm-lock.yaml`; Remotion's browser version is managed by Remotion's own versioning, no manual override needed.

7. **Artefact uploads in CI:** The current plan uploads `out/smoke.png` only. Should any other files (e.g., `out/smoke-timing.json` with render metadata) be uploaded? Proposal: PNG only; timing metadata is logged by Remotion and available in the job output. In T4.5, the full `reel.mp4` will be uploaded as an artefact by the render job's integration test, if needed.
