# T1.8 Brief: Replay and report

## Task

**ID:** T1.8

**Title:** Replay and report: `chronos wake replay`, `chronos wake annotate`, nightly report generator (Markdown) with score timeline, `GET /v1/report/{date}`

**Size:** M

**Depends:** T1.6

**Acceptance criteria:**
- Replay of fixture mornings under two rule versions prints a comparison table
- Report file produced for a fixture day

---

## Why it matters

T1.8 unlocks the most critical tuning loop: the owner can replay stored mornings against new rule candidates to validate that changes improve confirm latency without introducing false positives. Without replay, rule tuning is blind and risky.

The nightly report (required by D28 Observability) provides a Markdown audit trail of each day's behavior: timeline of ticks/scores, confirmation time vs. actual wake time, and anomaly flags (force-quit, clock skew, etc.). Developers and the owner can review failures together and add fixture mornings for edge cases.

The `annotate` CLI lets the owner record their actual wake time retroactively, which is essential for scoring (D06 requires every evaluation stored with full breakdown so the owner can replay and tune).

Without these tools, the wake engine remains a black box. Tuning becomes guesswork and the only feedback is "it didn't confirm in time."

---

## Governing decisions

| D# | Decision | Forces here |
|---|---|---|
| D06 | Scoring is a weighted additive algorithm; every evaluation stored with full breakdown | All stored evaluations (breakdown_json) must be readable for replay; replay must rebuild EvalContext exactly as service.py did; baseline comparisons are per-evaluation (not global) |
| D28 | Observability includes nightly Markdown report of the day's evaluations | Report generation is part of the scheduler daily loop; report file written to `data/logs/reports/<date>.md`; GET endpoint at `v1/report/{date}` serves the file as text/markdown |
| D25 | Timezone: phone sends IANA tz; server derives local date and window | Replay must use the tz from each evaluation; report header shows local_date, kind (weekday/weekend/holiday), and window_start/end in local time |
| D09 | Eager render mode: pipeline runs at window start − 30 min | Report timeline includes job durations (future in M3/M4); reels are pre-rendered so delivery is fast |

## Inputs and outputs

### Inputs

**For replay:**
1. **Date range + device:** `--from YYYY-MM-DD --to YYYY-MM-DD --device <id or 'default'>`
   - Pulls all `telemetry_events` in that range for the device
   - Re-parses raw_json into Signals (may fail on schema mismatch; skip with warning)
   - Must be in the DB (no import from CSV)

2. **Fixture morning mode:** `--fixture tests/fixtures/wake/mornings/<name>.json`
   - Loads a fixture JSON array of telemetry events
   - Replays against both stored rules (per-evaluation) and a candidate rules file
   - No DB access (pure in-memory replay)

3. **Rules selection:**
   - `--rules path/to/wake_rules.yaml` (candidate rules for comparison; optional)
   - If not provided, candidate = active rule version
   - Baseline per evaluation = stored rule_version_id (never changed)

## Constraints

1. **Replay is pure:** No DB writes, no I/O except reading telemetry_events and parsing raw_json
2. **Determinism:** Replaying stored data under the original rules must reproduce the stored scores exactly (regression test for scoring/service.py parity)
3. **Rule changes mid-day:** Baseline is per-evaluation (stored rule_version_id); candidate is uniform across the day
4. **Large ranges:** Avoid loading all evaluations into memory; stream per day, summarize as you go
5. **Invalid Signals:** If raw_json fails to parse under the Signals schema, skip the row with a warning and count it
6. **Scheduler integration:** The `report` action is added to the daily action list at day_boundary (03:00) for the *previous* local_date (idempotent; guarded by `settings.reports_dir`)
7. **Timezone/DST:** Report header shows local_date and window in the local timezone (tz from the day row); timeline uses device_ts with offset (as stored)
8. **Report retention:** Report files are written once and not rotated (they live in `data/logs/reports/`); retention job (T5.1) can purge old reports
9. **Media URLs in report:** Not needed yet; reserved for M3/M4 when job durations are logged
10. **Metrics target:** G1 target: median confirm latency ≤ 10 min after actual_wake_local; zero confirms > 30 min before it (checked in replay summary)

## Edge cases

1. **Days with no evaluations:**
   - Replay: skip, don't include in table
   - Report: generate anyway (empty timeline, counts = 0, state = initial)

2. **Days with no actual_wake_local:**
   - Latency calculation: n/a (show "n/a" or "—" in table)
   - Report: note that annotation is missing

3. **Multiple devices:**
   - Replay: `--device` filter required; default to "the single active device" (if exactly one)
   - Report: always per-device (local_date is key; device_id is implicit in the DB but should be confirmed from day row)

4. **Rules change mid-day (replay across rule versions):**
   - Each stored evaluation has rule_version_id; baseline = that version
   - Candidate rules applied uniformly to all ticks in the range
   - Table shows both; summary compares candidate to baseline

5. **raw_json schema mismatch:**
   - Older Signals payloads may fail Pydantic validation under a newer schema (e.g., new required field added)
   - Skip the row, log a warning, increment a "skipped" counter
   - Row should not appear in output

6. **High-confidence walk at 05:52 (before window), then asleep again:**
   - `steps_10m` at 06:00 = 100 from the walk 8 min ago
   - First window tick score high; second low (steps_10m = 0)
   - 2-tick rule does not fire (not consecutive high)
   - Real confirm at 08:10
   - Replay must show this: first tick high, second tick low, no confirm until later (test fixture: `early_walk.json`)

7. **Pedometer denied (reweighting path):**
   - First in-window tick with unlock + charger_disconnect + foreground (no pedometer) = strong confirm on first tick
   - Companion fixture shows that without foreground, max score < confirm threshold
   - Replay must test both paths

8. **Clock skew:**
   - Not stored (skew check happens at ingestion; events outside clock_skew_max_sec = 300 s are dropped before DB)
   - Report: no clock-skew section needed

9. **Force-quit before the window:**
   - `push_notifications` table shows zero `silent_push` events
   - Report flags this in "notes" section: "⚠️ Force-quit suspected: no silent push events recorded"

10. **Missed ticks within the 2-tick confirm window:**
    - Ticks at 07:00 and 07:12 both high (gap = 12 min, within confirm_max_gap_min)
    - Both should count as consecutive high
    - Ticks at 07:00 and 07:15 (gap = 15 min) do not count
    - Replay must validate this: test fixture `missed_ticks.json`

11. **DST transition (America/New_York, fall back):**
    - 02:00 EDT becomes 01:00 EST (repeated hour)
    - Window should be computed once per local_date (tz-aware, using the tz from the day row)
    - Device events may span both EDT and EST timestamps
    - Window.start_utc and Window.end_utc are absolute and do not change mid-evaluation
    - Test fixture: `dst_fall_back.json`

12. **Weekend vs. weekday windows:**
    - Weekday: 06:00–11:00
    - Weekend: 08:00–14:00
    - Report header shows the actual window for the day
    - Replay filters by `kind` from the day row (not recomputed)

## Proposed approach

### 1. New modules

**`services/api/src/chronos/wake/replay.py`**
- `ReplayRow` (dataclass): per-evaluation row (local_date, device_ts, score, decision, rule_version_id, etc.)
- `ReplayDay` (dataclass): aggregated per-day (date, kind, actual_wake_local, baseline_confirm_time, candidate_confirm_time, etc.)
- `replay_db_range(session, device_id, from_date, to_date, candidate_rules) -> list[ReplayDay]`
  - Queries telemetry_events and wake_evaluations for the range
  - Re-parses raw_json into Signals; skips on validation error (log warning)
  - Calls evaluate() for each event under candidate rules
  - Rebuilds EvalContext exactly as service.py does (previous tick, ticks_received)
  - Returns list of ReplayDay objects
- `replay_fixture(fixture_path, baseline_rules, candidate_rules) -> list[ReplayDay]`
  - Loads JSON fixture; re-plays in memory (no DB)
  - Returns same structure

**`services/api/src/chronos/report/builder.py`**
- `build_day_report(session, device_id, local_date) -> str`
  - Queries days, push_notifications, wake_evaluations, rule_versions for the day
  - Builds Markdown string with sections: header, state, counts, timeline, transitions, push errors, notes
  - Returns Markdown string (not written to disk; caller decides)
- Helper: `_timeline_table(evaluations) -> str` — Markdown table
- Helper: `_state_transitions(day_id) -> str` — transition list from day_transitions

**`services/api/src/chronos/report/sparkline.py`**
- `sparkline(scores: list[int], width: int = 30) -> str`
  - Takes list of scores (0–100)
  - Returns a unicode sparkline using `▁▂▃▄▅▆▇█` (8 levels)
  - Width = number of characters
  - Handles empty list

## Risks

1. **Scoring purity violation:** If `evaluate()` is modified to read from the DB or environment, replay will diverge from original scoring. **Mitigation:** Test that replaying original data under original rules reproduces stored scores exactly (regression test in every PR touching scoring.py).

2. **raw_json schema drift:** Adding required fields to Signals without a migration breaks replay of old telemetry. **Mitigation:** Signals schema is versioned (future work); replay must handle parse errors gracefully (skip + warning).

3. **EvalContext reconstruction failure:** If `service.py` changes how previous tick or ticks_received is computed, replay will diverge. **Mitigation:** Extract the context-building logic into a shared helper; both service.py and replay.py call it.

4. **Timezone-aware datetime bugs:** Incorrect UTC ↔ local conversion in report header or timeline. **Mitigation:** Replay and report use the `tz` from each telemetry_event or day row (not server tz); extensively test DST transitions.

5. **Performance on large ranges:** Loading all 30 days × 60 ticks = 1800 evaluations into memory could be slow. **Mitigation:** Process per-day, aggregate summary, do not hold full list (stream-friendly).

6. **Report scheduling race condition:** If two nodes try to write the report at the same time (future multi-device), they collide. **Mitigation:** V1 is single-device (D10); file write is atomic (SQLite-style); future: use a `reports_generated` flag in the day row.

## Open questions

1. **Replay source modes**: Should replay support both DB range queries (`--from --to`) and fixture JSON (`--fixture`)? The acceptance criteria mention "fixture mornings under two rule versions"; does that mean the default implementation should support both, or is fixture mode optional?

2. **Baseline rules selection for DB replay**: When replaying a DB range, baseline is the *stored* rule_version_id per evaluation (never changed). But what if the user wants to compare two *candidate* rule versions (neither of which was used originally)? Propose: `--baseline-rules path1.yaml --candidate-rules path2.yaml` for full flexibility, with fallback to stored rules if `--baseline` is omitted.

3. **Report file location and rotation**: Should old report files be kept or rotated? The retention job (T5.1) can purge reports > N days old. Propose: `data/logs/reports/` is kept indefinitely (no size limit); retention policy set per task; reports are small (~10 KB each).

4. **Device filtering in multi-device future**: V1 assumes one active device. When multiple devices exist, should `GET /v1/report/{date}` return all devices or require `?device=<id>`? Propose: require explicit device parameter or use the "active" device if exactly one exists.

5. **Report endpoint caching**: Should the API cache report files, or generate on-the-fly every time? Propose: read from disk if file exists (written by scheduler), else generate and serve (no cache); this ensures fresh data if scheduler fails.

6. **Annotate permission**: Should `PUT /v1/day/{date}/actual-wake` and `chronos wake annotate` be device-specific (user can only annotate their own days) or global admin? Propose: device-specific (authenticate via bearer token); CLI is admin (runs on the laptop).

7. **Early confirm flag threshold**: The "early?" flag in the replay table fires if any confirm > 30 min *before* actual_wake_local. Is 30 min the right threshold, or should it be tunable? Propose: hardcode 30 min for V1; make it a rule in wake_rules.yaml if tuning shows it should change.

8. **Report notes section anomalies**: Besides force-quit and pedometer_denied, what other anomalies should be flagged? Proposal list: (a) zero silent_push events → force-quit suspected; (b) pedometer_auth=denied on confirmation → reweighting applied; (c) consecutive high with gap > 12 min (shouldn't happen, data corruption); (d) score never reached threshold (day never confirmed, expected fallback).

9. **Sparkline scaling**: If all scores are low (e.g., 5–15), should the sparkline scale to 0–100 (full range, tall bars) or to the actual min/max of the data (finer granularity)? Propose: scale to 0–100 for consistency; if all scores ≤ 20, the bars will be tiny but that's the point (low scores).

10. **G1 metric in replay summary**: The summary line reports G1 (median latency ≤ 10 min, zero > 30 min before). Should this be a pass/fail badge, or just numbers? Proposal: one line per metric:
    ```
    Summary: 11 days | baseline median latency 15 min (❌ G1) | candidate median latency 12 min (✓ G1)
    ```

None of these block implementation; they are design nuances. The owner can answer by number.

## Summary

T1.8 delivers the tuning loop for the wake engine: `chronos wake replay` lets the owner compare rule versions on stored mornings; `chronos wake annotate` records actual wake times for latency calculation; the nightly report generator (scheduler-triggered and `GET /v1/report/{date}` endpoint) provides an audit trail of each day's evaluation timeline, state machine transitions, and anomaly flags. Together, they enable evidence-based rule tuning (D06) and provide the observability required by D28. ## Owner answers (2026-10-21)

Approved with the orchestrator's recommendations:

1. Replay sources: DB date range (`--from/--to [--device]`) and `--fixture path.json`.
2. Baseline = the rule version each stored evaluation was scored with; candidate = `--rules path`
   or `--rule-version N`. Replay never writes to the DB.
3. Report retention follows the logs policy in T5.1; T1.8 writes files idempotently.
4. `--device <public_id>` optional; default the single active device; error if ambiguous.
5. No caching; `GET /v1/report/{date}` serves the file if present, else builds in memory
   (text/markdown; 404 if no day row).
6. Annotate via CLI and the existing authenticated PUT; same validation.
7. Early-confirm threshold 30 min before `actual_wake_local`; `--early-min` flag.
8. Anomalies flagged: zero `silent_push` events inside the window (force-quit suspicion),
   pedometer denied, > 20 % deduped, ticks_sent − ticks_received ≥ 3, any push errors,
   fallback used.
9. Sparkline on a fixed 0–100 scale.
10. G1 line "median latency X min (target ≤ 10) · early confirms N (target 0) → PASS/FAIL" in the
    replay summary and the report.
11. Plain-text tables via typer unless `rich` is already a transitive dependency; `--json` flag.
    Scheduler writes the previous day's report once after the 03:00 boundary (tested with the
    fake clock).
